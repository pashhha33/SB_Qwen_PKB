# Архитектурная спецификация Second Brain

## 1. Основная модель

Second Brain представляет собой объектно-ориентированную базу знаний.

Базовая цепочка:

Тип объекта
↓
Экземпляр объекта
↓
Свойства
↓
Значения свойств

Классификация:

Таксономия
↓
Категория
↓
Экземпляр объекта

Связи:

Тип отношения
↓
Отношение
↓
Субъект ↔ Объект

Представление:

Объект
↓
Представление
↓
Base

Автоматизация:

Процесс
↓
Автоматизация
↓
QuickAdd / Templater / JS / Python

---

# 2. Универсальное ядро объекта

Каждый обычный объект имеет:

```yaml
---
id:
название:
тип_объекта:
категории:

aliases: []
tags: []
---
```

Обязательные предметные свойства:

- название;
    
- id;
    
- тип_объекта;
    
- категории.
    

Технические исключения:

- id;
    
- aliases;
    
- tags.
    

---

# 3. ID

Формат:

КОДТИПА-000001

Примеры:

WEBNOVEL-000001  
CHAPTER-000001  
PERSON-000001  
PROJECT-000001  
CATEGORY-000001  
TAXONOMY-000001  
RELATION-000001  
RELATION-TYPE-000001  
PROPERTY-000001  
PROPERTY-TYPE-000001  
OBJECT-TYPE-000001

ID:

- уникален;
    
- стабилен;
    
- неизменяем;
    
- не зависит от названия;
    
- не переиспользуется.

- возможожен ULID или UUID v7
    

---

# 4. Имена файлов

Основной формат:

Название — ID.md

Квадратные скобки в именах файлов запрещены.

Для отношений:

REL — Название отношения — RELATION-000001.md

REL является только префиксом имени файла.

# 7. Категории

`Категория` является самостоятельным объектом.

Объект содержит:

```yaml
категории:
  - "[[Название категории — CATEGORY-000001]]"
```

Категория содержит:

```yaml
таксономия:
родитель:
```

Иерархия строится через непосредственного родителя.

Предки вычисляются.

Корень категории определяется отсутствием родителя.

Искусственный объект «Корень» не создаётся.

---

# 8. Таксономии

Таксономия содержит:

```yaml
режим_иерархии:
кардинальность_назначения:
допустимые_типы_объектов:
требование_корня:
```

Допустимые значения:

режим_иерархии:

- строгая;
    
- полиaрхическая.
    

кардинальность_назначения:

- 0..1;
    
- 1;
    
- 0..N;
    
- 1..N.
    

требование_корня:

- один;
    
- несколько;
    
- не требуется.

# 9. Отношения

Принцип:

Тип отношения определяет семантику и правила.

Отношение хранит конкретную связь.

Простая связь:

```yaml
автор:
  - "[[Михаил Булгаков — PERSON-000001]]"
```

Сложная связь:

```yaml
---
id: RELATION-000001
название: Автор «Мастер и Маргарита»
тип_объекта: отношение

субъект: "[[Мастер и Маргарита — BOOK-000001]]"
тип_отношения: "[[Автор — RELATION-TYPE-000001]]"
объект: "[[Михаил Булгаков — PERSON-000001]]"
---
```

---

# 10. Тип отношения

Минимальное ядро:

```yaml
id:
название:
тип_объекта:

прямое_название:
обратное_название:
направление:
```

Дополнительно:

```yaml
рекомендуемый_субъект:
рекомендуемый_объект:
кардинальность:
правило_уникальности:
```

Рекомендуемые субъект и объект — ссылки на Тип объекта.

Рекомендация ≠ запрет.

---

# 11. Представления

`Представление` описывает семантическое назначение UI.

Пример:

```yaml
---
id: VIEW-000001
название: Карточка фильма
тип_объекта: представление

описание: Карточное представление объектов типа «Фильм».

целевые_типы_объектов:
  - "[[Фильм — OBJECT-TYPE-000003]]"

механизм: Base

активное: true
---
```

Base является основным механизмом.

Dataview применяется только при недостаточности Base.

DataviewJS — для сложной вычисляемой логики.

# 13. Автоматизация

`Автоматизация` описывает процесс.

Пример:

```yaml
---
id: AUTOMATION-000001
название: Создание объекта
тип_объекта: автоматизация

описание: Создание нового объекта по выбранному типу с заполнением обязательных метаданных.

триггер: ручной
механизм: QuickAdd

целевые_типы_объектов:
  - "[[Тип объекта — OBJECT-TYPE-000000]]"

активное: true
---
```

Код не является частью метамодели.

Он хранится в соответствующей технической реализации.

# 14. Наследование

Уровни:

1. универсальные;
    
2. семейства;
    
3. специализированные.
    

Дочерний FileClass может:

- уточнять обязательность;
    
- сужать кардинальность;
    
- добавлять ограничения;
    
- добавлять свойства.
    

Нельзя:

- менять смысл унаследованного свойства;
    
- менять его фундаментальный тип;
    
- ослаблять обязательность родительского свойства.

# 17. Миграции

При изменении типа объекта:

1. создаётся новый объект;
    
2. получает новый ID;
    
3. переносится только необходимая семантическая информация;
    
4. старый объект архивируется;
    
5. связь между объектами фиксируется.
    

ID никогда не переиспользуется.

---

# 18. Архивирование и объединение

Архивирование предпочтительнее удаления.

При объединении:

1. выбирается основной объект;
    
2. ссылки переводятся;
    
3. дубликат архивируется;
    
4. история сохраняется.
    

---

# 19. Контроль целостности

Проверки:

1. предварительная;
    
2. техническая;
    
3. структурная;
    
4. семантическая;
    
5. представлений;
    
6. постпроверка.
    

Результаты:

OK  
⚠ предупреждение  
❌ ошибка

Система не должна молча переписывать неправильные данные.
