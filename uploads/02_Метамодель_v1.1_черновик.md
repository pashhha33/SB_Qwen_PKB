# Метамодель

> Черновая редакция 1.1. Зафиксирован ULID как основной формат идентификатора, добавлен слой «Фасет» в классификацию. Остальные положения исходной версии сохранены до отдельного согласования.

## 1. Общие правила идентификации

Каждый объект метамодели и каждый экземпляр объекта имеет собственный стабильный `id`.

### 1.1. Формат ID

Основной и единственный формат идентификатора в текущей версии — ULID. UUID v7 не используется в новых объектах. Возможный переход на другой формат в будущем рассматривается как отдельное архитектурное решение с планом миграции.

Требования к `id`:

- уникален в пределах всей базы знаний;
- стабилен и не зависит от названия объекта;
- не меняется при переименовании объекта или файла;
- не переиспользуется после архивирования или удаления объекта;
- создаётся автоматически при создании объекта.

Формат ID — инфраструктурная настройка хранилища, а не предметное свойство объекта.

### 1.2. Префикс типа объекта

Каждому типу объекта назначается уникальный технический `TYPE_PREFIX`, например:

- `PERSON` — человек;
- `PROJECT` — проект;
- `PROPERTY` — свойство;
- `OBJECT-TYPE` — тип объекта;
- `RELATION-TYPE` — тип отношения.

Префикс является техническим кодом типа, а не отображаемым названием. Он должен быть уникальным в реестре типов и не должен зависеть от локализованного названия.

### 1.3. Имя файла

Канонический формат имени файла:

```text
{TYPE_PREFIX}-{ID}.md
```

Имя объекта не включается в имя файла. Отображаемое название хранится отдельно в свойстве `название`.

Примеры формата:

```text
PERSON-01J8Z6M4K2Q7V9X3N5B0C1D2EF.md
PROJECT-01J8Z6M4K2Q7V9X3N5B0C1D2EG.md
```

Это иллюстративный пример формата ULID, а не реальный ID объекта.

### 1.4. Ссылки Obsidian

Канонический формат ссылки на объект, которой управляет плагин:

```markdown
[[{TYPE_PREFIX}-{ID}.md|{название}]]
```

Пример:

```markdown
[[PERSON-01J8Z6M4K2Q7V9X3N5B0C1D2EF.md|Михаил Булгаков]]
```

Цель ссылки — каноническое имя файла, включая расширение `.md`; alias — актуальное отображаемое значение свойства `название`. ID в имени файла не зависит от отображаемого названия.

#### Нормализация ссылок, управляемых плагином

Плагин обязан формировать и поддерживать канонический формат для ссылок, которыми он управляет, в том числе ссылок в свойствах (frontmatter) объектов.

- При создании или заполнении свойства-ссылки плагин записывает ссылку в формате `[[имя-файла.md|название]]`.
- При проверке или исправлении управляемой ссылки плагин нормализует её цель до актуального канонического имени файла и alias — до актуального `название` целевого объекта, если цель однозначно определена.
- После переименования объекта плагин обновляет alias управляемых ссылок, когда может надёжно установить целевой объект.
- Если изменяется каноническое имя файла, плагин обновляет техническую часть управляемых ссылок в соответствии с новым именем.
- Если цель отсутствует, неоднозначна или не может быть надёжно определена, плагин сообщает о проблеме и не подставляет догадочное значение.
- Нормализация не должна запускать безусловную перезапись всех ссылок в хранилище. Она применяется к ссылкам, созданным или обслуживаемым плагином, либо в рамках явно запущенной пользователем проверки/миграции.
- Плагин не должен менять семантическую цель ссылки только ради приведения её к формату. Сначала требуется однозначно определить целевой объект.

#### Каноническое название и псевдонимы (`aliases`)

Поле `aliases` хранит каноническое название объекта в фиксированной позиции, а также дополнительные псевдонимы. Каноническое название намеренно дублируется в `aliases`; это системное правило, а не ошибка данных.

- `aliases[0]` — фиксированное место для актуального канонического значения `название`.
- При создании объекта плагин автоматически записывает `название` первым элементом `aliases`.
- При изменении `название` плагин обновляет `aliases[0]`, сохраняя остальные элементы списка.
- Дополнительные псевдонимы добавляются после фиксированного первого элемента. Они не заменяют, не вытесняют и не меняют позицию канонического названия.
- Если пользователь задаёт для управляемой ссылки отображаемый текст, отличающийся от канонического `название`, плагин рассматривает этот текст как возможный новый псевдоним и добавляет его в `aliases` после проверки согласно режиму работы плагина.
- Перед добавлением нового псевдонима плагин проверяет его на совпадение с каноническим названием и уже существующими псевдонимами (с нормализацией пробелов и без учёта регистра). Повторные значения не добавляются.
- Существующие дополнительные псевдонимы сохраняются; добавление нового не должно заменять или очищать список `aliases`.
- После сохранения нового псевдонима управляемая ссылка нормализуется к каноническому виду `[[{TYPE_PREFIX}-{ID}.md|{название}]]`. Альтернативное имя сохраняется в `aliases`, а ссылка продолжает отображать актуальное каноническое название.
- Если целевой объект не определён однозначно, плагин не изменяет `aliases` автоматически и сообщает о проблеме.

Пример:

```yaml
название: Михаил Булгаков
aliases:
  - Михаил Булгаков # фиксированное место: каноническое название
  - М. Булгаков     # дополнительный псевдоним
```

Переименование свойства `название` не меняет ID и не должно менять идентичность объекта. Alias канонической управляемой ссылки обновляется до актуального `название`; альтернативные имена хранятся в `aliases` целевого объекта.

### 1.5. Изменение типа объекта

Изменение названия не меняет ID, TYPE_PREFIX или имя файла.

Изменение типа существующего объекта не должно автоматически менять его ID. Правила допустимости смены типа и её последствия для `TYPE_PREFIX` и имени файла необходимо определить отдельно. До принятия такого правила смена типа считается контролируемой операцией, а не обычным редактированием метаданных.

## 2. Тип объекта

Физическое ядро:

```yaml
---
id: <ULID>
название: Человек
тип_объекта: тип_объекта

родительский_тип:
  - "[[OBJECT-TYPE-<ULID>|Контекст]]"

описание: Объект, представляющий конкретного человека.
---
```

Имя файла этого примера строится отдельно по правилу `OBJECT-TYPE-{ID}.md`.

Правило наследования: хранится только непосредственный родительский тип. `семейство` отдельно не хранится.

## 3. Тип свойства

Восемь самостоятельных объектов:

- Текст
- Число
- Дата
- Дата и время
- Логическое
- Список
- Ссылка
- Список ссылок

Набор фундаментальных типов закрыт для текущей версии.

Каждый тип свойства также получает собственный ULID и файл вида `PROPERTY-TYPE-{ID}.md`.

## 4. Свойство

```yaml
---
id: <ULID>
название: Название
тип_объекта: свойство

тип_значения: "[[PROPERTY-TYPE-<ULID>|Текст]]"

кардинальность: 1
обязательность: обязательное

определение: Читаемое человеком название объекта.

область_применения:
  - универсальное

уровень: универсальное

жизненный_цикл: стандартное
---
```

Технические ограничения не входят в семантическое ядро. Они определяются при реализации FileClass и плагина.

## 5. Тип отношения

```yaml
---
id: <ULID>
название: Автор
тип_объекта: тип_отношения

прямое_название: автор
обратное_название: автор произведения
направление: направленное

рекомендуемый_субъект:
  - "[[OBJECT-TYPE-<ULID>|Произведение]]"

рекомендуемый_объект:
  - "[[OBJECT-TYPE-<ULID>|Человек]]"

кардинальность: 0..N
правило_уникальности: уникальная_связь
---
```

Рекомендуемые субъект и объект задают допустимые или предпочтительные типы согласно правилам, которые будут отдельно уточнены; сами по себе рекомендации не следует считать запретом.

---

## 6. Отношение

```yaml
---
id: <ULID>
название: Автор «Мастер и Маргарита»
тип_объекта: отношение

субъект: "[[BOOK-<ULID>|Мастер и Маргарита]]"
тип_отношения: "[[RELATION-TYPE-<ULID>|Автор]]"
объект: "[[PERSON-<ULID>|Михаил Булгаков]]"
---
```

Используется гибридная модель:

- простая связь без собственных атрибутов, истории или контекста может храниться как ссылка в свойстве объекта;
- связь с собственными атрибутами, контекстом, периодом действия, источником или иными значимыми данными моделируется отдельным объектом `Отношение`.

Дополнительные свойства отношения могут включать:

- порядок;
- основное;
- дата_начала;
- дата_окончания;
- источник;
- контекст;
- описание.

Правило преобразования простой ссылки в самостоятельное отношение и синхронизации двух форм представления требует отдельной спецификации. Нельзя допускать неявного дублирования одной связи.

## 7. Классификация: таксономия, фасет, категория

Предварительная модель классификации содержит четыре уровня:

```text
Таксономия
  └── Фасет
        └── Категория
              └── Назначение категории объекту
```

### 7.1. Таксономия

`Таксономия` — самостоятельный объект, который объединяет один или несколько фасетов в рамках согласованной системы классификации. Она задаёт общие правила и область применения. Конкретные значения классификации хранятся в категориях фасетов.

```yaml
---
id: <ULID>
название: Классификация художественных произведений
тип_объекта: таксономия

фасеты:
  - "[[FACET-<ULID>|Жанр]]"
  - "[[FACET-<ULID>|Тональность]]"

допустимые_типы_объектов:
  - "[[OBJECT-TYPE-<ULID>|Книга]]"
  - "[[OBJECT-TYPE-<ULID>|Фильм]]"
---
```

### 7.2. Фасет

`Фасет` — самостоятельный объект метамодели, представляющий отдельное измерение классификации. Он не считается просто синонимом таксономии: одна таксономия может объединять несколько фасетов, например `Жанр`, `Тональность`, `Место действия` или `Тематическая область`.

```yaml
---
id: <ULID>
название: Жанр
тип_объекта: фасет

таксономия: "[[TAXONOMY-<ULID>|Классификация художественных произведений]]"
режим_иерархии: строгая
кардинальность_назначения: 0..N
требование_корня: несколько
---
```

Предлагаемое правило: настройки иерархии и назначения задаются на уровне фасета, поскольку разные измерения одной таксономии могут иметь разные правила. Таксономия определяет общую область и набор фасетов. Допустимость такого разделения и необходимость наследовать значения по умолчанию от таксономии остаются предметом дальнейшего согласования.

### 7.3. Категория

`Категория` — значение внутри одного конкретного фасета. Иерархия категорий строится через непосредственного родителя; предки вычисляются. Корневая категория не имеет родителя.

```yaml
---
id: <ULID>
название: Научная фантастика
тип_объекта: категория

фасет: "[[FACET-<ULID>|Жанр]]"
родитель: []
---
```

Пример дочерней категории:

```yaml
---
id: <ULID>
название: Космическая опера
тип_объекта: категория

фасет: "[[FACET-<ULID>|Жанр]]"
родитель:
  - "[[CATEGORY-<ULID>|Научная фантастика]]"
---
```

Категория принадлежит ровно одному фасету в рамках текущего чернового решения. Перенос категории в другой фасет должен быть контролируемой операцией, поскольку может менять смысл её назначения.

### 7.4. Назначение категорий объектам

Объект получает классификацию через назначение одной или нескольких категорий. Каждая категория однозначно указывает на фасет, поэтому фасет назначения можно определить через категорию. На уровне метамодели нужно различать:

- ограничения таксономии на типы объектов;
- правила назначения категорий, определённые фасетом;
- конкретные категории, назначенные экземпляру объекта.

Формат хранения назначений в метаданных обычного объекта и способ проверки кардинальности будут уточнены в спецификации реализации плагина.

## 10. Обёртка изображения и контекстное разрешение

`Обёртка изображения` — самостоятельный объект, представляющий изображение и его семантическое использование. Один объект-обёртка может быть связан с несколькими объектами базы знаний и использоваться в разных контекстах.

Плагин должен предусматривать механизм контекстного разрешения запросов к обёрткам изображений (*Image Wrapper Resolution*). Цель механизма — находить подходящую существующую обёртку и автоматически использовать связанное изображение и/или заданные метаданные, чтобы пользователю не приходилось каждый раз вручную указывать файл и повторно вводить одни и те же сведения.

### 10.1. Контекст запроса

Запрос на изображение может определяться сочетанием следующих данных:

- текущий объект и его тип;
- семантическая роль изображения, например `обложка`, `баннер`, `логотип`, `портрет`, `аватар`, `превью` или `фон`;
- целевой объект, к которому относится изображение;
- конкретное представление или место, в котором изображение требуется показать;
- дополнительные ограничения, если они заданы.

Пример: представление типа `Карточка фильма` запрашивает изображение с ролью `обложка` для конкретного объекта типа `Фильм`. Плагин ищет подходящую обёртку, связанную с этим фильмом и имеющую требуемую роль.

### 10.2. Результат разрешения

В зависимости от места использования плагин может:

1. вернуть ссылку на файл изображения или само изображение для отображения;
2. предоставить ссылку на объект-обёртку;
3. подставить разрешённые к автозаполнению метаданные обёртки;
4. сообщить, что подходящая обёртка не найдена или что найдено несколько равнозначных кандидатов.

### 10.3. Правила безопасности данных и неоднозначности

- Предпочтительно использовать ссылку на исходную обёртку, а не копировать все её данные в другие объекты.
- Автоматическое копирование метаданных допускается только для явно определённых полей и сценариев.
- Если подходящего изображения нет, плагин не должен молча выбирать произвольное изображение.
- Если найдено несколько кандидатов и правило приоритета не даёт однозначного результата, плагин должен запросить выбор пользователя либо применить заранее настроенное правило.
- Разрешение запроса само по себе не должно менять исходную обёртку или её метаданные.
- Удаление, архивирование или изменение роли обёртки должно учитываться механизмом проверки целостности и разрешения запросов.

### 10.4. Два сценария использования

Плагин должен поддерживать оба сценария:

1. **Динамическое отображение.** Представление запрашивает изображение по контексту и использует найденную обёртку без записи или дублирования её данных в метаданные текущего объекта.
2. **Автозаполнение метаданных.** В предусмотренных сценариях создания или редактирования объекта плагин может заполнить выбранные свойства данными обёртки. Автозаполнение должно быть ограничено явно разрешёнными полями и не должно незаметно перезаписывать пользовательские значения.

Динамическое разрешение запроса само по себе не изменяет данные. Запись метаданных — отдельная операция с собственными правилами.

### 10.5. Разделение метамодели и реализации

Метамодель описывает семантические данные, необходимые для разрешения запроса: связь обёртки с целевым объектом, роль изображения и метаданные. Алгоритм поиска, кэширование, реакция на изменения файлов и способ интеграции с представлениями относятся к реализации плагина.

На текущем этапе не фиксируется конкретный способ перехвата запросов. Отдельно предстоит определить, в каких местах Obsidian плагин должен разрешать такие запросы: при построении представления, при создании/редактировании заметки, через специальное поле или команду, либо сочетая несколько способов.

## 11. Создание объектов из пустых ссылок

Плагин должен поддерживать создание объектов из неразрешённых внутренних ссылок Obsidian (пустых ссылок), используя контекст места, в котором находится ссылка. Цель — сократить ручной ввод и выбирать тип объекта по правилам метамодели, не создавая объекты неверного типа автоматически.

### 11.1. Пустая ссылка в свойстве

Если пустая ссылка находится в значении свойства объекта, плагин определяет контекст по доступным сведениям:

- тип текущего объекта;
- свойство, в котором находится ссылка;
- объявление свойства и его тип значения;
- допустимые типы целевых объектов и другие ограничения, если они заданы в метамодели.

Далее применяются следующие правила:

1. **Контекст однозначно определяет один тип объекта.** Плагин предлагает создать объект этого типа; при явно разрешённом сценарии автоматического создания может сразу подготовить форму создания с уже выбранным типом.
2. **Контекст допускает несколько типов объектов.** До создания плагин показывает список допустимых типов и просит пользователя выбрать один из них.
3. **Контекст не определяет допустимый тип.** Плагин просит выбрать тип объекта либо сообщает, что для данного свойства не настроены правила создания. Он не должен угадывать тип по одному только тексту ссылки.
4. **Свойство допускает только ссылки на уже существующие объекты.** Плагин не предлагает создавать новый объект через это свойство, если такое поведение явно не разрешено его настройками.

После выбора типа плагин создаёт объект по общим правилам: генерирует ULID, назначает канонический префикс типа, формирует имя файла, заполняет обязательные метаданные и нормализует ссылку.

### 11.2. Пустая ссылка вне свойства

Если пустая ссылка обнаружена в обычном тексте заметки или в другом месте, для которого нельзя надёжно определить контекст свойства, плагин **до создания объекта** предлагает пользователю выбрать тип объекта. После выбора он создаёт объект и приводит ссылку к каноническому формату.

Если другой явный контекст доступен (например, команда создания объекта, вызванная из конкретного представления), плагин может использовать его как предварительно выбранный тип, но должен позволять пользователю проверить выбор до создания.

### 11.3. Каноническая ссылка после создания

После успешного создания или выбора существующего объекта плагин должен нормализовать обслуживаемую им ссылку по общему правилу:

```markdown
[[{TYPE_PREFIX}-{ULID}.md|{название}]]
```

В свойствах ссылка должна сохранять корректный формат значения, совместимый с типом свойства. Если пользователь выбрал существующий объект, новый объект не создаётся: ссылка нормализуется на выбранную цель.

### 11.4. Дубликаты и безопасность

- Перед созданием плагин проверяет, не существует ли уже объект с тем же каноническим именем файла или ULID.
- Само наличие пустой ссылки не означает, что объект уже создан; создание выполняется только после выбора типа и подтверждения в соответствующем сценарии.
- Если ссылка может соответствовать нескольким существующим объектам или имя не позволяет однозначно установить цель, плагин показывает варианты выбора, а не создаёт объект вслепую.
- Плагин не должен молча менять тип существующего объекта ради соответствия контексту свойства.
- Ошибки создания и несоответствия ограничениям свойства должны быть показаны пользователю; они не должны приводить к незаметному изменению данных.

### 11.5. Разделение правил и реализации

Метамодель определяет допустимые типы значений, типы объектов и ограничения свойств. Определение контекста ссылки, показ формы выбора, создание файла и последующая нормализация ссылки относятся к поведению плагина. Конкретные точки интеграции с интерфейсом Obsidian будут определены на этапе проектирования реализации.

## 14. Системные атрибуты и расширяемые свойства

### 14.1. Архитектурный принцип

Принято предварительное решение **B: фиксированное ядро системных атрибутов плюс расширяемый системный слой**. Ядро реализуется в коде плагина; дополнительные определения и правила могут задаваться метамоделью в хранилище.

Нужно различать:

- **системные атрибуты** — часть базового контракта объекта, необходимые для идентификации и управления объектом;
- **предметные свойства** — описывают объект и определяются метамоделью и типом объекта;
- **расширяемые системные атрибуты** — дополнительные атрибуты со специальным поведением, если такое поведение явно поддерживается ядром и описано в метамодели.

Системные атрибуты не должны случайно становиться необязательными или переопределяться как обычные предметные свойства. Плагин должен обеспечивать их базовые инварианты независимо от того, какие предметные свойства определены для конкретного типа объекта.

### 14.2. Базовый контракт

Предварительный минимальный набор системных атрибутов:

- `id` — стабильный ULID;
- `type` / существующее поле типа объекта — техническая идентификация типа; окончательное имя поля нужно согласовать с текущим `тип_объекта`;
- `название` — каноническое отображаемое имя;
- `aliases` — список, в котором `aliases[0]` дублирует актуальное `название`, а дополнительные псевдонимы следуют после него по правилам раздела 1.4;
- `created_at` и `updated_at` — возможные системные даты. Их обязательность, формат и политика обновления пока не утверждены.

**Важно:** решение о полном переименовании `тип_объекта` в техническое поле `type` не принято. До отдельного согласования сохраняется существующая терминология и схема в остальных разделах документа.

`название` относится к системному контракту, а не к обычному расширяемому предметному свойству. Определение этого атрибута не должно дублироваться как независимое обычное свойство метамодели без явно установленной связи между системным контрактом и его описанием.

### 14.3. Ответственность ядра и метамодели

Ядро плагина отвечает за механизмы: чтение и запись файлов, проверку базового контракта объекта, загрузку метамодели, построение форм, валидацию, обновление кэша и проведение миграций.

Метамодель определяет предметные типы объектов, свойства, типы значений, допустимые ссылки, ограничения, фасеты, категории и другие поддерживаемые сущности. Добавление обычного предметного свойства не должно требовать изменения исходного кода или перекомпиляции плагина.

Наличие определения нового свойства само по себе не означает автоматическую запись значения во все существующие объекты. Заполнение выполняется при создании/редактировании, явной пакетной операции или миграции, если она требуется.

## 15. Служебная область плагина `.sb/`

### 15.1. Принцип хранения

Принято предварительное решение: служебные данные и определения метамодели располагаются в скрытой папке `.sb/` в корне хранилища Obsidian. Штатное редактирование метамодели выполняется командами и интерфейсом плагина.

Скрытая папка является соглашением об организации файлов, а не механизмом безопасности. Пользователь технически может изменить её содержимое вручную; поэтому плагин обязан проверять данные при загрузке и перед применением, а не считать файлы неизменяемыми.

### 15.2. Предварительная структура

```text
Vault/
├── .sb/
│   ├── config.json
│   ├── metamodel/
│   │   ├── object-types/
│   │   ├── properties/
│   │   ├── property-types/
│   │   ├── relation-types/
│   │   ├── taxonomies/
│   │   ├── facets/
│   │   └── views/
│   ├── migrations/
│   ├── backups/
│   └── logs/
├── Books/
├── People/
├── Ideas/
└── ...
```

Структура предварительная. Не все каталоги обязаны войти в первую реализацию. Каталоги для категорий, отношений, автоматизаций и обёрток изображений можно добавить в соответствии с выбранной физической моделью хранения.

### 15.3. Форматы хранения

Для MVP предлагается использовать:

- **JSON** — для служебных определений метамодели и конфигурации;
- **Markdown с YAML frontmatter** — для обычных объектов базы знаний и человекочитаемой документации.

JSON выбран как основной формат определений, потому что он удобен для строгого программного чтения, проверки и записи. Определения рекомендуется хранить отдельными файлами, а не одним большим файлом: это упрощает независимые изменения, сравнение версий и восстановление.

Ссылки между определениями должны опираться на стабильные ID, а не на отображаемые названия или локализованные имена файлов. Пример ниже иллюстрирует направление и не утверждает окончательную схему полей:

```json
{
  "id": "01JEXAMPLEPROPERTY000000001",
  "kind": "property",
  "key": "publisher",
  "name": "Издательство",
  "valueType": "objectReference",
  "targetTypes": ["Organization"],
  "required": false,
  "multiple": false
}
```

Идентификаторы `kind`, `key`, `valueType`, `targetTypes` и английские имена полей в примере являются предварительным техническим предложением. Их нужно согласовать с существующей схемой метамодели, прежде чем считать нормативными. Семантические названия и отображаемые подписи могут быть локализованы отдельно от технических ключей.

Скрытые JSON-файлы не следует строить на предположении, что они являются обычными заметками Obsidian или поддерживают `[[wikilinks]]`. Плагин должен читать и проверять их через файловый API, разрешая ссылки на сущности по стабильным ID.

### 15.4. Редактирование и контроль изменений

Основной поддерживаемый способ изменения метамодели — команды и интерфейс плагина. Пользователь должен иметь возможность создавать и редактировать типы, свойства, фасеты и другие поддерживаемые сущности без непосредственного редактирования JSON.

Любое изменение определения проходит последовательность:

1. принять команду или обнаружить изменение файла;
2. разобрать содержимое и проверить структуру;
3. проверить обязательные поля, уникальность ID и ссылочную целостность;
4. проверить совместимость с текущей метамоделью и затрагиваемыми объектами;
5. для потенциально разрушительных изменений показать предварительный просмотр последствий;
6. при необходимости создать резервную копию и запросить подтверждение;
7. сохранить изменение;
8. повторно проверить сохранённую версию и обновить внутренний кэш только после успешной проверки.

Обычное добавление определения свойства не должно автоматически переписывать существующие объекты. Если изменение схемы требует преобразования данных, плагин должен оформить его как явную миграцию или пакетную операцию.

### 15.5. Ручные изменения

Принята рекомендация: ручное редактирование файлов технически возможно, но не является основным поддерживаемым рабочим процессом. Если плагин обнаруживает изменения файлов метамодели, он должен перечитать их и провести полную проверку до применения.

- Корректное и совместимое изменение может быть принято после валидации и обновления кэша.
- Некорректное изменение не должно применяться молча; плагин показывает ошибку и, если доступна последняя корректная версия, продолжает использовать её до исправления.
- Изменение, которое может нарушить данные или требует преобразования существующих объектов, требует предварительного просмотра и контролируемой миграции.
- Плагин не должен без предупреждения перезаписывать ручные изменения или автоматически восстанавливать файл из резервной копии.
- Если невозможно надёжно установить, какую версию применять, нужно сообщить о конфликте и запросить действие пользователя.

Для обнаружения изменений предполагается использовать события файлового API Obsidian и/или проверку актуальности при загрузке и перед критическими операциями. Точная стратегия обнаружения и разрешения конфликтов относится к реализации.

### 15.6. Резервирование и журналирование

Архитектура должна предусматривать возможность создавать резервную копию перед разрушительными изменениями метамодели и журналировать значимые операции. Полнота и срок хранения резервных копий, формат журнала, уровни детализации и механика восстановления пока не утверждены и могут реализовываться поэтапно.

## 16. Предварительные архитектурные решения по служебному слою

На текущем этапе зафиксированы как рабочие решения черновика:

1. Фиксированное ядро системных атрибутов плюс расширяемый системный слой, управляемый через метамодель там, где это поддерживает ядро.
2. `название` является системным атрибутом, а не обычным предметным свойством; правило синхронизации `aliases[0]` с `название` сохраняется.
3. Служебные данные размещаются в `.sb/` в корне хранилища Obsidian.
4. JSON — предложенный основной формат хранения определений метамодели в MVP; Markdown/YAML остаётся форматом обычных объектов и документации.
5. Штатное редактирование метамодели производится через команды и интерфейс плагина.
6. Ручные изменения файлов не запрещаются на уровне файловой системы, но принимаются только после проверки плагином.
7. Изменения схемы не должны молча переписывать существующие объекты; преобразования данных оформляются отдельно.
8. Перед потенциально разрушительными изменениями предусматриваются предварительный просмотр и подтверждение; резервирование и журналирование закладываются в архитектуру.

Эти решения сохраняют статус черновика v1.1 и не означают, что вся функциональность уже реализована. Точная JSON-схема, перечень системных атрибутов, структура всех каталогов `.sb/` и протокол разрешения конфликтов остаются предметом последующего уточнения.

## 17. Отображаемые названия объектов в интерфейсе Obsidian

### 17.1. Цель и терминология

Плагин должен по возможности показывать человеку читаемое значение системного атрибута `название` вместо технического имени файла в основных областях интерфейса Obsidian. Это **подмена отображения**, а не физическое переименование файла.

Следует различать три значения:

- **Физическое имя файла** — стабильное техническое имя вида `{TYPE_PREFIX}-{ID}.md`. Оно не меняется только ради отображения читаемого названия.
- **Каноническое название объекта** — значение системного атрибута `название`, используемое как основной источник отображаемого имени.
- **Текст ссылки** — отображаемый текст Markdown-ссылки или wikilink. Его нормализация регулируется отдельно правилами канонических ссылок и не должна выполняться как побочный эффект визуальной подмены.

Архитектурный ориентир — плагин Front Matter Title, который отдельно обрабатывает названия в разных частях интерфейса. Мы заимствуем общий принцип разделения разрешения названия и точек его отображения, но не предполагаем, что все области Obsidian доступны через единый публичный API.

### 17.2. Источник названия и резервное поведение

1. Канонический источник отображаемого названия — системный атрибут `название` объекта.
2. Разрешение названия должно опираться на стабильную идентичность объекта (`id`/ULID), а не на совпадение строк названий.
3. Если `название` отсутствует, пустое или не может быть надёжно прочитано, отображается резервное имя на основе физического имени файла.
4. Одинаковые названия у разных объектов допустимы, если другие правила метамодели не устанавливают ограничение уникальности. Подмена названия не должна объединять такие объекты или менять разрешение ссылок.
5. При изменении `название` внутренний индекс должен обновляться без перезапуска плагина, насколько это позволяет жизненный цикл файлов и кэша Obsidian.
6. Отображение само по себе не должно изменять Markdown-файл, `aliases`, ID или физическое имя файла. Синхронизация `aliases[0]` с `название` остаётся отдельным ранее установленным правилом жизненного цикла объекта.

### 17.3. Архитектура механизма

Для отделения общей логики от специфики интерфейса предлагается следующий внутренний слой:

- `TitleResolver` — получает объект/файл и определяет каноническое отображаемое название с резервным поведением.
- `TitleIndex` — хранит в памяти актуальное соответствие стабильных ID объектам и их отображаемым названиям; обновляется при загрузке, создании, изменении и удалении объектов. Это предлагаемая архитектурная абстракция, не готовый API Obsidian.
- `TitleDisplayAdapter` — общий контракт адаптера, который применяет отображаемое название в одной конкретной области интерфейса.
- Конкретные адаптеры (например, `ExplorerTitleAdapter`, `TabTitleAdapter`, `LinkSuggestTitleAdapter`) включаются и тестируются независимо. Названия классов предварительные.

Общая логика не должна зависеть от типа объекта. Книги, люди, идеи, отношения, фасеты и другие объекты используют один механизм разрешения названия, если для них задан системный атрибут `название`.

|---|---|---|---|
| Файловый проводник | Показывать `название` вместо технического имени | Отдельный адаптер проводника; проверить доступность и устойчивость интерфейсной точки | Высокий |

### 17.5. Уровни интеграции и ограничения

Интеграции следует классифицировать по уровню устойчивости:

1. **Публичный API Obsidian** — предпочтительный путь для чтения файлов, метаданных, наблюдения за изменениями и взаимодействия с рабочими областями. Наличие этих API само по себе не гарантирует возможность заменить любую системную подпись.
2. **DOM-интеграция** — может понадобиться для изменения отображаемых подписей в отдельных элементах интерфейса. Такая интеграция зависит от структуры интерфейса и требует регрессионных тестов после обновлений Obsidian.
3. **Внутренние API** — допускаются только при необходимости, когда нет устойчивой публичной точки интеграции. Каждый такой случай изолируется в отдельном адаптере, документируется и тестируется отдельно.

Плагин не должен заявлять гарантированную поддержку всех областей интерфейса до проверки. Если адаптер перестал работать после обновления Obsidian, он должен по возможности отключаться или деградировать отдельно, не нарушая идентичность объектов и работу остальных функций.

### 17.6. Объём MVP

Предлагается реализовывать отображение поэтапно:

**Этап 1 — ядро названий:** `TitleResolver`, резервное имя, индекс актуальных названий и обновление индекса при изменениях объектов.

**Этап 2 — базовая навигация:** файловый проводник, заголовок открытой вкладки и заголовок заметки. Каждая область включается в MVP только после проверки реализуемости и стабильности. Если inline title требует хрупкого вмешательства, его поддержка должна быть обозначена как экспериментальная либо перенесена на следующий этап.

**Этап 3 — создание ссылок:** автодополнение внутренних ссылок и быстрый переключатель. Отображаемое название используется для удобства выбора, но выбор цели и разрешение ссылки опираются на ID/технический путь, а не только на текст названия.

**Этап 4 — расширение покрытия:** поиск, обратные ссылки, закладки, граф и Canvas — отдельными адаптерами после прототипирования.

### 17.7. Критерии готовности MVP

- Изменение `название` не переименовывает физический файл.
- Поддерживаемые области показывают актуальное название объекта.
- Изменение названия обновляет отображение без перезапуска плагина, если это поддерживается соответствующей точкой интеграции.
- Пустое или недоступное `название` приводит к резервному отображению, а не к пустой подписи или ошибке.
- Разные объекты с одинаковыми названиями остаются различными объектами; разрешение целей не основывается исключительно на отображаемом тексте.
- Подмена отображения не переписывает содержимое Markdown, ссылки или `aliases`.
- Сбой одного адаптера не должен блокировать `TitleResolver` и другие адаптеры.
- Поддерживаемые версии Obsidian и известные ограничения каждого адаптера документированы и проверяются регрессионными тестами.

### 17.8. Статус решения

Зафиксировано как архитектурное направление черновика `v1.1-draft`: системный атрибут `название` является каноническим источником читаемого отображаемого имени; физическое имя файла с техническим префиксом и ULID сохраняется; отображение реализуется отдельным слоем разрешения названий и независимых адаптеров.

Не утверждены окончательно: полный список поддерживаемых областей интерфейса, точные способы интеграции для каждой области, минимальная версия Obsidian, использование DOM/внутренних API и конкретный охват первой поставки. Эти пункты требуют прототипа и проверки совместимости.

## 18. Валидация свойств, формы редактирования и интеграция с Bases

### 18.1. Архитектурное решение

Зафиксировано предварительное архитектурное решение `v1.1-draft`:

1. **Second Brain владеет метамоделью и правилами целостности данных.** Определения типов объектов, свойств, допустимых типов целей и ограничений хранятся в служебной области `.sb/` и интерпретируются ядром плагина.
2. **Ввод и редактирование поддерживаются двумя путями:** через стандартную панель Properties Obsidian и через собственный интерфейс Second Brain.
3. **Для свойств предусматривается специализированная модалка редактирования**, по общему UX-принципу похожая на интерфейс Fileclass: типизированные поля, списки допустимых значений, выбор ссылок на объекты и контекстные фильтры там, где они поддерживаются. Это не означает обязательного копирования интерфейса или зависимости от кода Fileclass.
4. **Валидация не зависит от интерфейса.** Одни и те же правила применяются к значениям, введённым через собственную модалку, записанным командами плагина или изменённым вручную/через стандартную панель Properties.
5. **Bases рассматривается как необязательная интеграция** для запросов, фильтрации кандидатов и динамических представлений. Bases не является источником истины для схемы Second Brain и не заменяет валидатор.
6. **Fileclass рассматривается как референсная реализация и потенциальная точка интеграции, но не обязательная зависимость.** Базовый функционал Second Brain должен оставаться работоспособным при отключённых Fileclass и Bases.

### 18.2. Разделение фильтрации и валидации

В архитектуре необходимо явно различать два механизма:

- **Фильтрация кандидатов (`Candidate Filtering`)** — определяет, какие значения предлагаются пользователю в списке выбора. Например, для свойства `автор` можно предлагать только объекты типа `PERSON`, а для свойства `том` — только тома выбранной серии.
- **Проверка сохранённого значения (`Value Validation`)** — проверяет, соответствует ли фактически записанное значение схеме свойства и текущему контексту объекта. Она нужна даже тогда, когда значение было выбрано из отфильтрованного списка.

Фильтр интерфейса не гарантирует целостность данных: значение может быть изменено через Properties, вручную в Markdown/YAML, другим плагином или после изменения связанного свойства. Поэтому ядро должно проверять как новые значения при записи через API Second Brain, так и обнаруженные изменения существующих объектов.

### 18.3. Ответственность Schema Engine

Предлагается выделить внутренний модуль `SchemaEngine` (техническое имя предварительное), который получает определения из метамодели и предоставляет единые операции:

- проверка системного контракта объекта;
- проверка типа значения свойства;
- проверка обязательности и кардинальности;
- проверка допустимого типа целевого объекта для ссылочного свойства;
- проверка существования цели и корректности разрешения ссылки;
- проверка ограничений допустимых значений;
- проверка контекстных/зависимых ограничений, если они определены и поддерживаются;
- формирование структурированных диагностик: объект, свойство, фактическое значение, нарушенное правило и возможный способ исправления.

`SchemaEngine` не должен зависеть от конкретного UI, от наличия Bases или от Fileclass. Интерфейсы вызывают его для предварительной проверки и перед записью; механизм проверки хранилища использует его для обнаружения некорректных данных после внешних изменений.

### 18.4. Собственная модалка редактирования свойств

Для редактирования свойств предусматривается модалка Second Brain, ориентированная на удобство Fileclass, но построенная на схемах нашей метамодели. Её предполагаемые возможности:

- показывать название и тип свойства, описание и признак обязательности;
- выбирать подходящий контрол по типу значения: текст, число, дата, логическое значение, одиночный/множественный выбор или ссылка на объект;
- для ссылочных свойств показывать только кандидатов, допустимых по схеме;
- отображать читаемые названия объектов, сохраняя разрешение целей по стабильному ID и каноническому пути;
- поддерживать фильтры, зависящие от других свойств текущего объекта, если они определены метамоделью и реализованы соответствующим механизмом запросов;
- показывать ошибки валидации рядом с соответствующим полем и не записывать значение, нарушающее жёсткие ограничения;
- различать блокирующие ошибки и предупреждения, например ссылку на отсутствующий объект или устаревшее значение после изменения схемы;
- выполнять запись через единый сервис изменения объектов, чтобы валидация, обновление `updated_at` (если это поле будет утверждено), индекса и журналирование не дублировались в каждом контроле.

Модалка является рекомендуемым основным интерфейсом для управляемого редактирования сложных свойств, но не единственным способом работы с данными. Стандартная панель Properties остаётся доступной.

### 18.5. Поведение стандартной панели Properties

Пользователь может редактировать frontmatter через встроенную панель Properties. Second Brain не должен предполагать, что все изменения проходят через собственную модалку.

Предварительная политика:

1. При обнаружении изменений файла плагин обновляет индекс объекта и запускает проверку затронутых свойств.
2. Некорректные значения не должны молча переписываться или автоматически удаляться.
3. Диагностики доступны пользователю через статус объекта, уведомление или команду проверки; точный UI диагностики предстоит выбрать.
4. Если значение нарушает ограничение, плагин сообщает об этом и предлагает исправление. Автоматическое исправление допустимо только в явно подтверждённой операции.
5. Проверка должна быть по возможности локальной: изменение одного свойства не должно без необходимости повторно валидировать всё хранилище. Полная проверка остаётся доступной отдельной командой.

Это означает, что собственная модалка может обеспечивать более богатые подсказки и фильтрацию до сохранения, а стандартная панель Properties — более свободное редактирование с последующей проверкой.

### 18.6. Интеграция с Bases

Bases рассматривается как существующий механизм Obsidian для запросов, фильтрации, сортировки и отображения наборов заметок. Его можно использовать там, где он действительно упрощает получение динамических списков кандидатов или представление данных.

Предлагается предусмотреть необязательный `BasesAdapter` (техническое имя предварительное), который изолирует взаимодействие с Bases от `SchemaEngine` и UI. Его задачи и ограничения:

- предоставлять динамические списки объектов, соответствующих фильтрам, если это поддерживается выбранной версией Obsidian/Bases;
- исследовать возможность контекстных фильтров, использующих свойства редактируемого объекта;
- не считать результат запроса доказательством корректности сохранённого значения;
- при недоступности Bases использовать внутренний индекс и простые фильтры Second Brain, если они достаточны для сценария;
- не генерировать и не синхронизировать отдельный `.base` для каждого свойства автоматически до подтверждения необходимости прототипом.

Точная граница использования Bases остаётся предметом технического прототипа. Наличие встроенного Bases само по себе не гарантирует, что его запросный движок имеет стабильный публичный API для всех сценариев интерактивного выбора. Если для конкретной функции потребуется DOM или внутренний API, такая интеграция должна быть изолирована и документирована.

### 18.7. Роль Fileclass

Fileclass изучается как референсный пример для:

- описания схем свойств и ограничений;
- формирования типизированного UI;
- получения списков кандидатов через Bases;
- контекстных и зависимых фильтров;
- разделения схемы, выбора значения и проверки данных.

Для MVP не вводится обязательная зависимость от Fileclass. Не следует поддерживать две независимые схемы — Second Brain и Fileclass — как два равноправных источника истины. Возможная будущая интеграция должна быть оформлена как отдельный адаптер и иметь явно определённое направление обмена данными.

### 18.8. Предлагаемый объём MVP

**Этап 1 — ядро схем и валидации:** загрузка определений из `.sb/`, `SchemaEngine`, структурированные диагностики и проверка значений независимо от UI.

**Этап 2 — модалка свойств:** типизированные контролы, выбор ссылочных объектов с фильтрацией по типу цели, предварительная валидация и единый сервис записи.

**Этап 3 — изменения через Properties:** обнаружение внешних изменений frontmatter, повторная проверка затронутых свойств, отображение ошибок без молчаливой перезаписи данных.

**Этап 4 — расширенные фильтры:** прототип `BasesAdapter` для динамических и зависимых списков. Включать в MVP только те сценарии, для которых подтверждён устойчивый технический путь. При необходимости обеспечить базовый внутренний фильтр как резервный вариант.

### 18.9. Критерии готовности

- Одно и то же правило валидации действует независимо от способа изменения свойства.
- Модалка предлагает типизированный контрол и отфильтрованные варианты в соответствии со схемой.
- Сохранение через собственный интерфейс проходит предварительную проверку и выполняется через единый сервис записи.
- Изменение через стандартную панель Properties обнаруживается и проверяется без молчаливого уничтожения значения.
- Некорректное значение приводит к диагностике, а не к неявному автоматическому исправлению.
- Отключение Bases не нарушает базовую валидацию и простой выбор объектов по внутреннему индексу.
- Отключение Fileclass не нарушает ни один основной сценарий Second Brain.
- Контекстные фильтры не считаются заменой повторной валидации сохранённого значения.

### 18.10. Статус решения

Зафиксировано как архитектурное направление черновика `v1.1-draft`: поддерживаются оба пути редактирования (собственная модалка и стандартная панель Properties); собственная модалка предоставляет более богатый типизированный ввод и фильтрацию; единый `SchemaEngine` отвечает за правила валидации; Bases остаётся необязательной интеграцией запросов/представлений; Fileclass — референс, но не обязательная зависимость.

Не утверждены окончательно: формат декларативных ограничений свойств, точный контракт `SchemaEngine`, UX диагностики внешних изменений, API-интеграция с Bases, поддержка зависимых фильтров, необходимость отдельной интеграции с Fileclass и конкретный набор контролов первой версии. Эти решения требуют прототипа.
