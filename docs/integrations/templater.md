# Интеграция: Templater

> [!important] Решение одной строкой
> **Отклонён как зависимость** (DL-190, 2026-10-23): тело заметок плагин строит сам.
> **Сосуществование совместимо**: пользователь вправе применять Templater к своим заметкам —
> наш плагин его не вызывает и от него не зависит. DL-004 («Templater — подтверждённая интеграция»)
> **частично пересмотрен**.

## Что это и зачем рассматривали

Templater — сторонний (community) плагин шаблонов для Obsidian: подставляет в заметку переменные
и результаты функций (`<% tp.date.now() %>`), умеет исполнять JavaScript (`<%* … %>`), может
автоматически применять шаблоны при создании файлов.

Рассматривался как способ **построения тела заметок объектов**: frontmatter пишет плагин,
а тело собирает пользовательский шаблон. Критерий задал пользователь (2026-10-23):
**«если привязывать шаблоны Templater как тела к нашим frontmatter — Templater нужен;
если строим тело своими методами — можно пропустить»**. Тело строим своими методами (см. ниже) —
значит, ветка «пропустить».

## Что он умеет (факты, не догадки)

- Версия / дата проверки: **проверено 2026-10-23** по официальной документации
  (silentvoid13.github.io/Templater, страница Settings) и CHANGELOG репозитория: релиз **2.21.0**
  от 2026-06-02, проект активно развивается. Репозиторий: <https://github.com/SilentVoid13/Templater>.
- Есть ли публичный API: **нет**. Стабильного документированного интерфейса для других плагинов
  не описано; доступ — только через внутренние объекты (`app.plugins.plugins["templater-obsidian"]…`),
  то есть недокументированный механизм. Нам он **запрещён рамками проекта**
  (`mvp-scope.md` §3.1: «патчи недокументированных внутренностей»).
- Что доступно (по документации, существенно для нас):
  - `Trigger Templater on new file creation` — Templater **слушает событие создания файла**
    и заменяет команды, найденные в содержимом нового файла;
  - Режимы сопоставления: None / **Folder templates** (по папкам, побеждает самая глубокая) /
    **File regex templates**; правило применяется только к файлам с тем же расширением, что и шаблон;
  - `Excluded folders` — папки, в которых триггер не срабатывает никогда;
  - Template Hotkeys (команды `Insert`/`Create`), startup-шаблоны, пользовательские скрипты
    (CommonJS), системные команды (опасно, по умолчанию выключены).
- Как тело строим мы (без Templater):
  - `media` — инвариант **И8**: тело содержит `![[{file}|{title}]]`; показ работает даже
    с выключенным плагином, постпроцессор лишь улучшает вывод (`embed-postprocessor`);
  - `chapter` — навигационный блок `sb-chapter-nav` через собственный `code_block_processor` (DL-129);
  - остальные типы — минимальный каркас и свободный текст; создание только командами
    (ADR-004, правила П1–П6).

## Варианты

### Вариант 1 — не использовать, тело строить самим (принят)
- Плюсы: ноль зависимостей; предсказуемый результат; соответствует принципу П7 раздела 12
  («поведение не зависит от сторонних плагинов») и правилу «мягкой зависимости» шаблона интеграции;
  инварианты тела (И8) под нашим контролем.
- Минусы: пользователь не может настроить тело по типам без нас.
- Риски: ожидание шаблонизации → фиксируем в документации: сосуществование совместимо,
  собственный механизм шаблонов тела — кандидат этапа 2.

### Вариант 2 — глубокая интеграция (команда плагина вызывает шаблон Templater)
- Плюсы: мощные пользовательские шаблоны без собственного движка.
- Минусы: только через недокументированный доступ; гонка двух обработчиков события `create`
  (нашего и Templater) — порядок не гарантирован; нарушение рамок проекта.
- Риски: обновление или отсутствие Templater ломает создание объектов. **Отклонён.**

### Вариант 3 — сосуществование без интеграции (принят как режим)
- Плюсы: пользователь сохраняет привычки; у нас ноль зависимостей.
- Минусы: нужно документировать единственную коллизию (триггер на создание файла).
- Риски: см. таблицу ниже — закрыты инструкцией и валидацией.

## Оценка

| Критерий | Оценка | Комментарий |
|---|---|---|
| Полезность для задач пользователя | Низкая (для плагина) | Тело либо диктуется инвариантами (И8, навигация), либо это свободный текст |
| Совместимость с нашей метамоделью | Средняя | О нашей схеме не знает; может писать любой frontmatter — ловит валидация |
| Стабильность API | Низкая (для нас) | Публичного API нет; только недокументированный доступ |
| Зависимость от чужого плагина | Была бы высокой | У пользователя может быть не установлен — создание объектов не должно от этого зависеть |
| Сложность реализации для новичка | Высокая | Гонки событий, чужие внутренности |

## Риск и способ защиты метамодели

| Риск | Вероятность | Последствие | Мера защиты |
|---|---|---|---|
| `Trigger Templater on new file creation` + Folder templates сработает на созданный нами файл | Низкая (нужно правило пользователя на наши папки) | Шаблон перезапишет тело/frontmatter | Мы **не пишем токены `<% %>`** в файлы — в режиме None Templater нечего заменять; инструкция: добавить папки объектов в `Excluded folders`; валидация frontmatter (уровни 2, 4, 6) ловит поломку |
| Шаблон пользователя удалил встраивание в теле `media` | Низкая | Обложка не показывается | Инвариант И8 + правила группы J: диагностика указывает на отсутствие встраивания |
| Шаблон пишет русские ключи или некорректные значения | Низкая | `error` валидации | ADR-003 + правила групп B/C; система ничего не исправляет молча |
| Templater не установлен | — | Ничего | Зависимости нет: плагин его не вызывает |

## Решение

**Отказать как зависимости — реализуем сами.** Тело заметки плагин строит собственными методами
(инвариант И8 у `media`, блок `sb-chapter-nav` у глав, минимальный каркас у остальных типов,
создание командами по ADR-004). По критерию пользователя от 2026-10-23 это ветка «Templater можно
пропустить» (DL-190). Сосуществование совместимо и ничем не ограничено; DL-004 частично пересмотрен.
**Кандидат этапа 2:** собственный лёгкий механизм шаблонов тела (простая подстановка токенов),
если потребность появится. Подтверждено пользователем: 2026-10-23.
