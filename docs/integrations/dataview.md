# Интеграция: Dataview

> [!important] Решение одной строкой
> **Отклонён** (DL-191, решение пользователя «А»; карточка — DL-195): как зависимость и как механизм
> представлений. Свои запросы пользователя Dataview к нашим данным **не запрещены, но не
> поддерживаются**. Модуль `dataview-integration` остаётся в «не реализуем» (`09-modules.md` §6).

## Что это и зачем рассматривали

Dataview — сторонний плагин, который превращает хранилище в запросную базу: читает YAML-frontmatter
и собственные «инлайновые поля» (`Ключ:: Значение` прямо в тексте), рисует таблицы, списки и задачи
по запросам на своём языке (DQL) или на JavaScript (DataviewJS).

Рассматривался как альтернативный механизм представлений (в черновике v1.1 §18.5 — наряду
с Fileclass и Bases) и как возможный способ «быстро показать данные, пока нет своего UI».

## Что он умеет (факты, не догадки)

- Версия / дата проверки: **проверено 2026-10-23** (obsidianstats.com/plugins/dataview, README
  репозитория). Последняя версия **0.5.70 (Beta)** — выпущена **около двух лет назад**;
  9 404 звезды, ~5,18 млн загрузок, **639 открытых issues**. Развитие фактически остановилось,
  проект в режиме редких maintenance-обновлений.
- Есть ли публичный API: **да** — JavaScript API для плагинов (`app.plugins.plugins.dataview.api`).
  Мы его **не используем**: решение принято, адаптер не пишем.
- Что именно доступно:
  - Данные: YAML-frontmatter + **инлайновые поля** `Ключ:: Значение` — собственный синтаксис
    в теле заметки. Мы инлайновые поля **не пишем и не читаем** (ADR-002: только frontmatter
    через API Obsidian);
  - Четыре режима запросов: DQL (пайплайновый, «похожий на SQL»), инлайновые DQL-выражения,
    DataviewJS, инлайновый JS;
  - Безопасность (цитата README): обычные DQL-запросы песочницуются, а **JavaScript-запросы
    выполняются с правами полноценного плагина** — могут переписывать, создавать и удалять файлы
    и делать сетевые вызовы.
- Ключевое ограничение для нас: **реифицированные связи невидимы**. Экземпляры связей живут
  в `.sb/relations/relations.jsonl` (ADR-010); папки с точкой Obsidian не индексирует —
  Dataview их не видит. Любой его запрос о связях дал бы неполную картину. `direct`-ссылки
  во frontmatter он видит.
- Рыночное подтверждение курса: новый **Fileclass** (2026, преемник Metadata Menu от того же
  автора) **отказался от зависимости Dataview в пользу базового Bases** — та же ставка,
  что и наша (`08-views.md`, механизм `base`).
- Источники: <https://github.com/blacksmithgu/obsidian-dataview>,
  <https://blacksmithgu.github.io/obsidian-dataview/>, <https://www.obsidianstats.com/plugins/dataview>.

## Варианты

### Вариант 1 — использовать как механизм представлений
- Плюсы: готовые таблицы/списки без своего UI; огромное сообщество и примеры.
- Минусы: сторонняя зависимость в состоянии стагнации (0.5.70 beta ~2 года, 639 открытых issues);
  второй язык запросов = второй источник правды о представлениях (против философии `08-views`);
  DataviewJS — произвольный JS с правами плагина (дыра в предсказуемости); связи из `.sb/` невидимы.
- Риски: плагин может остаться без поддержки; поломка после обновлений Obsidian. **Отклонён.**

### Вариант 2 — реализовать самим (принят ранее)
- Уже сделано: `08-views.md` — 12 представлений на Bases/`plugin_view`/`code_block`
  с путями деградации; `mechanism` закрыт без `dataview`/`dataviewjs`.

### Вариант 3 — отказаться (принят)
- Плюсы: ноль зависимостей; предсказуемость; честность к пользователю (оговорка ниже).
- Минусы: пользователь, привыкший к Dataview, не получит «своих» запросов из коробки.

## Оценка

| Критерий | Оценка | Комментарий |
|---|---|---|
| Полезность для задач пользователя | Средняя | Запросы закрыты Bases и нашими представлениями; уникальная польза Dataview для нас мала |
| Совместимость с нашей метамоделью | Низкая | Не видит `.sb/` (реифицированные связи); инлайновые поля — чужой формат данных в теле заметок |
| Стабильность API | Низкая | Развитие остановилось (~2 года без релиза), 639 открытых issues |
| Зависимость от чужого плагина | Высокая | Механизм представлений нельзя ставить на заброшенную зависимость |
| Сложность реализации для новичка | Высокая | Адаптер к чужому индексу и языку запросов |

## Риск и способ защиты метамодели

| Риск | Вероятность | Последствие | Мера защиты |
|---|---|---|---|
| Пользователь ставит Dataview и пишет запросы к нашим данным | Средняя | Неполная картина (без реифицированных связей), путаница | Честная оговорка в документации и README: запросы не запрещены, но не поддерживаются; связи из `.sb/` Dataview не видит |
| DataviewJS-запрос из чужого шаблона меняет файлы | Низкая | Повреждённые данные | Не наша поверхность: предупреждение в документации; валидация (уровни 2/4/6) ловит последствия; система ничего не переписывает молча |
| Ожидание «плагин умеет то же, что Dataview» | Средняя | Претензии к функциональности | Правило из `mvp-scope` §4: «фича нужна, чтобы было не хуже, чем у Dataview» — проверяем тремя вопросами; обычно это этап 2 |
| Инлайновые поля `Ключ:: Значение` появятся в заметках пользователя | Низкая | Данные вне схемы, мы их не читаем | Документируем: единственное место данных — frontmatter (ADR-002); инлайновые поля игнорируются валидацией |

## Решение

**Отказаться.** Основания: заброшенность (0.5.70 beta ~2 года, 639 открытых issues), права плагина
у JS-запросов, второй язык запросов как второй источник правды, невидимость реифицированных связей
из `.sb/`. Представления закрыты без него (`08-views.md`, принято DL-171). Решение пользователя —
ответ «А» на вопрос 8d-3 (DL-191); карточка создана в партии 2 шага 8d (DL-195), 2026-10-23.
Оговорка зафиксирована: **свои запросы пользователя не запрещены, но не поддерживаются**;
пересмотр возможен, только если Dataview обретёт активную поддержку и публичный стабильный API
индекса — признаков этого нет.
