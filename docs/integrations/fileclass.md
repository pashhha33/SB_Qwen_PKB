# Интеграция: Fileclass

> [!important] Решение одной строкой
> **Референс, не зависимость** (DL-018, C-11; карточка — DL-196). Как зависимость — отклонён;
> как источник проверенных архитектурных решений — чрезвычайно полезен: новый Fileclass (2026)
> независимо пришёл к той же схеме, что и мы.

## Что это и зачем рассматривали

Исходные черновики (v1.0 §9, v1.1 §14, §18) ссылались на плагин **Fileclass** как на «референсную
реализацию» и возможную точку интеграции: схема заметки + формы ввода полей.

> [!warning] Важный факт 2026: под именем Fileclass теперь другой плагин
> - **Старый** Fileclass (mmalecot/obsidian-file-class) — тот, на который ссылались черновики:
>   на дату проверки **2026-10-23 репозиторий недоступен (404)**. Живым проектом не обнаружен.
> - **Текущий** плагин с id `fileclass` в реестре сообщества — **новый плагин mdelobelle**
>   (автора Metadata Menu), **преемник Metadata Menu**, построенный на базовом **Bases**:
>   <https://github.com/mdelobelle/fileclass>.
> Выходит, ориентир из черновиков буквально исчез — прямое подтверждение правильного выбора
> «референс, не зависимость»: референсы умирают и меняют владельцев, метамодель остаётся.

## Что он умеет (факты, не догадки)

- Версия / дата проверки: **0.2.15** (~2 месяца до проверки); **проверено 2026-10-23**
  (obsidianstats.com/plugins/fileclass, документация mdelobelle.github.io/fileclass).
- Требования: Obsidian **1.12.7+** и включённый базовый **Bases**; без Bases схема и типизированный
  ввод работают, а зависящие от запросов части (кандидаты File/Media, генерируемые виды)
  **мягко деградируют вместо ошибок**.
- Есть ли публичный API: **да** — API на экземпляре плагина + отдельные CLI/TUI (репозиторий
  fileclass-cli). Мы их не используем (не зависимость).
- Что именно доступно (по документации):
  - **fileClasses** — схемы-заметки с наследованием (`extends`/`excludes`); привязка класса
    к заметкам по alias, тегу, пути, группе закладок, виду Base или глобальному умолчанию;
  - **типизированные поля**: Input, Number, Boolean, Select, Cycle, Multi, Date/DateTime/Time,
    File/MultiFile, **Media/MultiMedia**, Object/ObjectList, JSON/YAML, Canvas — с управляемым
    вводом (модалка, **нативный редактор Properties**, контекстные меню, индикаторы);
  - **качество данных**: обязательные поля и по-нотная валидация, видимая в табличном виде и CLI/API;
  - **только frontmatter**: чтение через metadata cache, запись через `processFrontMatter`
    (публичный API); текст заметок не парсится и не редактируется;
  - **виды**: генерация `.base` для fileClass с **односторонней синхронизацией**; редактируемый
    вид `fileclass-table` (Bases) с типизированной правкой ячеек;
  - качество кода: 541 модульный тест, TypeScript strict; формат fileClass-определений
    совместим с Metadata Menu.

## Что мы берём как референс (и что уже взяли)

| Их решение | Наше соответствие |
|---|---|
| Схема — заметка в выделенной папке (`Class files folder`) | ADR-002: определения метамодели — Markdown в `Metamodel/` |
| Только frontmatter, запись через `processFrontMatter` | ADR-002: чтение/запись только через API Obsidian |
| Формы управляемого ввода (модалка, Properties, меню) | Наша модалка свойств и панель объекта (В7); `MetadataEditor.register` — после прототипа (ADR-003) |
| Обязательные поля + валидация на ноту | Единый реестр правил валидации (группы A–N), 6 уровней контроля (`rules.md`, `severity-policy.md`) |
| Генерация `.base` с односторонней синхронизацией | `base-generator`: генерация в `Views/`, маркер `# sb-generated: v1`, перегенерация только с вопросом (DL-169/170) |
| Мягкая деградация без Bases | Пути деградации В1–В12, `bases-adapter` |
| Медиа-поля (Media/MultiMedia) | ADR-008: `media_reference` (осознанное отличие: множественность — только `cardinality`) |

**Чего у них нет и что есть у нас:** реифицированные связи с ролями и периодами (ADR-009/010),
самоопределяющаяся метамодель (тип — тоже объект), русские подписи при английских ключах как слой
(ADR-003), инварианты идентификации (ULID, имя файла, И1–И8).

## Варианты

### Вариант 1 — использовать как зависимость
- Плюсы: готовые формы и валидация без своего UI.
- Минусы: их схема (fileClass-заметки) конфликтует с нашей метамоделью — два источника правды
  о типах; привязка классов по тегам/путям против нашего явного `type`; молодой плагин (0.2.x);
  нет реифицированных связей. **Отклонён.**

### Вариант 2 — реализовать самим (принят)
- Всё перечисленное в таблице выше уже заложено в наших решениях; Fileclass подтверждает выбор.

### Вариант 3 — отказаться без изучения
- Минусы: потерять сильный референс. **Отклонён** — референс полезен и бесплатен.

## Оценка

| Критерий | Оценка | Комментарий |
|---|---|---|
| Полезность для задач пользователя | Как зависимость — отрицательная | Конфликт двух схем в одном хранилище |
| Совместимость с нашей метамоделью | Низкая (как зависимость) | fileClass-схема — конкурент нашей `Metamodel/` |
| Стабильность API | Средняя | Молодой плагин (0.2.x), но качественный (541 тест); старый Fileclass умер — урок |
| Зависимость от чужого плагина | Высокая (была бы) | Требует Bases 1.12.7+; формат классов — чужой |
| Сложность реализации для новичка | — | Не реализуем: только читаем опыт |

## Риск и способ защиты метамодели

| Риск | Вероятность | Последствие | Мера защиты |
|---|---|---|---|
| Пользователь включает Fileclass параллельно с нашим плагином | Низкая | Оба пишут frontmatter; их валидация ругается на наши поля и наоборот | Документируем рекомендацию: не смешивать на одних папках/типах; наша валидация помечает поля вне схемы; их правки не ломают наши `id`/`type` (И1–И3) |
| Соблазн «взять готовое вместо своего» | Средняя | Отказ от самоопределяемости метамодели | Решение зафиксировано: Fileclass не умеет реифицированные связи и метамодель-как-данные; карточка документирует почему |
| Ссылки черновиков на «старый» Fileclass введут в заблуждение | Уже случилось | Ориентир мёртв | Этот факт зафиксирован здесь; глоссарий: запись «Fileclass» заменена на актуальную (DL-196) |

## Решение

**Отказаться как от зависимости; использовать как референс.** Подтверждено ранее: DL-018
(QuickAdd и Fileclass вне MVP, по каждой — карточка), v1.1 §18.1/§18.7 («референсная реализация,
не обязательная зависимость»), C-11. Новое в карточке: зафиксирована смена плагина под именем
Fileclass (2026) и сверены их решения с нашими — расхождений по архитектуре нет, есть подтверждение
курса (Bases, frontmatter-only, генерация `.base`, деградация). Карточка создана в партии 2
шага 8d (DL-196), 2026-10-23.
