# Контрольная точка

> [!important] Как начать новую сессию с этим проектом
> 1. Откройте репозиторий: `https://github.com/pashhha33/SB_Qwen_PKB` (адрес указан в поле `repository` в frontmatter этого файла).
> 2. Скопируйте **весь этот файл** в первое сообщение новой сессии.
> 3. Добавьте одну строку: «Продолжаем проект Second Brain. Прочитай контрольную точку и документы по ссылкам, подтверди понимание и задай следующий шаг».
> 4. Ассистент обязан: подтвердить фазу и следующий шаг, перечислить принятые решения, назвать открытые вопросы — и только потом продолжать.
>
> **Что критично не потерять:** порядок шагов 0→9, правило «сверху вниз», четыре принятых ADR,
> состав ядра из 11 типов, требование создавать элементы метамодели командами.

## 1. Роль ассистента и режим работы (обязательно к соблюдению)

- Ведущий архитектор метамоделей, наставник, тимлид и технический соавтор. Не пассивный исполнитель.
- Пользователь — **новичок** в TypeScript, Obsidian API и разработке плагинов. Поверхностно знаком
  с онтологиями, метамоделями, графами знаний, JSON Schema. **Не знает RDF/OWL.**
- Любой технический термин при первом появлении: объяснить простыми словами + бытовая аналогия +
  зачем в проекте + пометка «термин» + занести в глоссарий.
- Инициатива обязательна: сначала 2–3 варианта с плюсами и минусами, потом рекомендация с обоснованием,
  потом ждать решения. **Ключевые решения за пользователя не принимать.**
- Не более 2–4 вопросов за сообщение. После вопросов — остановиться и ждать ответа.
- Артефакт создаётся **сразу** после утверждения решения, не «на потом».
- В конце каждого сообщения — блок «Компас» (где мы, куда идём, что дальше) и блок «Новые термины».
- Стиль: подробно, практично, с примерами и обоснованиями. Явно помечать: «предложение», «рекомендация»,
  «решение», «вопрос», «риск», «изменение, требующее подтверждения», «предположение», «термин».

## 3. Цель

1. Доработать метамодель личной базы знаний **Second Brain**: классификация, сложные объекты,
   устранение противоречий и дублей.
2. Зафиксировать её в документации и артефактах, довести до состояния «готова к реализации».
3. Реализовать MVP плагина Obsidian со стабильным ядром.

**Критерий «метамодель утверждена»** — 32 пункта в [[../roadmap/readiness-checklist|чек-листе]]
(блоки A–F) + явное подтверждение пользователя + версия `1.0.0`.

**Критерий стабильного ядра плагина:** устанавливается в пустой vault, создаёт заметку по типу из
метамодели, валидирует frontmatter, показывает связи хотя бы в одном сценарии, есть тесты на ядро,
есть README и руководство пользователя.

## 4. Что за модель (суть в трёх абзацах)

**Second Brain** — самоопределяющаяся объектная модель внутри Obsidian. Не «список типов заметок»,
а система, где тип объекта, свойство, тип свойства, тип отношения, отношение, таксономия, фасет,
категория, представление и автоматизация — **тоже объекты** со своими `id` и `type`.

Три слоя: **(1) Фундамент** — закрытый набор, заданный кодом: 8 типов значений + системные атрибуты;
**(2) Метауровень** — описания: типы объектов, свойства, типы отношений, таксономии, фасеты, категории,
представления, автоматизации; **(3) Данные пользователя** — экземпляры объектов и экземпляры отношений.

Следствие: нужен «порядок запуска» (bootstrapping) — слой 1 обязан быть закрытым и заданным кодом;
один универсальный механизм чтения вместо девяти частных; метамодель можно менять без перекомпиляции
плагина; объём работы больше, чем у обычной схемы данных.

## 6. Принятые решения

### 6.1. Рамки из промпта (DL-001…DL-007)

См. раздел 2 выше.

### 6.2. ADR-001 — идентификация и имя файла

| Параметр | Норма |
|---|---|
| `id` | **голый ULID**, 26 символов, Crockford Base32, верхний регистр. Пример: `01J8Z6M4K2Q7V9X3N5B0C1D2EF` |
| Имя файла | `{TYPE_PREFIX}-{ULID}.md`. Пример: `PERSON-01J8Z6M4K2Q7V9X3N5B0C1D2EF.md` |
| Каноническая ссылка | `[[{TYPE_PREFIX}-{ULID}.md\|{title}]]` |
| `TYPE_PREFIX` | технический код типа из реестра, `UPPER_SNAKE_CASE`, уникален как целая строка, 3–12 символов, только `A–Z`, `0–9`, дефис |
| Запрещено в именах файлов | квадратные скобки, `# ^ [ ] \|`, ведущие и завершающие пробелы |
| Переиспользование `id` | запрещено, в том числе после архивирования и удаления |

**Читаемость — три уровня по возрастанию стоимости:**
1. **Данные (обязательно в MVP):** инвариант `aliases[0] == title`. Obsidian нативно учитывает `aliases`
   в автодополнении ссылок и быстром переключателе.
2. **Чужой плагин:** Front Matter Title как **рекомендуемая необязательная** интеграция.
3. **Свой слой:** собственные адаптеры — только где уровень 2 не покрывает и область критична. **Вне MVP.**

**Раздел 17 черновика v1.1 вынесен за границы MVP.**

Обязательные меры: M1 отображаемое название никогда не участвует в разрешении ссылок (только `id` и
канонический путь); M2 инвариант `aliases[0] == title`; M3 каждый адаптер изолирован, сбой одного не
ломает остальные; M4 резервное поведение — показывать имя файла, а не пустоту; M5 при расхождении
`id` и ULID в имени файла чинить **имя файла по `id`**; M6 честная документация о границах поддержки;
M7 регрессионная проверка отображения после обновлений Obsidian.

Данные о стабильности Front Matter Title: [[../integrations/research-front-matter-title-stability]]
(10 открытых проблем из 179; два инцидента «белого экрана»; патчит ~10 недокументированных внутренностей
Obsidian; с июня 2026 — режим мягкого отказа).

### 6.3. ADR-002 — источник истины

**Определения метамодели — Markdown-заметки в хранилище. JSON в `.sb/` отклонён как место хранения определений.**

| Что | Где | Формат |
|---|---|---|
| Типы объектов, свойства, типы свойств, типы отношений, отношения, таксономии, фасеты, категории, представления, автоматизации | `Metamodel/**` (обычные папки vault) | Markdown + YAML frontmatter |
| Экземпляры объектов | обычные папки vault | Markdown + YAML frontmatter |
| Кэш, счётчики, журнал, резервные копии, настройки, черновики миграций | `.sb/` | JSON |

Критерий: если у сущности есть `id`, `type`, `title` и на неё можно сослаться — это объект метамодели
(Markdown). Если это технические данные плагина — `.sb/`.

Кэш в `.sb/cache/` — производные данные, обязан полностью пересоздаваться из заметок.
Чтение frontmatter — только через API Obsidian, не самописным разбором YAML.
Некорректное определение не применяется; плагин работает с последней корректной версией и показывает ошибку.
Восьмипунктовая последовательность применения изменений из §15.4 v1.1 сохраняется.

### 6.4. ADR-003 — язык ключей и слой подписей

| Слой | Поле | Язык | Стабильность |
|---|---|---|---|
| Технический | `key` | английский `snake_case` | стабилен; меняется только через ломающее изменение |
| Отображаемый | `label` | русский | свободный; меняется в любой момент |

**Соглашение об именах:** системные атрибуты — `snake_case`, закрытый список (`id`, `type`, `title`,
`aliases`, `created_at`, `updated_at`); ключи свойств — `snake_case`, латиница; имена типов —
`snake_case`, единственное число; `TYPE_PREFIX` — `UPPER_SNAKE_CASE`; значения перечислений —
`snake_case`, латиница; `label` — русский, с заглавной буквы.

**Подписи гарантированно показываются в:** нашей модалке свойств, наших представлениях, сообщениях
валидации, командах и меню. **Как получится:** стандартная панель свойств Obsidian (только после
прототипа `MetadataEditor.register`), таблицы Bases. **Не показываются:** режим источника (сырой YAML),
поиск по хранилищу.

CSS-подмена и DOM-подмена подписей **отклонены** как хрупкие.
Режимы `view` (подписи) и `source` (ключи) — настройка и команда `toggle-label-mode`.
Полная таблица соответствия 40 старых русских имён новым английским ключам — в ADR-003.

### 6.5. ADR-004 — объём первого прохода и командное создание

**Две ступени:** (1) реестр всех ~40 типов с разметкой статуса — дёшево, сохраняет полноту картины;
(2) детальное описание только типов ядра.

**Все элементы метамодели создаются и изменяются командами плагина**, не ручным редактированием файлов
(правила П1–П6). Это компенсирующая мера для ADR-002: раз риск Markdown-хранилища — сломанный вручную
YAML, основной способ правки не должен быть ручным.

Команды MVP — **18**, актуальный реестр — `roadmap/mvp-scope.md` §2.3 (DL-162, DL-188);
из команд классификации в реестре `create-taxonomy` и `assign-category` (этап B).
Вне MVP: `create-view`, `create-automation` (типы `view`/`automation` — этап 2).
`create-facet` / `create-category` описаны в ADR-004, но в реестр 18 не входят —
**DL-218 принято** (ответ «А»): покрываются универсальной `create-object`, обёртки — этап 2.

Добавление нового предметного свойства **не требует** изменения кода и перекомпиляции плагина.
Наличие определения свойства не означает автоматической записи значения во все существующие объекты.

### 6.6. ADR-005 — модель классификации (изменён ADR-006, предлагается правка ADR-007)

**Три уровня:** `taxonomy → facet → category → назначение объекту`.

- `taxonomy` объединяет фасеты и задаёт область применения (`allowed_object_types`).
- `facet` — отдельное измерение классификации; **настройки иерархии и назначения задаются на уровне фасета**:
  `hierarchy_mode`, `assignment_cardinality`, `root_requirement`. Фасет наследует значения по умолчанию
  от таксономии и может их переопределить.
- `category` — значение внутри ровно одного фасета; иерархия через `parent`, предки вычисляются,
  корень не имеет родителя. Перенос категории в другой фасет — контролируемая операция.

**Обязательность `categories` задаёт фасет** через `assignment_cardinality`, а не универсальное ядро.
По умолчанию категории необязательны.

**`tags`** — системный атрибут, **свободные метки вне метамодели**: без справочника, без валидации.
Правило разделения: `tags` — неформальные и спонтанные; `categories` — управляемые, из справочника
фасета, проверяются. Прижившаяся метка повышается до категории соответствующего фасета.

**Критерий «подтип или категория» — два теста по порядку:**

> **Тест 1.** Нужны ли этому виду объектов **собственные свойства**, которых нет у родителя?
> Да → подтип. Нет → тест 2.
>
> **Тест 2.** Является ли это **открытым множеством значений**, которое пользователь пополняет
> без изменения метамодели? Да → категория. Нет → подтип.

Применение теста: Веб-новела → категория; Глава → подтип (поля `номер`, отношение «часть — целое»);
Эпизод → подтип; Персонаж → подтип; Фантастика → категория; Стихотворение → спорный случай, решение
за пользователем.

### 6.7. ADR-006 — системные атрибуты, типы значений, тип `media`

**Типов значений семь, набор закрыт:**

`text`, `number`, `date`, `datetime`, `boolean`, `object_reference`, `media_reference`.

**Убраны** `Список` и `Список ссылок`: множественность задаётся **только** полем `cardinality`
(`1`, `0..1`, `0..N`, `1..N`).

**Ответ на вопрос «а если придётся использовать словарь?»** — новый механизм не нужен:

| Способ | Когда |
|---|---|
| Перечисление `allowed_values` | Значений мало, они стабильны, меняются только вместе с метамоделью |
| Ссылка на категорию (`target_types: [category]` + `target_facet`) | Значений много, список пополняет пользователь, нужна иерархия или русские подписи |
| Ссылка на объект другого типа | Значение — самостоятельный объект со своими полями |

**Системные атрибуты — закрытый набор из 8 полей**, задан кодом, нельзя отключить:
`id`, `type`, `title`, `aliases`, `created_at`, `updated_at`, `categories`, `tags`.

**Инварианты:** И1 `id` — валидный ULID, уникален, не переиспользуется; И2 `id` совпадает с ULID в имени
файла, при расхождении имя файла чинится по `id`; И3 `type` указывает на существующий неабстрактный тип;
И4 `aliases[0] == title`; И5 `created_at` неизменяем, `updated_at` ≥ `created_at`; И6 ключи системных
атрибутов не переопределяются предметными свойствами.

**Даты:** хранение `YYYY-MM-DD` и `YYYY-MM-DDTHH:mm`, **локальное время без смещения**, точность до минут.
Отображение — настройка плагина (формат даты, формат времени, относительные даты, порог), на хранение
не влияет. **Известное ограничение G-04-1:** при создании заметок в разных часовых поясах хронологический
порядок нарушается.

**Тип `media`** (префикс `MEDIA`) заменяет `image_wrapper`. Поля: `file` (обязательно), `media_kind`
(enum: `image`, `audio`, `video`, `document`, `other`), `role` (enum: `cover`, `banner`, `logo`,
`portrait`, `avatar`, `preview`, `background`, `other`), `description`.
- В **MVP**: сам тип + миниатюры в **нашей** модалке через публичный API `app.vault.getResourcePath()`.
- **Отложено на этап 2**: механизм контекстного разрешения обёрток (v1.1 §10.1–10.5).
- **Отложено**: миниатюры в стандартном автодополнении ссылок Obsidian — требует патча `EditorSuggest`,
  то есть недокументированных механизмов.
- Ориентиры пользователя — Fileclass и Metadata Menu — показывают миниатюры в **собственных** формах,
  что подтверждает выбранный путь. Карточки этих интеграций создаются на шаге 8 как референсы, не зависимости.

### 6.8. Ядро: 15 типов (было 14; `chapter` добавлен 2026-10-22, DL-124)

### 6.10. ADR-007 — фасет как самостоятельный объект (**принят**)

Пользователь усомнился в обязательности таксономии как промежуточного звена. Принят **вариант B**:

- фасет — самостоятельный объект метамодели, поле `taxonomy` у него **необязательно** (`0..1`);
- у фасета появилось поле `allowed_object_types`;
- правило наследования: значение фасета → иначе значение таксономии → иначе значение по умолчанию;
- ограничение согласованности: `allowed_object_types` фасета должно быть подмножеством значения таксономии,
  иначе `warning`;
- **категория по-прежнему принадлежит только фасету** — второй путь через таксономию запрещён (правило П8),
  потому что лишает назначения проверяемого адресата правил и возвращает противоречие C-04;
- правило П6 ADR-005 **отменено**: `create-taxonomy` больше не создаёт фасет автоматически, а группирует
  существующие; `create-facet` допускает ответ «без таксономии».

### 6.11. ADR-008 — тип свойства `media_reference`

Пользователь уточнил: речь шла о **типе свойства**, а не о типе объекта. Различие зафиксировано:

| | Тип **объекта** `media` | Тип **значения** `media_reference` |
|---|---|---|
| Что это | Запись в базе, представляющая файл и его семантику | Объявление того, какого рода данные в поле и каким контролом вводятся |
| Где живёт | Заметка `MEDIA-{ULID}.md` | Определение свойства |

Ориентир проверен по документации: у **Metadata Menu** есть типы полей `Media` и `MultiMedia`
с настройками «папки с медиа», «размер встраивания», «показывать как список или карточки (галерея)».

Норма:

- **цель ссылки настраивается** полем `media_target`: `object` (обёртки `media`), `file` (файлы вложений),
  `both` — покрывает требование «фильтрует обёртки изображений и сами изображения»;
- **отдельного типа `multi_media_reference` нет**: множественность задаёт `cardinality`
  (осознанное отличие от Metadata Menu, согласованное с отменой типа «Список»);
- **семь настроек**: `media_target`, `media_kinds`, `media_folders`, `media_extensions`, `media_display`
  (`gallery` / `list`), `media_thumbnail_size` (`small` / `medium` / `large`), `media_roles`;
- **миниатюры** через публичный API `app.vault.getResourcePath()`, работают в **нашей** модалке;
  для `audio` / `video` / `document` — значок вида медиа;
- в стандартном автодополнении Obsidian миниатюр **не будет**: это требует патча `EditorSuggest`.

### 6.15. Привязка связи: принято (DL-090)

**Связь привязана к свойству, если у объекта `relation` заполнено поле `origin_property`.**
При пустом значении связь является **свободно стоящей** — как в спецификации v1.0 §9.

| Случай | `origin_property` | Где показывается |
|---|---|---|
| Связь создана из объявления свойства с `link_mode: reified` | заполнено | В контроле этого свойства и нигде больше |
| Связь создана сама по себе | пусто | В общем блоке связей объекта |

Следствие: **`link_mode` объявляется на свойстве, а не на типе отношения** — один и тот же тип отношения
может в одном месте требовать периода (`reified`), а в другом нет (`direct`).

Решает конфликт: два свойства одного типа, использующие один тип отношения, больше не видят связи
друг друга.

Правила валидации: `relation.origin_property.exists`, `.type_match`, `.reified`,
`relation.no_duplicate_link`, `relation.free_standing.visible`.

### 6.16. Каскадное поведение: принято (DL-091)

| Ситуация | Поведение |
|---|---|
| Удаление объекта, на который указывают связи | Связи **удаляются** |
| Удаление определения свойства | Плагин **предупреждает**, показывает число затронутых связей и предлагает: архивировать или очистить `origin_property` (связь станет свободно стоящей и не потеряется) |
| Удаление определения типа отношения | **Запрещено**, пока есть связи |

### 6.17. Обратная сторона связи: принято (DL-092)

Обратная сторона **не хранится**, а вычисляется. В форме объекта показывается блок
«Связан с этим объектом» — **только для чтения**. Чтобы изменить связь, пользователь идёт к исходному
объекту. Один источник истины сохраняется.

### 6.19. ADR-011 — перечисления, даты, интервалы, шаблон вывода, `lifecycle`

**Значения перечислений:** английский `snake_case` в данных + русская подпись отдельно. Проверка
`^[a-z][a-z0-9_]*$`. Закрытые перечисления — в `05-enumerations.md` (13 закрытых, 2 открытых до шага 8);
открытые справочники — категории фасетов.

**Частичные даты:** неизвестный компонент обозначается `00` — `1928-00-00` (только год),
`1928-05-00` (год и месяц). Правила П1–П6: неизвестная часть не может идти после известной;
при сравнении неизвестный компонент считается меньшим; при проверке вхождения в диапазон частичная дата
входит, если входит хотя бы один день её множества; показывается по своему шаблону без нулей;
формат **не** ISO 8601 — перед вычислениями нормализуется в диапазон.

**Интервалы:** `ends_on: null` = «по настоящее время» (норма, уровень `info`); `starts_on` не позже
`ends_on`; длительность вычисляется, не хранится; пересечение интервалов по умолчанию разрешено,
запрет включается полем `forbid_overlap: true` (**предложение, DL-111**).

**Редактируемый шаблон вывода** (предложение пользователя принято): 7 настроек (`date_template`,
`datetime_template`, `time_template`, `partial_year_template`, `partial_month_template`,
`use_relative_dates`, `relative_threshold_days`), **17 токенов** в квадратных скобках
(`[YYYY]`, `[MMMM]`, `[DD]`, `[Do]`, `[HH]`, `[mm]`, `[ddd]`, `[N]` и др.), **5 пресетов**
(русская дата по умолчанию, ISO, словесная, короткая, американская), отдельные шаблоны относительных дат.
Неизвестный токен показывается как есть и даёт `warning`. Шаблон влияет **только на отображение**.

**`lifecycle` получил поведение:** `experimental` → `info`; `standard` → обычно (по умолчанию);
`deprecated` → `warning`, команды создания не предлагают, обязательно поле `superseded_by`;
`archived` → скрыто из форм, значения сохраняются.

**Шесть уровней контроля целостности** (из `01` §19, получили определения): 1 предварительная
(при вводе, до записи), 2 техническая (формат и идентичность), 3 структурная (ссылки, кардинальность,
циклы), 4 семантическая (обязательность, перечисления, `lifecycle`), 5 проверка представлений,
6 постпроверка (после записи). Уровни 1 и 6 отключить нельзя; 2–4 локально при изменении и полностью
по команде `validate-vault`; 5 лениво.

- Инвариант **И4 не меняется**: `aliases[0] == title`, собранные значения добавляются **в конец**.

### 6.22. ADR-010 — хранение связей (принят)

Экземпляры связей — в **JSON Lines**: `.sb/relations/relations.jsonl`, одна строка на связь.
Obsidian папки с точкой не индексирует → граф, поиск и проводник остаются чистыми.

- `direct`-связи при этом остаются во frontmatter объектов и видны в графе Obsidian.
- Ссылки внутри `.sb/` — **голые `id`**, не wikilink-и (основание — §15.3 черновика v1.1).
- Пустые значения — `null`, а не пропуск ключа. UTF-8 без BOM, LF.
- **Критерий ADR-002 уточнён:** в Markdown живёт то, с чем работает человек; в `.sb/` — то, с чем
  работает только плагин. Определения метамодели и экземпляры объектов остаются в Markdown.
  Принцип самоопределяемости не нарушен: тип `relation` — по-прежнему объект метамодели в Markdown.

> [!danger] `.sb/relations/` — основные данные, не производные
> Восстановить их из заметок нельзя. Меры: резервная копия перед любой массовой операцией (M1),
> плагин — единственный автор (M2), атомарная запись через временный файл (M3), повреждённая строка
> не применяется (M4), собственный просмотр обязателен (M5), собственный типизированный граф (M6),
> команда экспорта в Markdown на этап 2 (M7), журналирование (M8), предупреждение в README хранилища (M9).

Компенсация потери обратных ссылок и графа Obsidian: блок «Связан с этим объектом» (Р11) и собственный
типизированный граф с фильтром по типу связи — то, что граф Obsidian делать не умеет.

| Templater пользователя («Trigger on new file creation» + Folder templates) перезапишет созданный нами объект | Мы не пишем токены `<% %>` в файлы; инструкция — папки объектов в `Excluded folders`; валидация уровней 2/4/6 ловит поломку frontmatter; инвариант И8 защищает тело `media` (DL-190) |
