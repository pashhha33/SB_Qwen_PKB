> [!important] Как начать новую сессию с этим проектом

> 3. Добавьте одну строку: «Продолжаем проект Second Brain. Прочитай контрольную точку и документы по ссылкам, подтверди понимание и задай следующий шаг».
> 4. Ассистент обязан: подтвердить фазу и следующий шаг, перечислить принятые решения, назвать открытые вопросы — и только потом продолжать.

> состав ядра из 11 типов, требование создавать элементы метамодели командами.

## 1. Роль ассистента и режим работы (обязательно к соблюдению)

- Ведущий архитектор метамоделей, наставник, тимлид и технический соавтор. Не пассивный исполнитель.
- Пользователь — **новичок** в TypeScript, Obsidian API и разработке плагинов. Поверхностно знаком
  с онтологиями, метамоделями, графами знаний, JSON Schema. **Не знает RDF/OWL.**
- Любой технический термин при первом появлении: объяснить простыми словами + бытовая аналогия +
  зачем в проекте + пометка «термин» + занести в глоссарий.
- Инициатива обязательна: сначала 2–3 варианта с плюсами и минусами, потом рекомендация с обоснованием,
  потом ждать решения. **Ключевые решения за пользователя не принимать.**
- Не более 2–4 вопросов за сообщение. После вопросов — остановиться и ждать ответа.
- Артефакт создаётся **сразу** после утверждения решения, не «на потом».
- В конце каждого сообщения — блок «Компас» (где мы, куда идём, что дальше) и блок «Новые термины».
- Стиль: подробно, практично, с примерами и обоснованиями. Явно помечать: «предложение», «рекомендация»,
  «решение», «вопрос», «риск», «изменение, требующее подтверждения», «предположение», «термин».

## 3. Цель

1. Доработать метамодель личной базы знаний **Second Brain**: классификация, сложные объекты,
   устранение противоречий и дублей.
2. Зафиксировать её в документации и артефактах, довести до состояния «готова к реализации».
3. Реализовать MVP плагина Obsidian со стабильным ядром.

**Критерий «метамодель утверждена»** — 32 пункта в [[../roadmap/readiness-checklist|чек-листе]]
(блоки A–F) + явное подтверждение пользователя + версия `1.0.0`.

**Критерий стабильного ядра плагина:** устанавливается в пустой vault, создаёт заметку по типу из
метамодели, валидирует frontmatter, показывает связи хотя бы в одном сценарии, есть тесты на ядро,
есть README и руководство пользователя.

## 4. Что за модель (суть в трёх абзацах)

**Second Brain** — самоопределяющаяся объектная модель внутри Obsidian. Не «список типов заметок»,
а система, где тип объекта, свойство, тип свойства, тип отношения, отношение, таксономия, фасет,
категория, представление и автоматизация — **тоже объекты** со своими `id` и `type`.

Три слоя: **(1) Фундамент** — закрытый набор, заданный кодом: 8 типов значений + системные атрибуты;
**(2) Метауровень** — описания: типы объектов, свойства, типы отношений, таксономии, фасеты, категории,
представления, автоматизации; **(3) Данные пользователя** — экземпляры объектов и экземпляры отношений.

Следствие: нужен «порядок запуска» (bootstrapping) — слой 1 обязан быть закрытым и заданным кодом;
один универсальный механизм чтения вместо девяти частных; метамодель можно менять без перекомпиляции
плагина; объём работы больше, чем у обычной схемы данных.

### 6.1. Рамки из промпта (DL-001…DL-007)

### 6.2. ADR-001 — идентификация и имя файла

| Параметр | Норма |
|---|---|
| `id` | **голый ULID**, 26 символов, Crockford Base32, верхний регистр. Пример: `01J8Z6M4K2Q7V9X3N5B0C1D2EF` |
| Имя файла | `{TYPE_PREFIX}-{ULID}.md`. Пример: `PERSON-01J8Z6M4K2Q7V9X3N5B0C1D2EF.md` |
| Каноническая ссылка | `[[{TYPE_PREFIX}-{ULID}.md\|{title}]]` |
| `TYPE_PREFIX` | технический код типа из реестра, `UPPER_SNAKE_CASE`, уникален как целая строка, 3–12 символов, только `A–Z`, `0–9`, дефис |
| Запрещено в именах файлов | квадратные скобки, `# ^ [ ] \|`, ведущие и завершающие пробелы |
| Переиспользование `id` | запрещено, в том числе после архивирования и удаления |

**Читаемость — три уровня по возрастанию стоимости:**
1. **Данные (обязательно в MVP):** инвариант `aliases[0] == title`. Obsidian нативно учитывает `aliases`
   в автодополнении ссылок и быстром переключателе.
2. **Чужой плагин:** Front Matter Title как **рекомендуемая необязательная** интеграция.
3. **Свой слой:** собственные адаптеры — только где уровень 2 не покрывает и область критична. **Вне MVP.**

**Раздел 17 черновика v1.1 вынесен за границы MVP.**

Обязательные меры: M1 отображаемое название никогда не участвует в разрешении ссылок (только `id` и
канонический путь); M2 инвариант `aliases[0] == title`; M3 каждый адаптер изолирован, сбой одного не
ломает остальные; M4 резервное поведение — показывать имя файла, а не пустоту; M5 при расхождении
`id` и ULID в имени файла чинить **имя файла по `id`**; M6 честная документация о границах поддержки;
M7 регрессионная проверка отображения после обновлений Obsidian.

Данные о стабильности Front Matter Title: [[../integrations/research-front-matter-title-stability]]
(10 открытых проблем из 179; два инцидента «белого экрана»; патчит ~10 недокументированных внутренностей
Obsidian; с июня 2026 — режим мягкого отказа).

### 6.3. ADR-002 — источник истины

**Определения метамодели — Markdown-заметки в хранилище. JSON в `.sb/` отклонён как место хранения определений.**

| Что | Где | Формат |
|---|---|---|
| Типы объектов, свойства, типы свойств, типы отношений, отношения, таксономии, фасеты, категории, представления, автоматизации | `Metamodel/**` (обычные папки vault) | Markdown + YAML frontmatter |
| Экземпляры объектов | обычные папки vault | Markdown + YAML frontmatter |
| Кэш, счётчики, журнал, резервные копии, настройки, черновики миграций | `.sb/` | JSON |

Критерий: если у сущности есть `id`, `type`, `title` и на неё можно сослаться — это объект метамодели
(Markdown). Если это технические данные плагина — `.sb/`.

Кэш в `.sb/cache/` — производные данные, обязан полностью пересоздаваться из заметок.
Чтение frontmatter — только через API Obsidian, не самописным разбором YAML.
Некорректное определение не применяется; плагин работает с последней корректной версией и показывает ошибку.
Восьмипунктовая последовательность применения изменений из §15.4 v1.1 сохраняется.

### 6.4. ADR-003 — язык ключей и слой подписей

| Слой | Поле | Язык | Стабильность |
|---|---|---|---|
| Технический | `key` | английский `snake_case` | стабилен; меняется только через ломающее изменение |
| Отображаемый | `label` | русский | свободный; меняется в любой момент |

**Соглашение об именах:** системные атрибуты — `snake_case`, закрытый список (`id`, `type`, `title`,
`aliases`, `created_at`, `updated_at`); ключи свойств — `snake_case`, латиница; имена типов —
`snake_case`, единственное число; `TYPE_PREFIX` — `UPPER_SNAKE_CASE`; значения перечислений —
`snake_case`, латиница; `label` — русский, с заглавной буквы.

**Подписи гарантированно показываются в:** нашей модалке свойств, наших представлениях, сообщениях
валидации, командах и меню. **Как получится:** стандартная панель свойств Obsidian (только после
прототипа `MetadataEditor.register`), таблицы Bases. **Не показываются:** режим источника (сырой YAML),
поиск по хранилищу.

CSS-подмена и DOM-подмена подписей **отклонены** как хрупкие.
Режимы `view` (подписи) и `source` (ключи) — настройка и команда `toggle-label-mode`.
Полная таблица соответствия 40 старых русских имён новым английским ключам — в ADR-003.

### 6.5. ADR-004 — объём первого прохода и командное создание

**Две ступени:** (1) реестр всех ~40 типов с разметкой статуса — дёшево, сохраняет полноту картины;
(2) детальное описание только типов ядра.

**Все элементы метамодели создаются и изменяются командами плагина**, не ручным редактированием файлов
(правила П1–П6). Это компенсирующая мера для ADR-002: раз риск Markdown-хранилища — сломанный вручную
YAML, основной способ правки не должен быть ручным.

Команды MVP: `create-object`, `create-object-type`, `create-property`, `create-relation-type`,
`validate-object`, `validate-vault`, `show-object-panel`, `toggle-label-mode`.
Вне MVP, но обозначены логически: `create-category`, `create-facet`, `create-taxonomy`,
`create-relation`, `create-view`, `create-automation`, `assign-category`.

Добавление нового предметного свойства **не требует** изменения кода и перекомпиляции плагина.
Наличие определения свойства не означает автоматической записи значения во все существующие объекты.

### 6.6. ADR-005 — модель классификации

**Три уровня:** `taxonomy → facet → category → назначение объекту`.

- `taxonomy` объединяет фасеты и задаёт область применения (`allowed_object_types`).
- `facet` — отдельное измерение классификации; **настройки иерархии и назначения задаются на уровне фасета**:
  `hierarchy_mode`, `assignment_cardinality`, `root_requirement`. Фасет наследует значения по умолчанию
  от таксономии и может их переопределить.
- `category` — значение внутри ровно одного фасета; иерархия через `parent`, предки вычисляются,
  корень не имеет родителя. Перенос категории в другой фасет — контролируемая операция.

**Обязательность `categories` задаёт фасет** через `assignment_cardinality`, а не универсальное ядро.
По умолчанию категории необязательны.

**`tags`** — системный атрибут, **свободные метки вне метамодели**: без справочника, без валидации.
Правило разделения: `tags` — неформальные и спонтанные; `categories` — управляемые, из справочника
фасета, проверяются. Прижившаяся метка повышается до категории соответствующего фасета.

**Критерий «подтип или категория» — два теста по порядку:**

> **Тест 1.** Нужны ли этому виду объектов **собственные свойства**, которых нет у родителя?
> Да → подтип. Нет → тест 2.
>
> **Тест 2.** Является ли это **открытым множеством значений**, которое пользователь пополняет
> без изменения метамодели? Да → категория. Нет → подтип.

Применение теста: Веб-новела → категория; Глава → подтип (поля `номер`, отношение «часть — целое»);
Эпизод → подтип; Персонаж → подтип; Фантастика → категория; Стихотворение → спорный случай, решение
за пользователем.

   - подтверждение объединения `scope` и `уровень` в одно поле (U-06, уже сделано в ADR-003);
   - избыточны ли `title` и `label` у свойства;
   - полный список системных атрибутов и граница «системное / расширяемое» (пункт 13 §13 v1.1).
2. **Шаг 6** — связи. Ключевое: критерий «ссылка-свойство или объект-отношение» и защита от дубля (C-07).
3. **11 карточек типов ядра** по [[../templates/entity-template|шаблону сущности]] — можно начать после
   шага 5, чтобы карточки сразу были полными, а не с заглушками.
