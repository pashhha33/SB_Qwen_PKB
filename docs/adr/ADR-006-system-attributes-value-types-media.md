# ADR-006. Системные атрибуты, типы значений и тип `media`

## Контекст

Шаг 5 плана. Открытыми оставались четыре группы вопросов:

1. тип значения «Список» без указания типа элементов при уже существующем поле `cardinality` (U-05);
2. обязательность, формат и политика обновления `created_at` / `updated_at` (C-13);
3. инвариант `aliases[0] == title` как правило валидации (C-12);
4. граница между системными атрибутами и расширяемыми предметными свойствами (пункт 13 §13 v1.1).

Плюс предложение пользователя: ввести тип `media`, который отвечает за медиафайлы и обёртки изображений,
чтобы в модалке выбора такие значения показывались миниатюрами — как в плагинах Fileclass и Metadata Menu.

Действующие ограничения: локально и офлайн; разработчик-новичок; ядро должно остаться подъёмным по объёму.

## Проблема

1. Сколько типов значений и какие именно?
2. Какие атрибуты являются системными, и что значит «системный»?
3. В каком формате хранятся даты и как они показываются?
4. Как моделировать медиафайлы и нужен ли для них отдельный тип?

## Рассмотренные варианты

### По типу значения «Список»

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A** | Убрать «Список» как тип значения; множественность задаёт `cardinality` у любого свойства | Семь типов вместо восьми; исчезает дублирование смысла; `categories` и `tags` естественно становятся множественными свойствами | Ломающее изменение относительно закрытого набора из восьми |
| B | Оставить «Список», добавить поле «тип элемента» | Набор из восьми сохраняется | Множественность описывается в двух местах (`cardinality` и тип «Список») — будущее противоречие |
| C | Оставить как есть | Ничего не меняем | Валидацию написать нельзя: непонятно, что проверять внутри списка |

### По датам

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A'** | Локальное время без смещения + настройка отображения в плагине | Просто читать и писать вручную; сортировка по строке совпадает с хронологией внутри одного часового пояса | При переезде в другой часовой пояс порядок записей нарушается |
| B | UTC с последующим отображением в локальном времени | Хронология верна всегда | Значение в файле не совпадает с тем, что видел пользователь при вводе; ручная правка становится неудобной |
| C | ISO 8601 со смещением (`+03:00`) | Точность без потери локальности | Смещение всё равно нужно учитывать при сравнении; ручная правка затруднена |

### По типу `media`

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A** | Ввести тип `media` в ядро с минимальным набором полей; механизм контекстного разрешения (v1.1 §10) оставить отложенным | Закрывает G-13; даёт опору для миниатюр в модалке; объединяет все носители одним типом | Ядро растёт до 14 типов |
| B | Оставить `image_wrapper` отложенным целиком, тип не вводить | Ядро меньше | Нечем показать миниатюру; медиа остаются вне модели |
| C | Ввести `media` вместе со всем механизмом разрешения из §10 | Полнота | Одна из самых больших подсистем черновика попала бы в MVP — неприемлемо |

## Решение

Приняты варианты **A** (типы значений), **A'** (даты), **A** (`media`).

Формулировки пользователя: «1. Вводи» (абстрактные `work` и `activity`), «2. A, а если придётся
использовать словарь?» (+ предложение ввести тип медиа с миниатюрами), «3. A только с локальным временем
и настройкой в плагине их представления».

### Нормативная часть 1. Типы значений: семь вместо восьми

| `value_type` | Подпись | Что хранит | Пример |
|---|---|---|---|
| `text` | Текст | Строка | `Мастер и Маргарита` |
| `number` | Число | Целое или дробное | `1967`, `7.5` |
| `date` | Дата | Календарная дата, локальная | `2026-10-22` |
| `datetime` | Дата и время | Дата и время, локальные | `2026-10-22T14:35` |
| `boolean` | Логическое | `true` / `false` | `true` |
| `object_reference` | Ссылка на объект | Ссылка на объект метамодели или данных | `"[[PERSON-01J8….md|Михаил Булгаков]]"` |
| `media_reference` | Ссылка на медиа | Ссылка на объект типа `media` | `"[[MEDIA-01J8….md|Обложка]]"` |

**Убраны:** `Список` и `Список ссылок`.

**Множественность задаётся только полем `cardinality`** у свойства:

| `cardinality` | Значение | Пример свойства |
|---|---|---|
| `1` | ровно одно | `title` |
| `0..1` | ноль или одно | `publication_year` |
| `0..N` | ноль или много | `categories`, `tags`, `aliases` |
| `1..N` | одно или много | `author` у книги |

Пример: `tags` — свойство с `value_type: text` и `cardinality: 0..N`. Отдельный тип «список» не нужен.

> [!warning] Ломающее изменение
> Набор фундаментальных типов значений в исходниках объявлен закрытым. Мы его меняем: было восемь,
> стало семь. Это MAJOR относительно черновиков, но данных нет, поэтому цена близка к нулю.

### Нормативная часть 2. Ответ на вопрос «а если придётся использовать словарь?»

**Новый механизм не нужен.** Словарь (справочник допустимых значений) выражается существующими средствами,
и выбор между способами делается по одному правилу.

| Способ | Как устроен | Когда применять | Пример |
|---|---|---|---|
| **Перечисление (`enum`)** | Закрытый список значений, записанный прямо в определении свойства | Значений мало, они стабильны и носят технический характер. Добавление значения = изменение метамодели | `hierarchy_mode: strict \| polyhierarchical` |
| **Ссылка на категорию** | Свойство с `value_type: object_reference`, `target_types: [category]` и указанием фасета | Значений много, список пополняется, им управляет пользователь | `categories` → фасет «Жанр» |
| **Ссылка на объект другого типа** | То же, но `target_types` указывает предметный тип | Значение — самостоятельный объект со своими полями | `author` → `person` |

Пример свойства, которое является словарём:

```yaml
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D2ES
type: property
title: Country of publication
key: country_of_publication
label: Страна издания
value_type: object_reference
target_types:
  - "[[OBJECT_TYPE-….md|Категория]]"
target_facet: "[[FACET-….md|Страна издания]]"
cardinality: 0..1
required: false
definition: Страна издания произведения. Значения берутся из справочника фасета «Страна издания».
---
```

**Правило выбора:**

> Значений меньше десятка и они меняются только вместе с метамоделью → **`enum`**.
> Значений много, список пополняет пользователь, нужна иерархия или переводы → **категория фасета**.

Побочное преимущество: словарь-категория автоматически получает иерархию, подписи на русском,
валидацию кардинальности и возможность строить представления. Перечисление — нет.

### Нормативная часть 3. Системные атрибуты

**Системный атрибут** — поле, которое есть у **каждого** объекта, задано кодом плагина и не может быть
переопределено или отключено предметным свойством.

| `key` | Подпись | Тип значения | `cardinality` | Обязательность | Кто заполняет |
|---|---|---|---|---|---|
| `id` | — | `text` (ULID) | `1` | **обязательно** | плагин при создании |
| `type` | Тип объекта | `text` (ключ типа) | `1` | **обязательно** | плагин при создании |
| `title` | Название | `text` | `1` | **обязательно** | пользователь |
| `aliases` | Псевдонимы | `text` | `0..N` | необязательно, но подчиняется инварианту | плагин + пользователь |
| `created_at` | Создан | `datetime` | `1` | **обязательно** | плагин при создании |
| `updated_at` | Изменён | `datetime` | `1` | **обязательно** | плагин при каждом сохранении |
| `categories` | Категории | `object_reference` → `category` | `0..N` | задаёт фасет | пользователь через `assign-category` |
| `tags` | Метки | `text` | `0..N` | необязательно | пользователь |

**Граница «системное / расширяемое» (закрывает пункт 13 §13 v1.1):**

| | Системные атрибуты | Предметные свойства |
|---|---|---|
| Набор | Закрыт, задан кодом | Открыт, задаётся метамоделью |
| Можно отключить | Нет | Да |
| Можно переопределить тип значения | Нет | — |
| Можно уточнить обязательность в наследнике | Нет | Да |
| Добавление нового | Ломающее изменение MAJOR | Не требует изменения кода |
| Проверка | Ядром плагина всегда | Движком схемы по определениям |

**Инварианты системного слоя:**

- И1. `id` — валидный ULID, уникален в хранилище, не переиспользуется.
- И2. `id` совпадает с ULID в имени файла; при расхождении имя файла чинится по `id` (мера M5 ADR-001).
- И3. `type` указывает на существующий тип объекта; тип не абстрактный.
- И4. `aliases[0] == title`. Остальные элементы — дополнительные псевдонимы, порядок сохраняется.
- И5. `created_at` не меняется после создания. `updated_at` ≥ `created_at`.
- И6. Значения системных атрибутов не могут быть переопределены предметными свойствами с теми же ключами.

### Нормативная часть 4. Даты и время

| Параметр | Норма |
|---|---|
| Хранение `date` | `YYYY-MM-DD`, локальная дата |
| Хранение `datetime` | `YYYY-MM-DDTHH:mm`, **локальное время без смещения** |
| Точность | Минуты. Секунды не храним |
| Часовой пояс | Не хранится. Предполагается часовой пояс устройства в момент записи |
| Отображение | Настройка плагина, см. ниже |
| Сравнение и сортировка | Лексикографически по строке, что при едином часовом поясе совпадает с хронологией |

**Настройка отображения в плагине** (требование пользователя):

| Настройка | Значения | По умолчанию |
|---|---|---|
| Формат даты | `YYYY-MM-DD`, `DD.MM.YYYY`, `DD MMM YYYY`, «как в файле» | `DD.MM.YYYY` |
| Формат времени | `HH:mm`, `HH:mm:ss`, не показывать | `HH:mm` |
| Относительные даты | показывать «сегодня», «вчера», «3 дня назад» вместо абсолютных | выключено |
| Порог относительных дат | сколько дней считать «недавними» | 7 |

Настройка влияет **только на отображение**. В файлах всегда хранится канонический формат.

> [!warning] Известное ограничение
> Локальное время без смещения ломает хронологический порядок, если заметки создаются в разных
> часовых поясах (поездка, переезд, два устройства). Для личной базы знаний в одном часовом поясе
> это приемлемо. Если ограничение станет мешать, добавим необязательное поле `timezone` или переход
> на UTC — как ломающее изменение MINOR/MAJOR с миграцией. Зафиксировано как G-04-1.

### Нормативная часть 5. Тип `media`

```yaml
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D2ET
type: media
title: Master and Margarita cover
aliases:
  - Обложка «Мастер и Маргарита»
created_at: 2026-10-22T14:35
updated_at: 2026-10-22T14:35
file: "[[attachments/master-i-margarita-cover.jpg]]"
media_kind: image
role: cover
description: Обложка издания 1973 года.
---
```

| `key` | Подпись | Тип значения | `cardinality` | Обязательность |
|---|---|---|---|---|
| `file` | Файл | `text` (путь к вложению) | `1` | **да** |
| `media_kind` | Вид медиа | enum: `image`, `audio`, `video`, `document`, `other` | `1` | **да** |
| `role` | Роль | enum: `cover`, `banner`, `logo`, `portrait`, `avatar`, `preview`, `background`, `other` | `0..1` | нет |
| `description` | Описание | `text` | `0..1` | нет |

Правила:

- один объект `media` может быть связан с несколькими объектами — через тип отношения, а не через копирование;
- роль не кодируется в имени файла (сохранено из `01` §12);
- у объекта может быть несколько медиа с разными ролями;
- **тип `media` заменяет тип `image_wrapper`** из спецификации: он шире по смыслу и покрывает изображения,
  аудио, видео и документы.

### Что входит в MVP, а что отложено

| Возможность | Статус | Обоснование |
|---|---|---|
| Тип `media` с полями `file`, `media_kind`, `role`, `description` | **MVP** | Дешёвая карточка типа |
| Миниатюры в нашей модалке выбора значения для свойств типа `media_reference` | **MVP** | Требуется пользователем; реализуется через `app.vault.getResourcePath()` — публичный API |
| Связь медиа с объектами через тип отношения | MVP (после шага 6) | Обычный механизм отношений |
| Механизм контекстного разрешения обёрток (v1.1 §10.1–10.5): поиск подходящей обёртки по контексту, приоритеты ролей, автозаполнение метаданных, разрешение неоднозначности | **отложено, этап 2** | Одна из самых больших подсистем черновика; рекомендация R-07 |
| Миниатюры в **стандартном** автодополнении ссылок Obsidian | **отложено** | Требует патча `EditorSuggest`, то есть недокументированных механизмов — ровно тот риск, который описан в [[../integrations/research-front-matter-title-stability]] |

> [!note] Про Fileclass и Metadata Menu как ориентир
> Оба плагина показывают миниатюры и типизированные контролы в **собственных** формах, а не в стандартном
> автодополнении Obsidian. Это подтверждает выбранный путь: делать свою модалку (что уже зафиксировано
> в §18.4 v1.1) и показывать миниатюры там. Карточки интеграций для Fileclass и Metadata Menu будут
> созданы на шаге 8 — как референсы, не как зависимости (C-11, R-08).

### Нормативная часть 6. Абстрактные родители `work` и `activity`

| Тип | `type` | `TYPE_PREFIX` | `abstract` | Наследники |
|---|---|---|---|---|
| Произведение | `work` | `WORK` | **true** | `book`; позже `chapter`, `poem`, `lyrics`, `movie`, `series`, `episode`, `music_track`, `music_album`, `video_game` |
| Деятельность | `activity` | `ACTIVITY` | **true** | `project`; позже `task`, `goal`, `problem` |

Общие поля, которые предлагается описать на родителях (уточняется в карточках типов):

- `work`: `title`, `description`, `categories`, plus предметные `author`, `publication_year` — решить,
  общие они или только у `book`;
- `activity`: `status`, `starts_on`, `ends_on`, `description`.

### Нормативная часть 7. Ядро — 14 типов

| Группа | Типы | Количество |
|---|---|---|
| Предметные | `person`, `project`, `book`, `knowledge`, `media` | 5 |
| Абстрактные предметные | `work`, `activity` | 2 |
| Системные метамодели | `object_type`, `property`, `relation_type`, `relation` | 4 |
| Системные классификации | `taxonomy`, `facet`, `category` | 3 |
| **Итого** | | **14** |

`property_type` — в реестре, `abstract: true`, без детальной карточки (ADR-004, подтверждено ADR-006:
семь типов значений заданы кодом).

## Обоснование

1. **Семь типов значений вместо восьми.** Множественность — характеристика свойства, а не тип значения.
   Поле `cardinality` уже существует; держать множественность в двух местах — значит заложить будущее
   противоречие (мы только что потратили шаг на разбор похожего в классификации).
2. **Словарь не требует нового механизма.** Он выражается либо перечислением, либо ссылкой на категорию
   фасета. Второй способ автоматически даёт иерархию, русские подписи и валидацию.
3. **Локальное время выбрано пользователем осознанно** и совпадает с практикой личной базы знаний:
   значение в файле должно совпадать с тем, что пользователь видел при вводе. Ограничение при смене
   часового пояса зафиксировано честно, а не замалчивается.
4. **Тип `media` вводится малой кровью.** Сам тип — это четыре поля. Отложена дорогая часть: механизм
   контекстного разрешения из §10 v1.1. Так пользователь получает миниатюры в модалке, не втягивая
   в MVP одну из крупнейших подсистем черновика.
5. **Миниатюры — через публичный API.** `app.vault.getResourcePath()` отдаёт адрес ресурса, который
   можно вставить в `<img>`. Никакой DOM-подмены и недокументированных механизмов.

## Последствия

### Положительные
- Закрыты U-05, C-13, G-13, G-04 (формат дат).
- Появился ответ на вопрос о словарях — без нового механизма.
- `image_wrapper` (одна из самых тяжёлых подсистем) заменён более общим и дешёвым типом `media`.
- Системные атрибуты перечислены исчерпывающе; граница «системное / расширяемое» формализована.

### Отрицательные / чем платим
- **Ядро выросло с 11 до 14 типов.** Риск объёма — см. меры ниже.
- Набор типов значений изменён относительно объявленного закрытым — ломающее изменение.
- Локальное время без смещения ломает хронологию при смене часового пояса.
- Миниатюры будут только в нашей модалке, не в стандартном автодополнении Obsidian.

### Обязательные компенсирующие меры

|---|---|
| M1 | Карточки **системных** типов (`object_type`, `property`, `relation_type`, `relation`, `taxonomy`, `facet`, `category`) описываются **сокращённо**: их состав полей уже задан в `01-classification.md` и этом ADR. Отдельно расписывать их как пользовательские типы не нужно |
| M2 | Карточки абстрактных типов (`work`, `activity`) — минимальные: только общие наследуемые поля |

| M5 | Если `created_at` или `updated_at` отсутствуют (заметка создана не плагином), плагин дописывает их при первом сохранении через свою команду и выдаёт `warning` — не `error`. Действие видимое, соответствует принципу «не молча переписывать данные» |
| M6 | Миниатюры в модалке имеют резервное поведение: если файл недоступен — показываем значок типа и имя файла, а не пустое место |
| M7 | Ограничение локального времени зафиксировано в `06-time-and-intervals.md` и в руководстве пользователя |

## Открытые следствия

1. **`music_track` против `media` вида `audio`.** Трек — это произведение (название, исполнитель, альбом),
   а аудиофайл — носитель. Предлагаю: `music_track` наследует `work` и **ссылается** на объект `media`
   с `media_kind: audio`. Решаем на этапе 2, когда дойдём до группы «Произведение».
2. **Свойство `file` у `media`.** Хранит путь к вложению как строку, а не ссылку. Причина: вложение —
   не объект метамодели (у него нет `id`). Альтернатива — хранить wikilink на файл вложения. Уточняем
   на шаге 6 вместе с правилами ссылок.
3. **Общие поля `work` и `activity`** — что именно наследуется, решаем при описании карточек типов.
4. **Относительные даты** в представлениях — настройка есть, реализация на этапе 2.
