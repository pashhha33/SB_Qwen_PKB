# ADR-004. Объём первого прохода и командный способ создания метамодели

## Контекст

Спецификация v1.0 §5 перечисляет около сорока типов объектов в восьми группах: системные, знание,
произведение, коллекция, источник, контекст, деятельность, медиаматериалы. Но **ни для одного типа не
описаны его свойства** (пробел G-01). При этом критерий стабильного ядра плагина из промпта проекта —
«создаёт заметку по типу из метамодели».

Черновик v1.1 §15.4 фиксирует: «основной поддерживаемый способ изменения метамодели — команды и интерфейс
плагина», а §14.3: «добавление обычного предметного свойства не должно требовать изменения исходного кода
или перекомпиляции плагина».

Действующие ограничения: проект делает один разработчик-новичок; риск «не дойти до кода» при объёме в
40 типов — высокий; реальных данных нет.

## Проблема

Сколько типов описать детально в первом проходе и каким способом создаются элементы метамодели?

## Рассмотренные варианты (объём)

### Вариант A — все ~40 типов с полями
- Плюсы: полнота.
- Минусы: по оценке, плюс 20–30 сообщений диалога; высокая вероятность завязнуть в типах, которые
  годами не понадобятся; риск не дойти до реализации.

### Вариант B — ядро из 6–8 типов с полями, остальные в реестре как «отложено»
- Плюсы: быстрый выход к работающему плагину; на небольшом наборе отрабатывается весь механизм
  (тип → свойства → связи → валидация → шаблон), дальше тиражируется.
- Минусы: часть типов временно без описания.

### Вариант C — все ~40 в реестре, поля только у 3–5
- Плюсы: быстро даёт общую карту.
- Минусы: большинство типов непригодны для создания заметок; к описанию полей придётся возвращаться.

## Решение по объёму

**Принят вариант B с элементом варианта C.** Формулировка пользователя: «B с возможностью создавать типы
и свойства через команды, вписывая их прямо в метамодель, и общее пожелание создавать сущности метамодели
через команды».

### Двухступенчатый план

**Ступень 1 — реестр всех типов (дёшево).** Все ~40 типов из спецификации заносятся в
`docs/metamodel/02-entities.md` с четырьмя колонками: имя, родитель, абстрактный ли, статус
(`core` / `phase2` / `deferred` / `out_of_scope`) и `TYPE_PREFIX`. Поля не описываются.
Закрывает D-01 и G-02, даёт полную карту.

**Ступень 2 — детальное описание ядра.** По карточке на тип по [[../templates/entity-template|шаблону
сущности]]: назначение, признаки типа, контрпримеры, свойства, связи, правила валидации, пример
экземпляра, этап и модуль.

### Предлагаемое ядро: 4 предметных типа + 4 системных

| Тип | `type` | `TYPE_PREFIX` | Группа | Почему в ядре |
|---|---|---|---|---|
| Человек | `person` | `PERSON` | Контекст | Есть в примерах черновиков; нужен для связей «автор», «владелец» |
| Проект | `project` | `PROJECT` | Деятельность | Есть в примерах v1.1 §1.2; проверяет группу «Деятельность» и жизненный цикл |
| Книга | `book` | `BOOK` | Произведение | Есть в примерах; проверяет группу «Произведение» и связь с категорией |
| Знание | `knowledge` | `KNOWLEDGE` | Знание | Без него база знаний не база; самый «свободный» тип, хорошо проверяет валидацию |
| Тип объекта | `object_type` | `OBJECT_TYPE` | Системные | Без него модель не самоопределяющаяся |
| Свойство | `property` | `PROPERTY` | Системные | Без него нельзя описать поля |
| Тип отношения | `relation_type` | `RELATION_TYPE` | Системные | Без него связи не типизированы |
| Отношение | `relation` | `RELATION` | Системные | Нужен для проверки реификации связи |

**Кандидаты на добавление в ядро (требуется ваше решение — см. вопросы ниже):**

| Тип | Аргумент «за» | Аргумент «против» |
|---|---|---|
| `category` (Категория) | Без него не проверить классификацию, а классификация — одна из главных целей проекта | Системный тип, добавляет объёма |
| `facet` (Фасет) | Нужен, если уровень «Фасет» будет утверждён | Зависит от нерешённого вопроса C-04 |
| `taxonomy` (Таксономия) | То же | То же |
| `property_type` (Тип свойства) | Слой 1 закрыт и задан кодом — но в самоопределяющейся модели ему положено быть объектом | Можно задать кодом и не описывать карточку |

### Остальные типы — разметка в реестре

| Группа | Типы | Предлагаемый статус | Обоснование |
|---|---|---|---|
| Системные | Категория, Таксономия, Фасет, Свойство, Тип свойства, Отношение, Тип отношения, Представление, Автоматизация | `core` или `phase2` | Зависят от шага 4 (классификация) и шага 8 (представления) |
| Знание | Концепция, Идея, Гипотеза, Вывод, Решение | `phase2` | Похожи на `knowledge`; сначала описываем родителя, потом решаем, нужны ли отдельные типы или это категории |
| Произведение | Веб-новела, Глава, Стихотворение, Текст песни, Фильм, Сериал, Эпизод, Музыкальный трек, Музыкальный альбом, Видеоигра | `phase2` | Большая группа; сначала отрабатываем механизм на `book` |
| Коллекция | Франшиза, Книжная серия, Серия фильмов, Музыкальная серия, Галерея | `deferred` | Потребуется после «Произведения» |
| Источник | Статья, Веб-страница, Видео, Аудио | `phase2` | Вероятно понадобятся рано, но не в первом проходе |
| Контекст | Организация, Место, Событие | `phase2` | Механизм тот же, что у `person` |
| Деятельность | Задача, Цель, Проблема | `phase2` | Механизм тот же, что у `project` |
| Медиаматериалы | Обёртка изображения | `deferred` (R-07) | Полноценная подсистема, см. [[../metamodel/analysis-01-incoming-drafts]] рекомендацию R-07 |
| Отдельно | Персонаж (`CHARACTER`) | `phase2` | Требует исправления опечатки в префиксе (U-10) и решения: подтип `person` или самостоятельный тип |

## Решение по способу создания

**Принято: все элементы метамодели создаются и изменяются командами плагина.** Формулировка пользователя:
«с возможностью создавать типы и свойства через команды, вписывая их прямо в метамодель, и общее пожелание
создавать сущности метамодели через команды».

### Нормативная часть

| Правило | Содержание |
|---|---|
| П1 | Элементы метамодели создаются **командами плагина**, а не ручным созданием файлов |
| П2 | Команда создаёт заметку в правильной папке, с правильным именем файла, генерирует `id`, заполняет обязательные системные атрибуты и проверяет результат |
| П3 | Ручное редактирование технически возможно, но не является поддерживаемым способом (§15.5 v1.1 сохраняется). Плагин перечитывает и проверяет такие файлы до применения |
| П4 | Добавление нового предметного свойства **не требует** изменения кода и перекомпиляции плагина (§14.3 v1.1 сохраняется) |
| П5 | Наличие определения свойства не означает автоматической записи значения во все существующие объекты (§14.3 v1.1 сохраняется) |
| П6 | Любое изменение определения проходит восьмипунктовую последовательность из §15.4 v1.1 без изменений |

### Предлагаемый набор команд MVP

Команды Obsidian — это пункты, которые вызываются через палитру команд (по умолчанию `Ctrl+P` / `Cmd+P`)
или через кнопку. Предлагаемый минимальный набор:

| Команда (внутреннее имя) | Что делает | Приоритет |
|---|---|---|
| `create-object` | Создать объект: выбор типа → форма с обязательными полями → файл | **MVP** |
| `create-object-type` | Создать тип объекта: `title`, `key`, `TYPE_PREFIX`, `parent_type`, признак абстрактности | **MVP** |
| `create-property` | Создать свойство: `title`, `key`, `label`, `value_type`, `cardinality`, `required`, `scope` | **MVP** |
| `create-relation-type` | Создать тип отношения: роли, направление, кардинальности, допустимые типы | **MVP** |
| `create-category` | Создать категорию в выбранном фасете | MVP, если фасет утверждён |
| `create-facet` / `create-taxonomy` | Создать фасет / таксономию | MVP, если фасет утверждён |
| `validate-object` | Проверить текущий объект и показать диагностики | **MVP** |
| `validate-vault` | Проверить всё хранилище | MVP |
| `show-object-panel` | Панель сущностей: список объектов по типам | MVP |
| `toggle-label-mode` | Переключить режим подписей `view` / `source` (см. [[ADR-003-bilingual-keys-and-label-layer]]) | MVP |
| `create-relation` | Создать объект-отношение | этап 2 |
| `create-view` / `create-automation` | Создать представление / автоматизацию | этап 2 |
| `assign-category` | Назначить категорию объекту | этап 2 |

Команды вне MVP остаются обозначенными логически, но не реализуются — это ровно требование промпта
про «модули: реализуемые и нереализуемые, но логически и семантически обозначенные».

### Связь с ADR-002

Правила П1–П3 — не пожелание, а **компенсирующая мера** для решения хранить определения в Markdown.
Раз основной риск Markdown-хранилища — ручная правка YAML, то основной способ правки должен быть не ручным.
Команды плагина и есть этот способ.

## Обоснование

1. **8 типов достаточно, чтобы отработать весь механизм.** На них проверяется всё: наследование
   (`person` ← контекст), связи (`book` — автор → `person`), классификация (`book` — жанр), валидация,
   шаблоны, самоопределение (`object_type` и `property` — сами объекты).
2. **Тиражирование дешевле проектирования.** Описать девятый тип по готовому образцу — час работы.
   Описывать сорок типов до того, как образец отлажен, — риск переделывать сорок раз.
3. **Реестр всех типов сохраняет полноту картины** и не даёт потерять ни один тип из спецификации.
4. **Командный способ создания закрывает главный риск ADR-002** и соответствует вашему же §15.4.
5. **Список команд — это заодно и граница MVP.** Что есть в списке с пометкой MVP — то и реализуем.

## Последствия

### Положительные
- Реалистичный объём: вместо 40 карточек — 8, плюс дешёвый реестр.
- Ни один тип из спецификации не потерян.
- Ясная граница MVP по командам.
- Основной риск Markdown-хранилища закрыт организационно.

### Отрицательные / чем платим
- Часть типов некоторое время существует только как строка в реестре, без полей.
- Пользователь не сможет создать заметку типа «Фильм», пока тип не описан. Нужно честное сообщение об этом
  в интерфейсе: «тип не описан, создание недоступно».
- Набор команд требует поддержки: каждая команда — код, тесты, документация.

### Обязательные компенсирующие меры

| № | Мера |
|---|---|
| M1 | Тип со статусом, отличным от `core`, показывается в интерфейсе как «недоступен в этой версии» с причиной |
| M2 | Реестр типов — живой документ: при описании нового типа строка реестра обновляется в тот же ход |
| M3 | Уникальность `TYPE_PREFIX` проверяется при создании типа командой `create-object-type` |
| M4 | Автоматическая проверка формата `key` и `TYPE_PREFIX` при создании (см. ADR-003, мера M4) |
| M5 | Каждая команда MVP покрыта минимум одним тестом |

## Влияние на метамодель

| Что меняется | Было | Стало | Ломающее изменение? | Нужна миграция? |
|---|---|---|---|---|
| Объём описанных типов | ~40 названий без полей | 8 детальных карточек + реестр из ~40 | нет | нет |
| Способ создания определений | не определён | команды плагина | нет | нет |
| Типы «Веб-новела», «Глава», «Фильм» и др. | равноправные элементы списка | помечены `phase2` / `deferred` | нет | нет |
| Обёртка изображения | раздел метамодели v1.1 §10 | отложенный модуль | нет | нет |

## Открытые следствия

1. **Состав ядра подлежит вашему подтверждению.** Восемь типов выше — предложение. Особенно спорны
   `category`, `facet`, `taxonomy`, `property_type`.
2. **Критерий «подтип или категория»** (например, «Веб-новела» — подтип книги или категория?) будет применён
   на шаге 4 и может изменить состав ядра.
3. **Префикс `CHARACTER`** содержит кириллическую «Е» в исходнике — исправить при занесении в реестр (U-10).
4. **`Персонаж`** — самостоятельный тип или подтип `person`? Открытый вопрос шага 4.
