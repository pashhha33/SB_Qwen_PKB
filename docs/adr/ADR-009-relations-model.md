# ADR-009. Модель связей

## Контекст

Шаг 6 плана. В исходных черновиках связи описаны наполовину: есть правильная идея «тип отношения задаёт
семантику и правила, отношение хранит конкретную связь» (`01` §9–10), но:

- кардинальность одна (`0..N`) при двух сторонах связи (U-01);
- `правило_уникальности: уникальная_связь` не определено (U-02);
- `направление: направленное` — другие значения не перечислены (U-03);
- «рекомендация ≠ запрет» без указания последствий нарушения (U-04);
- роли `прямое_название` / `обратное_название` есть как поля, но правила их не описаны (G-11);
- два способа хранить связь (ссылка-свойство и объект-отношение) без критерия выбора и без защиты
  от дубля (C-07, пункт 5 §13 v1.1).

Плюс вопрос пользователя, которого в черновиках не было вовсе: **к чему привязана связь — к объекту
или к его свойству.**

Все решения по этому ADR получены от пользователя в диалоге 2026-10-22 и записаны в журнале как
DL-078…DL-084, DL-090…DL-092, DL-094…DL-095.

## Проблема

Как устроена связь: где объявляется, как хранится, какие ограничения задаёт тип отношения,
как читаются обе стороны и что происходит при удалении.

## Решение

Принято тринадцать решений. Ниже — каждое с нормативной формулировкой.

### Р1. Гибридная модель, критерий выбора объявляется в свойстве

Два способа хранения связи сосуществуют, и **выбор делается не «по ситуации», а в определении свойства**
полем `link_mode`:

| Значение | Что значит | Когда применять |
|---|---|---|
| `direct` | Значение хранится как ссылка в поле самого объекта | У связи нет собственных данных |
| `reified` | Значение хранится как объект `relation` | У связи есть собственные данные: период, порядок, источник, роль, описание |

> **Критерий:** у связи нужны собственные данные → `reified`. Иначе → `direct`.

Обоснование: объявление в свойстве делает выбор детерминированным и проверяемым кодом. Движок схемы
заранее знает, где искать значение, поэтому дубль одной связи двумя способами невозможен по построению.

### Р2. `link_mode` объявляется на свойстве, а не на типе отношения

Один и тот же тип отношения может в одном месте требовать периода (`reified`), а в другом — нет
(`direct`). Объявление на типе отношения этого не позволит.

### Р3. Привязка связи: поле `origin_property`

| Случай | `origin_property` | Где показывается связь |
|---|---|---|
| Создана из объявления свойства с `link_mode: reified` | заполнено | В контроле **этого** свойства и нигде больше |
| Создана сама по себе | пусто | В общем блоке связей объекта |

**Зачем это нужно.** Без `origin_property` два свойства одного типа, использующие один тип отношения,
видели бы связи друг друга. Конкретный пример поломки: у книги свойства `author` и `editor`, оба
с `target_types: [person]` и оба на типе отношения «Участие». Плагин ищет «связи с `subject` = эта книга
и `relation_type` = Участие» и находит всех участников сразу — в поле «Автор» попал бы редактор.

Свободно стоящие связи при этом сохраняются — они есть в спецификации v1.0 §9 и нужны для фактов,
которые не являются значением чьего-то поля: «Проект A конфликтует с Проектом B», «знают друг друга
с 1920 года».

### Р4. Двусторонняя кардинальность

Одно поле `cardinality` у типа отношения заменено на два:

| Поле | Что ограничивает |
|---|---|
| `subject_to_object` | Сколько объектов может быть у одного субъекта при данном типе отношения |
| `object_to_subject` | Сколько субъектов может быть у одного объекта при данном типе отношения |

Значения у обоих: `1`, `0..1`, `0..N`, `1..N`.

### Р5. Правило уникальности

Поле `uniqueness_rule` с тремя значениями:

| Значение | Что считается дублем | Пример |
|---|---|---|
| `pair` | Пара «субъект — объект»: связь любого типа между ними может быть только одна | Между двумя объектами вообще не может быть двух связей |
| **`triple` (по умолчанию)** | Тройка «субъект — тип отношения — объект» | «автор» и «редактор» между теми же двумя объектами допустимы |
| `none` | Ограничений нет | Для заведомо повторяющихся связей |

### Р6. Направление и симметричные связи

Поле `direction` — enum из двух значений:

| Значение | Что значит | Пример | Хранение |
|---|---|---|---|
| `directed` | Стороны неравноправны: субъект и объект | «автор книги» | Как обычно |
| `symmetric` | Связь читается одинаково в обе стороны | «супруг», «синоним», «коллега» | **Один раз**; обратная сторона вычисляется |

Правило: у типа отношения с `direction: symmetric` значения `forward_label` и `reverse_label`
**должны совпадать**. Иначе — `warning`.

### Р7. Допустимые и предпочтительные типы концов разделены

Два поля из черновиков (`рекомендуемый_субъект`, `рекомендуемый_объект`) заменены на четыре:

| Поле | Подпись | Что делает | Нарушение |
|---|---|---|---|
| `allowed_subject_types` | Допустимые типы субъекта | Жёсткое ограничение | **`error`**, значение не принимается |
| `allowed_object_types` | Допустимые типы объекта | Жёсткое ограничение | **`error`** |
| `suggested_subject_types` | Предпочтительные типы субъекта | Порядок вариантов в списке и предвыбор в модалке | Ничего, максимум `info` |
| `suggested_object_types` | Предпочтительные типы объекта | То же | Ничего |

Правила: пустой `allowed_*` означает «ограничений нет» (как в черновиках). Если `suggested_*` задано,
а `allowed_*` пусто — рекомендации влияют только на порядок в интерфейсе. `suggested_*` должен быть
подмножеством `allowed_*`, если заданы оба, иначе `warning`.

### Р8. Роли — свободный текст, оба поля обязательны

| Поле | Подпись | Пример |
|---|---|---|
| `forward_label` | Прямое название | `автор` |
| `reverse_label` | Обратное название | `автор произведения` |

Оба обязательны. Автоматическое образование одного из другого **отклонено**: правила русского языка
слишком разнообразны («автор» → «автор произведения», но «владелец» → «владеет»), автоматика будет
ошибаться. Плагин проверяет только непустоту и совпадение у симметричных типов.

Чтение связи: `субъект — forward_label → объект` и обратно `объект — reverse_label → субъект`.

### Р9. Локальные свойства объекта `relation`

| Поле | Подпись | Статус |
|---|---|---|
| `order` | Порядок | **ядро** — без него нельзя упорядочить список (главы книги, треки альбома) |
| `starts_on` | Дата начала | **ядро** — период действия связи |
| `ends_on` | Дата окончания | **ядро** — то же |
| `description` | Описание | **ядро** — одна строка |
| `is_primary` | Основное | этап 2 |
| `source` | Источник | этап 2 — появится вместе с типами группы «Источник» |
| `context` | Контекст | этап 2 — семантика неясна, пока нет конкретной потребности |
| `role` | Роль в этой конкретной связи | **ядро** — уточнение роли сверх `forward_label`; например «соавтор» при типе отношения «Участие» |

**Собственного текста у связи нет.** Решение пользователя: основную информацию можно получить из
контекста связи и из самого субъекта или объекта. Следствие: `description` — короткая строка, а не
заметка. Это же позволило выбрать компактный формат хранения (см. [[ADR-010-relation-storage]]).

### Р10. Системные атрибуты объекта `relation` — сокращённый набор

| Атрибут | У экземпляра объекта (Markdown) | У объекта `relation` |
|---|---|---|
| `id` | обязателен | **обязателен** |
| `type` | обязателен | **обязателен** |
| `title` | обязателен | **обязателен** — нужен для показа в типизированном графе и в списке связей |
| `aliases` | обязателен инвариант `aliases[0] == title` | **не применяется**: на связь нельзя сослаться wikilink-ом |
| `created_at` | обязателен | **обязателен** |
| `updated_at` | обязателен | **обязателен** |
| `categories` | задаёт фасет | **не применяется** |
| `tags` | необязателен | **не применяется** |

Это уточнение раздела 3 [[../metamodel/04-attributes|04-attributes.md]]: инварианты И1, И3, И5 действуют
полностью, И4 и И6 — только для Markdown-объектов.

### Р11. Обратная сторона вычисляется, не хранится

В форме объекта показывается вычисляемый блок «Связан с этим объектом», **только для чтения**.
Чтобы изменить связь, пользователь идёт к исходному объекту. Один источник истины сохраняется.

### Р12. Каскадное поведение

| Ситуация | Поведение |
|---|---|
| Удаление объекта | Его связи **удаляются** |
| Удаление определения свойства | Плагин **предупреждает**, показывает число затронутых связей и предлагает: архивировать или очистить `origin_property` (связь станет свободно стоящей и не потеряется) |
| Удаление определения типа отношения | **Запрещено**, пока есть связи |

Обоснование: связь без субъекта или объекта бессмысленна. Архивирование при удалении объекта породило бы
тысячи мёртвых записей. Принцип «архивирование предпочтительнее удаления» из `01` §18 относится
к **объектам**, а не к фактам связи.

### Р13. Защита от дубля `direct` / `reified`

Правило `relation.no_duplicate_link`: если свойство объявлено с `link_mode: reified`, в объекте не должно
быть значения-ссылки в этом поле; если объявлено `direct` — не должно быть объекта `relation` с таким
`origin_property`. Уровень `error`.

## Нормативная схема типа отношения

```yaml
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D2G0
type: relation_type
title: Authorship
aliases:
  - Authorship
created_at: 2026-10-22T14:35
updated_at: 2026-10-22T14:35

key: authorship
label: Авторство
forward_label: автор
reverse_label: автор произведения
direction: directed

subject_to_object: 1..N
object_to_subject: 0..N
uniqueness_rule: triple

allowed_subject_types:
  - "[[OBJECT_TYPE-….md|Книга]]"
allowed_object_types:
  - "[[OBJECT_TYPE-….md|Человек]]"
suggested_subject_types: []
suggested_object_types: []

definition: Authorship of a written work.
---
```

| Поле | Подпись | Тип значения | `cardinality` | Обязательность |
|---|---|---|---|---|
| `key` | Ключ | `text` | `1` | да |
| `label` | Подпись | `text` | `1` | да |
| `forward_label` | Прямое название | `text` | `1` | да |
| `reverse_label` | Обратное название | `text` | `1` | да |
| `direction` | Направление | enum `directed`, `symmetric` | `1` | да |
| `subject_to_object` | Кардинальность от субъекта | enum `1`, `0..1`, `0..N`, `1..N` | `1` | да |
| `object_to_subject` | Кардинальность от объекта | enum `1`, `0..1`, `0..N`, `1..N` | `1` | да |
| `uniqueness_rule` | Правило уникальности | enum `pair`, `triple`, `none` | `1` | да, по умолчанию `triple` |
| `allowed_subject_types` | Допустимые типы субъекта | → `object_type` | `0..N` | нет |
| `allowed_object_types` | Допустимые типы объекта | → `object_type` | `0..N` | нет |
| `suggested_subject_types` | Предпочтительные типы субъекта | → `object_type` | `0..N` | нет |
| `suggested_object_types` | Предпочтительные типы объекта | → `object_type` | `0..N` | нет |
| `definition` | Определение | `text` | `0..1` | нет |

## Нормативная схема экземпляра связи

```json
{
  "id": "01J8Z6M4K2Q7V9X3N5B0C1D2G1",
  "type": "relation",
  "title": "Bulgakov authored The Master and Margarita",
  "subject": "01J8Z6M4K2Q7V9X3N5B0C1D2F3",
  "relation_type": "01J8Z6M4K2Q7V9X3N5B0C1D2G0",
  "object": "01J8Z6M4K2Q7V9X3N5B0C1D2EF",
  "origin_property": "01J8Z6M4K2Q7V9X3N5B0C1D2F0",
  "role": "автор",
  "order": 1,
  "starts_on": "1928-01-01",
  "ends_on": null,
  "description": null,
  "created_at": "2026-10-22T14:35",
  "updated_at": "2026-10-22T14:35"
}
```

Ссылки внутри хранилища связей — **голые `id`**, а не wikilink-и. Формат и расположение —
в [[ADR-010-relation-storage]].

## Правила валидации

| ID правила | Формулировка | Уровень |
|---|---|---|
| `relation.subject.exists` | Субъект существует | error |
| `relation.object.exists` | Объект существует | error |
| `relation.type.exists` | Тип отношения существует | error |
| `relation.subject_not_object` | Субъект и объект — разные записи | error |
| `relation.allowed_subject_type` | Тип субъекта входит в `allowed_subject_types`, если список задан | error |
| `relation.allowed_object_type` | Тип объекта входит в `allowed_object_types`, если список задан | error |
| `relation.cardinality.subject_to_object` | Число связей от субъекта не нарушает `subject_to_object` | error |
| `relation.cardinality.object_to_subject` | Число связей от объекта не нарушает `object_to_subject` | error |
| `relation.uniqueness` | Нет дубля по правилу `uniqueness_rule` | error |
| `relation.origin_property.exists` | Если `origin_property` заполнено, оно указывает на существующее свойство | error |
| `relation.origin_property.type_match` | Тип субъекта соответствует типу, в котором объявлено свойство | error |
| `relation.origin_property.reified` | Свойство, на которое указывает `origin_property`, имеет `link_mode: reified` | error |
| `relation.no_duplicate_link` | Нет одновременно значения-ссылки в поле и объекта `relation` для одного свойства | error |
| `relation.free_standing.visible` | Свободно стоящая связь показана в общем блоке связей объекта | info |
| `relation.period.order` | `starts_on` не позже `ends_on` | error |
| `relation.period.open` | `ends_on` пустое означает «по настоящее время», это допустимо | info |
| `relation_type.labels.required` | `forward_label` и `reverse_label` непустые | error |
| `relation_type.symmetric.labels_equal` | У типа с `direction: symmetric` роли совпадают | warning |
| `relation_type.suggested_subset_allowed` | `suggested_*` является подмножеством `allowed_*`, если заданы оба | warning |
| `relation_type.direction.enum` | `direction` равен `directed` или `symmetric` | error |
| `relation_type.uniqueness.enum` | `uniqueness_rule` равен `pair`, `triple` или `none` | error |
| `property.link_mode.enum` | `link_mode` равен `direct` или `reified` | error |
| `property.link_mode.relation_type` | У свойства с `link_mode: reified` указан тип отношения | error |

Всего 23 правила; вместе с ранее записанными — 61 предварительное правило валидации.

## Обоснование

1. **Каждое решение закрывает конкретную запись реестра проблем**, а не добавляет новую сущность:
   U-01 → Р4, U-02 → Р5, U-03 → Р6, U-04 → Р7, G-11 → Р8, C-07 → Р1–Р3 и Р13.
2. **Привязка к свойству через необязательное `origin_property`** сохраняет свободно стоящие связи
   из спецификации и одновременно убирает реальный конфликт двух свойств. Вариант «привязка обязательна»
   был бы проще, но отменил бы часть вашей архитектуры; вариант «привязки нет» оставил бы конфликт.
3. **Отказ от автоматического образования ролей** — пример случая, где автоматика дешевле не делает:
   ошибка в подписи связи видна пользователю постоянно.
4. **Сокращённый набор системных атрибутов у связи** — вынужденное, но честное уточнение: связь не является
   заметкой, у неё нет псевдонимов и категорий. Лучше записать это явно, чем оставить правило,
   которое не выполняется.
5. **Отсутствие собственного текста у связи** (Р9) — решение пользователя, и оно же открыло путь
   к компактному хранению в ADR-010.

## Последствия

### Положительные
- Все шесть записей реестра про связи закрыты.
- Выбор способа хранения детерминирован и проверяем.
- Симметричные связи не плодят дубли.
- Жёсткие ограничения отделены от подсказок — пользователь понимает, что запрещено, а что просто не рекомендовано.

### Отрицательные / чем платим
- Тип отношения стал сложнее: 13 полей вместо 6 в черновиках.
- Появилось поле `origin_property`, которого в черновиках не было.
- Системные атрибуты действуют не единообразно: у связи сокращённый набор. Это исключение нужно помнить.
- Свободно стоящие связи требуют отдельного места в интерфейсе, иначе пользователь их не найдёт.

### Обязательные компенсирующие меры

| № | Мера |
|---|---|
| M1 | Команда `create-relation-type` задаёт разумные значения по умолчанию: `direction: directed`, `uniqueness_rule: triple`, кардинальности `0..N`, списки допустимых типов пустые |
| M2 | Команда `create-property` при выборе `link_mode: reified` сразу спрашивает тип отношения |
| M3 | Блок «Связан с этим объектом» в форме объекта показывает и свободно стоящие связи, с пометкой «без свойства» |
| M4 | Раздел «Системные атрибуты» в `04-attributes.md` дополнен оговоркой о сокращённом наборе для `relation` |
| M5 | Все 23 правила получают тесты на примерах из `examples/instances/` — минимум по одному корректному и одному некорректному случаю |
| M6 | При удалении определения свойства плагин показывает предварительный просмотр последствий (число связей) до подтверждения |

## Влияние на метамодель

| Что меняется | Было | Стало | Ломающее изменение? | Нужна миграция? |
|---|---|---|---|---|
| `cardinality` у типа отношения | одно поле | `subject_to_object` + `object_to_subject` | **да** | Да; данных нет |
| `правило_уникальности` | значение не определено | `uniqueness_rule`: `pair` / `triple` / `none`, по умолчанию `triple` | **да** | То же |
| `направление` | значение не определено | `direction`: `directed` / `symmetric` | **да** | То же |
| `рекомендуемый_субъект` / `рекомендуемый_объект` | два поля | четыре: `allowed_*` и `suggested_*` | **да** | То же |
| `прямое_название` / `обратное_название` | необязательные | `forward_label` / `reverse_label`, оба обязательны | **да** | То же |
| Поле `origin_property` у связи | отсутствовало | введено, необязательное | нет | нет |
| Локальные свойства связи | семь, без разделения | ядро: `role`, `order`, `starts_on`, `ends_on`, `description`; этап 2: `is_primary`, `source`, `context` | нет | нет |
| Системные атрибуты у связи | те же, что у всех | сокращённый набор | **да** | нет |
| `link_mode` у свойства | введено ADR-006 без значений | `direct` / `reified`, обязательно для `object_reference` | нет | нет |

## Открытые следствия

1. **Интервалы.** `starts_on` и `ends_on` требуют правил для неполных дат и открытых периодов —
   шаг 7 (`06-time-and-intervals.md`).
2. **Порядок значений** для свойств с `cardinality: 0..N` — использовать ли `order` у связи или порядок
   элементов списка в frontmatter. Предлагаю: для `reified` — поле `order`, для `direct` — порядок
   элементов списка. Уточняется на шаге 7.
3. **Представление связей** в графе и таблицах — шаг 8 (`08-views.md`).
4. **Связь объекта `media` с другими объектами** — через тип отношения; конкретные типы появятся
   вместе с уточнениями пользователя по обёртке (DL-088).
