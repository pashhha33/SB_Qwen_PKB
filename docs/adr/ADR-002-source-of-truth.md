# ADR-002. Источник истины для определений метамодели

## Контекст

Спецификация v1.0 и метамодель v1.0 показывают каждый элемент метамодели как **заметку хранилища**
с полями `id` и `тип_объекта`: `PROPERTY-000001`, `RELATION-TYPE-000001`, `TAXONOMY-000001` — это файлы.

Черновик v1.1 §15 предлагает иное: определения метамодели хранятся в скрытой папке `.sb/metamodel/**`
в формате **JSON**, а Markdown с YAML-frontmatter остаётся форматом пользовательских объектов.

Оба подхода в черновиках присутствуют одновременно, что даёт два источника истины (C-02).

Действующие ограничения: работа локально и офлайн; разработчик — новичок в TypeScript и Obsidian API;
главный архитектурный принцип модели — «тип объекта сам является объектом» (самоопределяющаяся модель).

## Проблема

Где физически хранятся определения метамодели и что считается единственно правильными данными?

## Рассмотренные варианты

### Вариант A — определения в Markdown-заметках хранилища
- Суть: всё, включая типы объектов, свойства, типы отношений, таксономии, фасеты, категории, представления
  и автоматизации, — обычные заметки с frontmatter. `.sb/` хранит только служебные данные, не являющиеся объектами.
- Плюсы:
  - один формат и один механизм чтения на всю систему;
  - сохраняется главный принцип модели: метамодель — часть той же модели, что и данные;
  - определения видны в поиске, в графе, в быстром переключателе Obsidian;
  - не нужен отдельный редактор JSON;
  - работает механизм Obsidian по обновлению ссылок при переименовании;
  - меньше кода: не нужна вторая ветка чтения/записи.
- Минусы:
  - YAML чувствителен к отступам — ручная правка может сломать разбор;
  - служебные файлы смешиваются с пользовательскими заметками в одном пространстве;
  - при большом числе определений индексация может замедлиться.
- Последствия: обязательны строгая валидация при загрузке и создание определений через команды плагина,
  а не ручным редактированием.

### Вариант B — определения в JSON внутри `.sb/`
- Суть: как предложено в v1.1 §15.3.
- Плюсы: строгая структура; надёжное чтение и запись кодом; независимость от синтаксиса YAML; определения
  изолированы от пользовательских заметок.
- Минусы:
  - **нарушается принцип самоопределяющейся модели**: метамодель перестаёт быть частью той же модели;
  - два формата и две ветки кода;
  - определения не видны в графе, поиске и быстром переключателе;
  - для правки нужен внешний редактор или собственный интерфейс (который всё равно придётся писать);
  - скрытая папка не является механизмом защиты — это прямо признано в §15.1 v1.1.
- Последствия: растёт объём кода и поверхность для ошибок; теряется наглядность.

### Вариант C — гибрид: JSON как источник истины + генерируемые заметки-представления
- Суть: JSON главный, плагин порождает из него Markdown-копии для чтения и графа.
- Плюсы: машиночитаемость и человекочитаемость одновременно.
- Минусы: **синхронизация двух представлений — классический источник расхождений**; самый сложный в реализации;
  при любом сбое непонятно, какая копия правильная.
- Последствия: максимальная сложность при максимальной же неопределённости. Для новичка — неприемлемо.

## Решение

**Принят вариант A.** Формулировка пользователя: «Хотел B, но убедили твои аргументы A».

### Нормативная часть: что где лежит

| Что | Где | Формат | Является объектом метамодели? |
|---|---|---|---|
| Типы объектов, свойства, типы свойств, типы отношений, отношения, таксономии, фасеты, категории, представления, автоматизации | обычные папки хранилища | Markdown + YAML frontmatter | **да** |
| Пользовательские объекты (экземпляры) | обычные папки хранилища | Markdown + YAML frontmatter | да (экземпляры) |
| Кэш индекса, счётчики, журнал операций, резервные копии, настройки плагина, черновики миграций | `.sb/` | JSON | **нет** |

### Правило разделения

> [!important] Критерий
> Если у сущности есть `id`, `type` и `title` и к ней можно построить ссылку — это **объект метамодели**,
> он живёт в Markdown. Если это технические данные плагина, на которые нельзя сослаться как на объект, —
> они живут в `.sb/`.

Предварительная структура `.sb/` (уточняется на шаге 8, закрывает ваш пункт 14 из §13 v1.1):

```text
Vault/
├── .sb/
│   ├── config.json          # настройки плагина
│   ├── cache/               # производный индекс; может быть пересоздан с нуля
│   ├── logs/                # журнал значимых операций
│   ├── backups/             # резервные копии перед разрушительными изменениями
│   └── migrations/          # черновики и журнал миграций
├── Metamodel/               # ← объекты метамодели, обычные заметки
│   ├── ObjectTypes/
│   ├── Properties/
│   ├── PropertyTypes/
│   ├── RelationTypes/
│   ├── Relations/
│   ├── Taxonomies/
│   ├── Facets/
│   ├── Categories/
│   ├── Views/
│   └── Automations/
├── People/
├── Books/
└── ...
```

`Metamodel/` — предлагаемое имя папки, требует подтверждения (см. вопрос к шагу 4).

## Обоснование

1. **Сохраняется главный архитектурный принцип.** Самоопределяющаяся модель теряет смысл, если её описания
   вынесены в другой формат и в другое пространство. Тип объекта должен быть таким же объектом, как книга.
2. **Меньше кода — меньше ошибок.** Один механизм чтения, записи и валидации вместо двух. Для проекта,
   который пишет новичок, это решающий аргумент.
3. **Бесплатная наглядность.** Определения попадают в поиск, граф и быстрый переключатель Obsidian
   без единой строчки DOM-интеграции — в отличие от JSON, для которого всё это пришлось бы делать руками.
4. **Основной риск варианта A снимается организационно, а не технически.** YAML ломается при ручной правке —
   но ручная правка и не является основным способом изменения метамодели (§15.4 v1.1 это уже фиксирует,
   и это усилено в [[ADR-004-first-pass-scope-and-command-driven-authoring]]).

## Последствия

### Положительные
- Один формат, один парсер, один набор правил валидации.
- Метамодель видна и редактируема в самом Obsidian.
- Разделы 15.2–15.3 v1.1 сокращаются: `.sb/` остаётся, но только для служебных данных.
- Устраняется риск двух источников истины.

### Отрицательные / чем платим
- Определения смешаны с пользовательскими заметками в одном пространстве имён файлов.
- Ручная правка YAML опасна → нужна строгая валидация при загрузке и понятные сообщения об ошибках.
- Всё, что в `01` и v1.0 написано про JSON-определения (§15.3, пример с `kind`/`key`/`valueType`),
  переходит в статус **предварительного технического предложения**, а не нормативного описания хранилища.

### Обязательные компенсирующие меры

| № | Мера |
|---|---|
| M1 | Чтение frontmatter — только через API Obsidian (`app.metadataCache` и штатные функции), **не** самописным разбором YAML. Это снимает половину риска «сломал отступом» |
| M2 | Определение метамодели, не прошедшее валидацию, **не применяется**. Плагин показывает ошибку и продолжает работать с последней корректной версией (§15.5 v1.1 сохраняется дословно) |
| M3 | Основной способ изменения метамодели — команды и интерфейс плагина (усилено в ADR-004) |
| M4 | Последовательность применения изменения из восьми шагов (§15.4 v1.1) сохраняется без изменений, с заменой «разобрать JSON» на «прочитать frontmatter» |
| M5 | Папки определений (`Metamodel/**`) помечаются в документации как «служебные»: плагин предупреждает при ручной правке |
| M6 | Кэш в `.sb/cache/` — производные данные. Он должен полностью пересоздаваться из заметок. Никакой уникальной информации в нём не хранится |

## Влияние на метамодель

| Что меняется | Было | Стало | Ломающее изменение? | Нужна миграция? |
|---|---|---|---|---|
| Место хранения определений | не определено (два варианта одновременно) | Markdown-заметки в хранилище | нет (данных нет) | нет |
| Формат определений | JSON (v1.1 §15.3) | Markdown + YAML frontmatter | **да** относительно v1.1 | нет, данных нет |
| Назначение `.sb/` | хранилище определений метамодели | только служебные данные плагина | **да** относительно v1.1 | нет |
| Поля `kind`, `key`, `valueType`, `targetTypes`, `required`, `multiple` | нормативный пример JSON | предварительное предложение по именам полей; см. [[ADR-003-bilingual-keys-and-label-layer]] | — | — |

## Открытые следствия

1. **Порядок запуска (bootstrapping).** Чтобы прочитать объект, нужен его тип; чтобы прочитать тип — нужно
   уметь читать объекты. Решение: слой 1 (8 типов значений + системные атрибуты) задаётся **кодом**, а не
   данными. Это согласуется с «набор фундаментальных типов закрыт для текущей версии».
2. **Поведение при обнаружении ручных изменений файлов метамодели** (ваш пункт 15 из §13 v1.1) — описано
   в §15.5 v1.1 и сохраняется. Детализация: `docs/plugin/architecture.md` на Фазе 5.
3. **Резервирование и журналирование** (§15.6 v1.1) — в `.sb/backups/` и `.sb/logs/`, объём и сроки хранения
   определяются на шаге 8.
