# ADR-008. Тип свойства `media_reference`

## Контекст

[[ADR-006-system-attributes-value-types-media|ADR-006]] ввёл тип объекта `media` и седьмой тип значения
`media_reference`, но не раскрыл, **как тип значения ведёт себя в интерфейсе**.

Пользователь уточнил требование (дословно):

> «ты наверное неправильно понял, в плане типа медиа, я имел ввиду тип свойства, предложенное тобой можно
> оставить, а тип свойства уточнить. Тип свойства медиа фильтрует обёртки изображений и сами изображения,
> и представляет при выборе в виде миниатюр, для удобства выбора. Наподобие как в плагинах FileClass и
> Metadata Menu, подобный тип свойств там существует»

Различие существенное: **тип объекта** — это то, чем является запись в базе; **тип значения свойства** —
это то, какого рода данные хранятся в поле и каким контролом они вводятся. ADR-006 описал первое,
требование пользователя — про второе.

## Проверка ориентиров

### Metadata Menu

Подтверждено по официальной документации плагина. У него есть отдельный **тип поля** `Media`:

> «Media — A type that accepts an internal link to a media file from your vault»

Настройки типа поля `Media`:

| Настройка | Что делает |
|---|---|
| `the folders where your media files are located` | ограничивает поиск указанными папками |
| `the embed size for images` | задаёт размер встраиваемого изображения |
| `display the media modal search as list or cards (gallery style)` | **переключает список на галерею карточек** |

Отдельный тип `MultiMedia` — то же для нескольких значений.

Важное следствие: Metadata Menu хранит в поле **ссылку на сам медиафайл**, а не на объект-обёртку.

### Fileclass

Fileclass в экосистеме Obsidian — это механизм описания схемы заметки, который Metadata Menu использует
как источник определений полей («a fileClass … the field definition will be applied to the files mapped
with this fileClass»). Типизированные контролы и галереи даёт именно Metadata Menu. Поэтому в качестве
технического ориентира принимаем Metadata Menu, а Fileclass остаётся референсом по способу хранения
определений полей (карточки интеграций создаются на шаге 8).

## Проблема

1. Что хранится в значении свойства типа `media_reference`: ссылка на объект `media`, ссылка на файл
   вложения или допустимы оба варианта?
2. Какие настройки нужны типу значения, чтобы обеспечить фильтрацию и миниатюры?
3. Как тип значения соотносится с `cardinality` (нужен ли отдельный «мульти»-вариант)?

## Рассмотренные варианты

### По цели ссылки

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| A | Только объект `media` | Всегда есть роль, описание, вид медиа; один механизм | Для каждой картинки нужна заметка-обёртка — тяжело для массовых вложений |
| B | Только файл вложения (как в Metadata Menu) | Просто, без лишней сущности | Нет места для роли и описания; теряется смысл `media` как типа |
| **C** | **Настраивается в определении свойства**: `objects`, `files` или `both` | Каждый случай получает подходящий механизм; обложка с ролью — через объект, иллюстрация в тексте — напрямую файлом | Валидация должна различать два вида цели; правило сложнее |

### По отдельному типу для множественных значений

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| A | Ввести `multi_media_reference` по образцу Metadata Menu | Совпадает с ориентиром | Дублирует механизм: множественность у нас уже задаёт `cardinality` (ADR-006) |
| **B** | Один тип `media_reference`, множественность через `cardinality: 0..N` | Согласовано с решением об отмене типа «Список»; набор типов значений остаётся закрытым из семи | Отличие от Metadata Menu — но оно осознанное |

## Решение

**Приняты вариант C** (цель ссылки настраивается) **и вариант B** (один тип значения, множественность
через `cardinality`).

### Нормативная часть 1. Тип значения `media_reference`

Тип значения `media_reference` — это **ссылка на медиа**, которая в интерфейсе открывается
специализированным контролом с фильтрацией и миниатюрами.

| Параметр | Значение |
|---|---|
| Множественность | Задаётся **только** полем `cardinality` свойства. Отдельного «мульти»-типа нет |
| Цель ссылки | Настраивается полем `media_target` определения свойства |
| Контрол | Галерея карточек с миниатюрами или список — настраивается |
| Хранение | Тот же формат, что у `object_reference` (wikilink) или путь к файлу — в зависимости от `media_target` |

### Нормативная часть 2. Поля определения свойства типа `media_reference`

Добавляются к стандартному набору полей свойства (см. [[../metamodel/04-attributes]] §4).

| `key` | Подпись | Тип значения | `cardinality` | Обязательность | Допустимые значения |
|---|---|---|---|---|---|
| `media_target` | Цель ссылки | enum | `1` | да | `object` (только объекты `media`), `file` (только файлы вложений), `both` |
| `media_kinds` | Допустимые виды медиа | enum-список | `0..N` | нет | Подмножество `image`, `audio`, `video`, `document`, `other`. Пусто = все |
| `media_folders` | Папки для поиска | `text`-список | `0..N` | нет | Пути в хранилище. Пусто = всё хранилище |
| `media_extensions` | Допустимые расширения | `text`-список | `0..N` | нет | Например `jpg`, `png`, `webp`. Применяется при `media_target: file` или `both` |
| `media_display` | Способ показа | enum | `1` | нет, по умолчанию `gallery` | `gallery` (карточки с миниатюрами), `list` (список) |
| `media_thumbnail_size` | Размер миниатюры | enum | `1` | нет, по умолчанию `medium` | `small`, `medium`, `large` |
| `media_roles` | Допустимые роли | enum-список | `0..N` | нет | Подмножество ролей из ADR-006. Применяется при `media_target: object` или `both`. Пусто = все |

### Нормативная часть 3. Примеры определений

**Обложка — одна, только объекты `media` с ролью `cover`:**

```yaml
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D2F0
type: property
title: Cover
key: cover
label: Обложка
value_type: media_reference
media_target: object
media_kinds: [image]
media_roles: [cover]
media_display: gallery
media_thumbnail_size: medium
cardinality: 0..1
required: false
definition: Обложка издания. Выбирается из объектов типа «Медиа» с ролью «обложка».
---
```

**Иллюстрации — много, напрямую файлы из папки вложений:**

```yaml
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D2F1
type: property
title: Illustrations
key: illustrations
label: Иллюстрации
value_type: media_reference
media_target: file
media_kinds: [image]
media_folders: [attachments/illustrations]
media_extensions: [jpg, png, webp]
media_display: gallery
media_thumbnail_size: small
cardinality: 0..N
required: false
---
```

**Фрагменты интервью — и обёртки, и файлы сразу:**

```yaml
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D2F2
type: property
title: Interview fragments
key: interview_fragments
label: Фрагменты интервью
value_type: media_reference
media_target: both
media_kinds: [audio, video]
media_display: list
cardinality: 0..N
required: false
---
```

### Нормативная часть 4. Поведение контрола

| Элемент поведения | Норма |
|---|---|
| Источник кандидатов | Хранилище Obsidian: файлы вложений и объекты типа `media` — согласно `media_target` |
| Фильтрация | По `media_kinds`, `media_folders`, `media_extensions`, `media_roles` — все условия применяются одновременно |
| Поиск текстом | По `title` и `aliases` объекта `media`, по имени файла |
| Миниатюра | Формируется через `app.vault.getResourcePath(file)` — **публичный API Obsidian**. Для объекта `media` берётся файл из его поля `file` |
| Резервное поведение | Если файл недоступен или не является изображением — показывается значок вида медиа и имя, а не пустое место |
| Не-изображения | Для `audio`, `video`, `document` вместо миниатюры показывается значок вида медиа и длительность, если она известна |
| Запись значения | При `media_target: object` — каноническая ссылка `[[MEDIA-….md\|title]]`; при `file` — путь или wikilink на файл вложения; при `both` — то, что выбрано |
| Где работает | В **нашей** модалке редактирования свойств (ADR-003, §18.4 v1.1). В стандартном автодополнении Obsidian миниатюры **не** появляются — это требует патча `EditorSuggest`, то есть недокументированных механизмов |

### Нормативная часть 5. Правила валидации

| ID правила | Формулировка | Уровень |
|---|---|---|
| `value.media.target_kind` | Значение соответствует `media_target`: объект `media`, файл вложения или и то и другое | error |
| `value.media.kind_allowed` | Вид медиа цели входит в `media_kinds`, если список задан | error |
| `value.media.role_allowed` | Роль объекта `media` входит в `media_roles`, если список задан | warning |
| `value.media.in_folders` | Файл находится в одной из папок `media_folders`, если список задан | warning |
| `value.media.extension_allowed` | Расширение файла входит в `media_extensions`, если список задан | error |
| `value.media.file_exists` | Файл существует в хранилище | error |
| `property.media.settings_required` | У свойства типа `media_reference` заполнено поле `media_target` | error |
| `property.media.settings_consistent` | `media_roles` задано только если `media_target` равен `object` или `both`; `media_extensions` — только если `file` или `both` | warning |

### Нормативная часть 6. Соотношение с типом объекта `media`

| | Тип **объекта** `media` | Тип **значения** `media_reference` |
|---|---|---|
| Что это | Запись в базе, представляющая файл и его семантику | Объявление того, какого рода данные хранятся в поле и каким контролом вводятся |
| Где живёт | Заметка `MEDIA-{ULID}.md` | Определение свойства (`type: property`) |
| Поля | `file`, `media_kind`, `role`, `description` | `media_target`, `media_kinds`, `media_folders`, `media_extensions`, `media_display`, `media_thumbnail_size`, `media_roles` |
| Когда нужен | Когда у файла есть смысл за пределами самого файла: роль, описание, использование несколькими объектами | Когда поле объекта должно содержать медиа |

**Связь:** свойство типа `media_reference` с `media_target: object` или `both` ссылается на объекты `media`.
С `media_target: file` — напрямую на файлы вложений, и объект `media` при этом не создаётся.

### Нормативная часть 7. Что в MVP, а что отложено

| Возможность | Статус |
|---|---|
| Определение свойства типа `media_reference` со всеми семью настройками | **MVP** (схема и валидация) |
| Контрол-галерея с миниатюрами в нашей модалке | **MVP** |
| Фильтрация по виду медиа и папкам | **MVP** |
| Фильтрация по роли | **MVP** |
| Режим списка (`media_display: list`) | **MVP** |
| Длительность для аудио и видео в контроле | этап 2 |
| Автоматическое создание объекта `media` при выборе файла (`wrap-on-select`) | этап 2 |
| Механизм контекстного разрешения обёрток (v1.1 §10) | этап 2 |
| Миниатюры в стандартном автодополнении ссылок Obsidian | **отложено**, требует недокументированных механизмов |
| Загрузка медиа из внешних источников | **вне области**: проект работает офлайн |

## Обоснование

1. **Требование пользователя выполнено буквально:** тип свойства фильтрует и обёртки, и сами изображения,
   и показывает миниатюры при выборе.
2. **Ориентир проверен, а не взят на веру.** Metadata Menu действительно имеет тип поля `Media`
   с настройками папок, размера встраивания и режима «список или карточки». Наши настройки — надмножество:
   добавлены фильтрация по виду медиа и по роли, которых у ориентира нет.
3. **Вариант `both` закрывает реальный разрыв.** Metadata Menu хранит ссылку на файл, ваша модель — обёртку.
   Настраиваемая цель позволяет не выбирать между ними и использовать обёртку там, где нужна семантика
   (роль, описание, переиспользование), и прямую ссылку там, где она не нужна (иллюстрация в тексте).
4. **Отказ от `multi_media_reference` согласован с ADR-006.** Мы только что убрали тип «Список»,
   потому что множественность задаёт `cardinality`. Вводить отдельный «мульти»-тип для медиа означало бы
   вернуть ту же ошибку в одном частном случае.
5. **Миниатюры через публичный API.** `app.vault.getResourcePath()` — документированный способ получить
   адрес ресурса. Никакой DOM-подмены и недокументированных механизмов, в отличие от сценария
   с Front Matter Title ([[../integrations/research-front-matter-title-stability]]).

## Последствия

### Положительные
- Тип значения `media_reference` перестал быть «просто ссылкой»: у него есть поведение и настройки.
- Один механизм покрывает обложки, иллюстрации, аудио и видео.
- Появилась ясная граница между типом объекта и типом значения — её раньше не было, что и вызвало
  разночтение.

### Отрицательные / чем платим
- Определение свойства усложнилось: добавилось семь полей, имеющих смысл только для `media_reference`.
- Валидация должна различать два вида цели ссылки.
- Расхождение с Metadata Menu в способе хранения: при `media_target: object` значение — ссылка на заметку,
  а не на файл. Обмен данными с этим плагином возможен только при `media_target: file`.

### Обязательные компенсирующие меры

| № | Мера |
|---|---|
| M1 | Поля `media_*` допускаются **только** у свойств с `value_type: media_reference`. Правило `property.media.settings_consistent` |
| M2 | Команда `create-property` при выборе типа значения `media_reference` показывает только относящиеся к нему поля |
| M3 | Значения по умолчанию: `media_target: object`, `media_display: gallery`, `media_thumbnail_size: medium`, остальные списки пустые |
| M4 | Миниатюры имеют резервное поведение: значок вида медиа + имя, а не пустое место |
| M5 | Карточка интеграции Metadata Menu создаётся на шаге 8: режим `media_target: file` документируется как совместимый |
| M6 | Производительность: при большом числе вложений список кандидатов строится по индексу, а не обходом хранилища (пункт 28 §13 v1.1) |

## Открытые следствия

1. **`media_target: both` остаётся в MVP.** Подтверждено пользователем 2026-10-22.
2. **Автоматическое создание обёртки при выборе файла** (`wrap-on-select`) — отложено на этап 2.
   Подтверждено пользователем.
3. **Обёртка будет уточняться пользователем.** Зафиксировано 2026-10-22: «при проектировании обёртки
   у меня будут уточнения и дополнения». Раздел «Нормативная часть 6» (соотношение типа объекта `media`
   и типа значения `media_reference`) и состав полей типа `media` считаются **предварительными**
   и будут пересмотрены отдельным ADR, когда пользователь внесёт дополнения. Следствие: карточку типа
   `media` не финализировать до этих уточнений.
4. **Порядок значений** для `cardinality: 0..N` (например, порядок иллюстраций) — решается на шаге 6
   вместе с локальным свойством `order` у отношений.
5. **Совместимость с Metadata Menu** — проверяется на шаге 8 при создании карточки интеграции.
