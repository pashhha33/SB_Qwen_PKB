# ADR-010. Хранение экземпляров связей

## Контекст

[[ADR-002-source-of-truth|ADR-002]] установил: определения метамодели — Markdown-заметки в хранилище,
а `.sb/` — только служебные данные плагина (кэш, журнал, резервные копии, настройки, черновики миграций).
Критерий был сформулирован так: «если у сущности есть `id`, `type`, `title` и на неё можно сослаться —
это объект метамодели, он живёт в Markdown».

[[ADR-009-relations-model|ADR-009]] сделал экземпляр связи (`relation`) полноценным объектом: у него есть
`id`, `type`, `title`, локальные свойства. Формально по критерию ADR-002 он должен быть Markdown-заметкой.

Идея пользователя (дословно):

> «А если загнать связи под капот, в скрытую папку, чтобы плагин знал о них, а сам Obsidian нет,
> это может разгрузить хранилище и не засорять граф»

Дополнительное условие, полученное там же: **собственного текста у связи нет** — основная информация
получается из контекста связи и из самого субъекта или объекта. Значит, заметочная природа связи
не используется: произвольный Markdown внутри связи не нужен.

Факты про Obsidian, на которые опирается решение:

- папки, имя которых начинается с точки, Obsidian **не индексирует**: они не видны в проводнике,
  в поиске, в графе и в обратных ссылках;
- Obsidian строит узел графа для **каждой** заметки хранилища;
- индексация заметок происходит при запуске и при каждом изменении файла.

## Проблема

Где и в каком формате хранить экземпляры связей, чтобы не засорять хранилище и граф, но не потерять
надёжность и скорость?

## Рассмотренные варианты

### Вариант A — Markdown-заметки в обычной папке (как следует из ADR-002)
- Плюсы: полная самоопределяемость; работают wikilink-и, поиск, граф и обратные ссылки Obsidian.
- Минусы: на 500 объектов при 20 связях каждый — 10 000 служебных заметок в проводнике, в поиске
  и в графе. Граф становится нечитаемым. Индексация замедляется.
- Последствия: ровно то, от чего пользователь хочет избавиться.

### Вариант B — Markdown-заметки в `.sb/relations/`
- Плюсы: Obsidian их не видит; заметочная природа сохранена.
- Минусы: тысячи мелких файлов; медленный обход и разбор; польза от Markdown не используется,
  потому что его никто не читает — ни человек, ни Obsidian.
- Последствия: худшее из двух миров — сложность Markdown без его преимуществ.

### Вариант C — JSON Lines в `.sb/relations/`
- Плюсы: компактно; одну связь можно перезаписать, не трогая остальные; чтение и индекс строятся
  за один проход; решён вопрос производительности на больших хранилищах; формат проверяется JSON Schema.
- Минусы: связь перестаёт быть заметкой; нужен собственный просмотр; ручная правка неудобна.
- Последствия: плагин становится единственным способом увидеть связи. Компенсируется блоком
  «Связан с этим объектом» (Р11 ADR-009) и собственным типизированным графом.

### Вариант D — гибрид
- Суть: `direct`-связи остаются в frontmatter объектов (видимые), `reified` — в `.sb/`.
- Плюсы: каждый механизм на своём месте; в графе Obsidian остаются только осмысленные рёбра.
- Минусы: две ветки кода чтения и записи.
- Замечание: фактически это и есть принятое решение, потому что `direct`-связи **уже** хранятся
  в frontmatter по Р1 ADR-009. Отличие варианта D от C — только в том, считать ли это отдельным решением.

## Решение

**Принят вариант C**, который одновременно является вариантом D: `direct`-связи живут в frontmatter
объектов, `reified`-связи — в `.sb/relations/` в формате JSON Lines.

Формулировка пользователя: «1. C» и «2. A, я думаю основную информацию можно получить из контекста связи,
и самого субъекта или объекта связи».

### Нормативная часть 1. Расположение

```text
Vault/
├── .sb/
│   ├── config.json
│   ├── relations/
│   │   ├── relations.jsonl      ← основной файл: по одной связи на строку
│   │   └── archive/             ← связи, затронутые удалением определения свойства
│   ├── cache/                   ← производные данные, пересоздаются с нуля
│   ├── logs/
│   ├── backups/
│   └── migrations/
├── Metamodel/                   ← определения, Markdown
└── Books/, People/, …           ← экземпляры объектов, Markdown
```

### Нормативная часть 2. Формат строки

Одна строка = одна связь. Никаких переносов строки внутри записи.

```json
{"id":"01J8Z6M4K2Q7V9X3N5B0C1D2G1","type":"relation","title":"Bulgakov authored The Master and Margarita","subject":"01J8Z6M4K2Q7V9X3N5B0C1D2F3","relation_type":"01J8Z6M4K2Q7V9X3N5B0C1D2G0","object":"01J8Z6M4K2Q7V9X3N5B0C1D2EF","origin_property":"01J8Z6M4K2Q7V9X3N5B0C1D2F0","role":"автор","order":1,"starts_on":"1928-01-01","ends_on":null,"description":null,"created_at":"2026-10-22T14:35","updated_at":"2026-10-22T14:35"}
```

| Правило | Содержание |
|---|---|
| Ссылки | **Голые `id`**, а не wikilink-и. Основание: §15.3 черновика v1.1 — «скрытые JSON-файлы не следует строить на предположении, что они поддерживают `[[wikilinks]]`» |
| Пустые значения | `null` для необязательных полей, а не пропуск ключа — чтобы схема была предсказуемой |
| Даты | Тот же формат, что и в Markdown-объектах: `YYYY-MM-DD`, `YYYY-MM-DDTHH:mm`, локальное время |
| Кодировка | UTF-8, без BOM |
| Конец строки | `\n` (LF) |
| Порядок строк | Не значим. Порядок связей внутри одного свойства задаётся полем `order` |
| Схема | Формат строки описан JSON Schema: `schema/relation.schema.json` |

### Нормативная часть 3. Уточнение критерия ADR-002

Критерий «если на сущность можно сослаться как на объект — она в Markdown» **уточняется**:

| Что | Где | Формат |
|---|---|---|
| Определения метамодели (типы объектов, свойства, типы свойств, типы отношений, таксономии, фасеты, категории, представления, автоматизации) | `Metamodel/**` | Markdown + YAML |
| Экземпляры предметных объектов | обычные папки | Markdown + YAML |
| **Экземпляры связей** | `.sb/relations/` | **JSON Lines** |
| Кэш, журнал, резервные копии, настройки, черновики миграций | `.sb/` | JSON |

**Новая формулировка критерия:** в Markdown живёт то, с чем **работает человек** — читает, редактирует,
на что ссылается. В `.sb/` живёт то, с чем **работает только плагин**. Экземпляр связи — структурный
факт, а не документ; у него нет собственного текста (Р9 ADR-009), на него не ссылаются wikilink-ом,
его не ищут поиском Obsidian.

Принцип самоопределяемости при этом **не нарушается**: тип `relation` остаётся объектом метамодели
в Markdown, и его определение описывает структуру экземпляра. В JSON уезжают только экземпляры.

### Нормативная часть 4. Статус данных

> [!danger] `.sb/relations/` — основные данные, не производные
> В отличие от `.sb/cache/`, который пересоздаётся из заметок, хранилище связей **невозможно
> восстановить из Markdown-файлов**. Его потеря — потеря данных. Отсюда меры M1–M3.

### Нормативная часть 5. Обязательные меры

| № | Мера |
|---|---|
| M1 | **Резервная копия** `.sb/relations/` перед любой массовой операцией: миграцией, удалением объекта, удалением определения свойства, пакетным изменением связей |
| M2 | **Плагин — единственный автор.** Ручная правка технически возможна, но не поддерживается. При обнаружении внешнего изменения файл перечитывается и проверяется **целиком** до применения |
| M3 | **Атомарная запись:** запись идёт во временный файл, затем переименование. Повреждённый файл не должен остаться на месте основного |
| M4 | **Повреждённая строка не применяется.** Плагин сообщает номер строки и причину, продолжает работать с остальными записями и с последней корректной резервной копией |
| M5 | **Собственный просмотр обязателен:** блок «Связан с этим объектом» в форме объекта (Р11 ADR-009) и команда «показать связи объекта». Это единственный способ увидеть связи человеку |
| M6 | **Собственный типизированный граф** — представление, в котором у рёбер есть название типа и фильтр по типу. Компенсирует потерю графа Obsidian и превосходит его по возможностям |
| M7 | **Команда экспорта связей в Markdown** — этап 2. Страховка и путь отмены решения: если когда-нибудь понадобится вернуть связи в заметки, экспорт даст исходный материал |
| M8 | **Журналирование** значимых операций со связями в `.sb/logs/`: создание, изменение, удаление, массовые операции |

## Обоснование

1. **Главная цель достигнута:** граф Obsidian остаётся чистым. Узлы — только настоящие объекты,
   рёбра — только настоящие ссылки в frontmatter.
2. **Производительность.** Одна строка JSON разбирается быстрее, чем открытие и разбор заметки с
   frontmatter. На тысячах связей разница кратная. Это закрывает пункт 28 §13 v1.1.
3. **Решение стало возможным благодаря Р9 ADR-009.** Раз у связи нет собственного текста, ей не нужен
   Markdown. Если бы текст был, пришлось бы выбирать вариант B или D.
4. **Симметрия хранения получилась осмысленной:** определения в Markdown (их мало, их читает человек),
   экземпляры объектов в Markdown (их читает человек), экземпляры связей в `.sb/` (их читает только плагин).
5. **Отличие от Metadata Menu и Fileclass не мешает.** Оба плагина хранят определения полей в своих
   структурах; мы храним определения в Markdown, а экземпляры связей — в JSON Lines. Обмен данными
   на уровне объектов при этом сохраняется.

## Последствия

### Положительные
- Чистый граф, чистый проводник, чистый поиск Obsidian.
- Быстрая загрузка и индексация.
- Атомарность записи одной связи.
- Возможность построить типизированный граф с фильтром по типу связи — то, что граф Obsidian не умеет.

### Отрицательные / чем платим
- Связи невидимы для Obsidian: нет wikilink-ов на связь, нет её в поиске и в обратных ссылках.
- Плагин становится единственным способом увидеть связи. Если плагин отключён, связи «исчезают» из поля зрения,
  хотя данные на месте.
- `.sb/relations/` — основные данные в скрытой папке: их легко потерять при небрежном копировании хранилища.
- Ручная правка JSON неудобна и опасна.
- Отступление от буквы ADR-002: не всё, что имеет `id` и `type`, живёт в Markdown.

### Компенсирующие меры
M1–M8 в нормативной части 5. Дополнительно:

| № | Мера |
|---|---|
| M9 | В `README.md` хранилища и в руководстве пользователя явно написано: **папка `.sb/` содержит основные данные и подлежит резервному копированию вместе с заметками** |
| M10 | При отключении плагина связи остаются в файле и применяются при повторном включении; никаких данных не теряется |
| M11 | Настройка плагина «показывать связи в графе Obsidian» — этап 2: при желании можно генерировать видимые заметки-представления для отдельных типов связей |

## Влияние на метамодель

| Что меняется | Было | Стало | Ломающее изменение? | Нужна миграция? |
|---|---|---|---|---|
| Место хранения экземпляров связей | Markdown-заметки (следовало из ADR-002) | `.sb/relations/relations.jsonl` | **да** относительно ADR-002 | Да; данных нет |
| Формат экземпляра связи | YAML frontmatter | строка JSON | **да** | То же |
| Ссылки внутри связи | wikilink-и | голые `id` | **да** | То же |
| Критерий «что живёт в Markdown» | «есть `id`, `type`, `title`» | «с этим работает человек» | уточнение | нет |
| Назначение `.sb/` | только служебные данные | служебные данные **+ основные данные связей** | **да** | нет |

## Открытые следствия

1. **JSON Schema для строки связи** — `schema/relation.schema.json`, создаётся на шаге 9.
2. **Индекс связей в памяти** — структура и способ обновления: шаг 8 и Фаза 5.
3. **Разбиение на несколько файлов.** При очень большом числе связей один `relations.jsonl` может стать
   неудобным. Предлагаемое правило на будущее: разбиение по типу отношения или по году создания.
   В MVP — один файл.
4. **Экспорт в Markdown** (M7) — формат и команда: этап 2.
5. **Синхронизация между устройствами.** Если пользователь синхронизирует хранилище, `.sb/` попадёт
   в синхронизацию. Конфликты в JSON Lines разрешаются сложнее, чем в Markdown. Риск зафиксирован;
   мера — журнал и резервные копии. Для офлайн-работы на одном устройстве проблемы нет.
