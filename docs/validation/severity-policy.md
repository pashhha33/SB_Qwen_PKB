# Политика уровней сообщений

> [!info] Назначение документа
> Определяет, чем `error` отличается от `warning` и `info`, что плагин делает в каждом случае
> и как это показывает пользователю. Реестр самих правил — [[rules]].

## 1. Три уровня

| Уровень | Что значит | Блокирует запись? | Как показываем | Пример |
|---|---|---|---|---|
| `error` | Данные неверные: нарушено обязательное требование метамодели | **Да**, если запись идёт через наш интерфейс | Красная отметка + текст | «У проекта не заполнен статус» |
| `warning` | Данные допустимы, но подозрительны: вероятна опечатка или незавершённая работа | Нет | Жёлтая отметка | «Псевдоним не совпадает с названием» |
| `info` | Подсказка, не проблема | Нет | Серая отметка, можно скрыть | «Период не завершён — это нормально» |

> [!warning] Принцип
> Уровень `error` присваивается **только** тому, что действительно ломает смысл данных.
> Слишком много ошибок — и пользователь перестаёт их читать. Сейчас в реестре 72 `error`,
> 12 `warning` и 3 `info` из 87 правил. Доля ошибок высокая, потому что большинство правил —
> форматные и ссылочные; при необходимости часть из них будет переведена в `warning` на Фазе 5
> по результатам реальной эксплуатации.

## 2. Поведение плагина по уровням

### 2.1. Запись через наш интерфейс (модалка свойств, команды создания)

| Уровень | Поведение |
|---|---|
| `error` | Запись **блокируется**. Поле подсвечено, сообщение рядом с ним, кнопка сохранения неактивна или требует явного подтверждения «сохранить с ошибкой» |
| `warning` | Запись разрешена. Сообщение показано рядом с полем, но не мешает |
| `info` | Не показывается при вводе, видно только в панели диагностик |

### 2.2. Изменение через стандартную панель свойств Obsidian или вручную в файле

| Уровень | Поведение |
|---|---|
| `error` | Значение **не переписывается и не удаляется**. Плагин фиксирует диагностику и показывает её через статус объекта, уведомление или команду проверки |
| `warning` | То же, но без срочности |
| `info` | Фиксируется, показывается только в панели диагностик |

> [!important] Главный принцип, унаследованный из спецификации v1.0 §19
> **Система не должна молча переписывать неправильные данные.** Плагин сообщает о проблеме и предлагает
> исправление; автоматическое исправление допустимо только в явно подтверждённой пользователем операции.

### 2.3. Исключение: три случая автоматического исправления

Автоматическое действие допустимо **только** там, где оно не меняет смысл данных и всегда сообщается:

| Случай | Действие | Как сообщаем |
|---|---|---|
| Отсутствуют `created_at` / `updated_at` в заметке, созданной вне плагина | Дописываем при первом сохранении через команду плагина | `warning`: «Даты создания и изменения добавлены» |
| `aliases[0]` не совпадает с `title` | Предлагаем восстановить, не делаем молча | `warning` с кнопкой действия |
| Имя файла не совпадает с `id` | Чиним **имя файла по `id`**, никогда наоборот | `warning`: «Имя файла приведено в соответствие с идентификатором» |

## 3. Шесть уровней контроля целостности

Определения из ADR-011 часть 6 (закрывают неясность U-08 из спецификации v1.0 §19).

| Уровень | Название | Что проверяет | Когда запускается | Можно отключить |
|---|---|---|---|---|
| 1 | Предварительная | Данные, вводимые прямо сейчас, до записи | В модалке при вводе | Нет |
| 2 | Техническая | Формат и идентичность: ULID, имя файла, кодировка, формат даты, наличие системных атрибутов | При чтении объекта и при записи | Нет |
| 3 | Структурная | Ссылки и связи: существование цели, допустимый тип цели, кардинальность, уникальность, отсутствие циклов | При чтении, при изменении, по команде | Нет |
| 4 | Семантическая | Соответствие правилам метамодели: обязательность, перечисления, согласованность наследования, `lifecycle` | При изменении и по команде | Частично: можно отключить отдельные правила в настройках |
| 5 | Проверка представлений | Что представление можно построить: целевые типы существуют, свойства объявлены, механизм доступен | При открытии представления | Нет, но запускается лениво |
| 6 | Постпроверка | Состояние после записи: объект сохранился корректно, индекс обновлён, каскадные действия выполнены | После записи | Нет |

### Правила запуска

- Уровни 1 и 6 — всегда, отключить нельзя.
- Уровни 2–4 — **локально** при изменении одного объекта и **полностью** по команде `validate-vault`.
  Локальная проверка не должна без необходимости перепроверять всё хранилище (§18.5 v1.1).
- Уровень 5 — лениво, при открытии представления.
- Результат любой проверки — список **диагностик** (раздел 4).

### Соответствие результату из спецификации v1.0 §19

Спецификация задавала три исхода проверки: `OK`, `⚠ предупреждение`, `❌ ошибка`. Наша модель их сохраняет
и добавляет четвёртый:

| Исход в спецификации | Наш уровень |
|---|---|
| `OK` | диагностик нет |
| `⚠ предупреждение` | `warning` и `info` |
| `❌ ошибка` | `error` |
| — | `info` как отдельный, скрываемый уровень |

## 4. Формат диагностики

Каждая диагностика — структура, а не текст. Основание — §18.3 черновика v1.1.

| Поле | Что содержит | Пример |
|---|---|---|
| `rule_id` | Идентификатор правила из [[rules]] | `object.title.required` |
| `severity` | `error` / `warning` / `info` | `error` |
| `level` | Уровень контроля целостности (1–6) | `2` |
| `object_id` | Идентификатор объекта | `01J8Z6M4K2Q7V9X3N5B0C1D2K0` |
| `object_path` | Путь к файлу, если объект — заметка | `Books/BOOK-01J8….md` |
| `property_key` | Ключ поля, если проблема в поле | `title` |
| `actual_value` | Фактическое значение | `""` |
| `message` | Готовое сообщение на русском | «У книги не заполнено название» |
| `hint` | Что сделать | «Заполните поле „Название“» |
| `fix_available` | Есть ли автоматическое исправление | `false` |
| `fix_description` | Что сделает исправление | — |

### Правила формирования сообщений

- М1. Сообщение — на русском, с **подписью** поля (`label`), а не с техническим ключом.
  Не «поле `title` пусто», а «У книги не заполнено название».
- М2. Если известны допустимые значения — они перечисляются в сообщении.
- М3. Сообщение констатирует факт и не обвиняет пользователя.
- М4. На одно нарушение — одна диагностика. Не плодить три записи об одной причине.
- М5. Если причина одна, а следствий много (например, удалён объект, на который ведут десять ссылок),
  показывается одна диагностика с числом затронутых мест.

### Примеры сообщений

| Нарушение | Сообщение |
|---|---|
| `object.title.required` | «У книги не заполнено название» |
| `value.allowed_values` | «Статус проекта может быть только одним из: идея, в работе, приостановлен, завершён, отменён» |
| `relation.cardinality.subject_to_object` | «У проекта должен быть ровно один владелец, сейчас указано два» |
| `value.reference.target_type` | «Владелец проекта должен быть человеком, а указана организация» |
| `date.partial.no_gap` | «День указан, но месяц неизвестен. Неизвестная часть даты должна идти в конце» |
| `object.id.filename_match` | «Имя файла не совпадает с идентификатором. Предложить исправить имя файла?» |

## 5. Где пользователь видит диагностики

| Место | Что показывает | Статус |
|---|---|---|
| Модалка редактирования свойств | Сообщение рядом с полем, до сохранения | MVP |
| Панель сущностей (`show-object-panel`) | Число проблем у каждого объекта, фильтр по уровню | MVP |
| Статус объекта в строке состояния Obsidian | Значок и число проблем текущего файла | MVP |
| Команда `validate-object` | Список диагностик текущего объекта | MVP |
| Команда `validate-vault` | Список диагностик всего хранилища, группировка по типу и правилу | MVP |
| Уведомление при сохранении | Краткое сообщение, если появились новые `error` | MVP |
| Представления (таблицы, карточки) | Значок проблемы в ячейке или на карточке | этап 2 |

## 6. Настройки

| Настройка | Значения | По умолчанию |
|---|---|---|
| Показывать `info` в панели диагностик | да / нет | нет |
| Проверять всё хранилище при запуске плагина | да / нет | нет |
| Уведомлять о новых `error` после сохранения | да / нет | да |
| Отключённые правила | список идентификаторов | пусто |
| Блокировать сохранение при `error` в модалке | да / нет | да |
