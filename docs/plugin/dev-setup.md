# Настройка dev-связки плагина с хранилищем Obsidian

> [!info] Для чего этот документ
> Плагин разрабатывается в репозитории (`plugin/`), а запускается только внутри
> хранилища (vault) Obsidian. На время разработки их нужно «связать»: чтобы
> Obsidian видел файлы плагина, а пересборка кода попадала в хранилище автоматически.
> Документ написан для **Windows + PowerShell 5.1** (среда пользователя); команды
> даются построчно — `&&` в PowerShell 5.1 не работает (урок DL-232).

## 0. Как Obsidian находит плагины (1 минута теории)

Obsidian ищет сторонние плагины в служебной папке хранилища:

```text
<хранилище>\.obsidian\plugins\<id-плагина>\
    manifest.json   ← паспорт плагина (id, имя, версия)
    main.js         ← собранный код (бандл)
    styles.css      ← стили (у нас появится позже)
```

Папка `<id-плагина>` должна совпадать с `id` из `manifest.json` — у нас **`second-brain`**
(F5-1 = А, DL-243). Obsidian загружает плагин из этой папки; после изменения `main.js`
плагин нужно перезагрузить (см. §4).

**Аналогия.** Хранилище — квартира, `.obsidian/plugins/` — щиток с автоматами:
каждый плагин подключается своим автоматом-папкой; чтобы прибор заработал,
его нужно воткнуть в щиток и включить.

Предварительные требования (однократно):

```powershell
cd <путь-к-репозиторию>\plugin
npm install
```

Дальше — два варианта связки. **Рекомендуется вариант А (junction)**.

---

## Вариант А (рекомендуемый). Junction: папка плагина «прямо внутри» хранилища

**Junction** (**термин**) — «ссылка-Shortcut на уровне файловой системы»: папка
в хранилище, которая на самом деле является окном в папку `plugin/` репозитория.
Файлы физически лежат в репозитории, а Obsidian видит их у себя в `.obsidian\plugins\`.
В отличие от символических ссылок, junction **не требует прав администратора**
и работает, даже если репозиторий и хранилище на разных дисках.

**Аналогия.** Зеркало-портал в шкафу: вещи лежат в кладовке (репозиторий),
а дверь в комнату (хранилище) открывается прямо в кладовую.

### А1. Создать junction (один раз)

Подставьте свои пути (кавычки обязательны — пути с пробелами и кириллицей):

```powershell
# Папка плагинов в хранилище (создаётся, если нет)
New-Item -ItemType Directory -Force -Path "C:\Users\Имя\МоеХранилище\.obsidian\plugins"

# Junction: <хранилище>\.obsidian\plugins\second-brain  →  <репозиторий>\plugin
New-Item -ItemType Junction -Path "C:\Users\Имя\МоеХранилище\.obsidian\plugins\second-brain" -Target "D:\Проекты\SB_Qwen_PKB\plugin"
```

Проверка:

```powershell
Get-Item "C:\Users\Имя\МоеХранилище\.obsidian\plugins\second-brain" | Select-Object LinkType, Target
```

Ожидание: `LinkType = Junction`, `Target` — путь к `plugin\` репозитория.

> [!warning] Если junction уже существует и указывает не туда
> Удалите и создайте заново:
> ```powershell
> (Get-Item "C:\Users\Имя\МоеХранилище\.obsidian\plugins\second-brain").Delete()
> ```
> Junction удаляется безопасно: содержимое репозитория не трогается
> (удаляется только «окно», не кладовка).

### А2. Собрать плагин

```powershell
cd D:\Проекты\SB_Qwen_PKB\plugin
npm run build
```

Ожидание: `[second-brain] сборка завершена → main.js`. Файл `main.js` появится
в `plugin/` — и через junction мгновенно станет виден Obsidian.

### А3. Включить плагин в Obsidian

1. Откройте хранилище в Obsidian.
2. `Настройки → Сторонние плагины` (Community plugins) → выключите
   **Безопасный режим** (Restricted mode), если он включён.
3. В списке «Установленные» появится **Second Brain** (если не появился —
   нажмите кнопку обновления списка ⟳ или перезапустите Obsidian).
4. Включите переключатель. Должно появиться уведомление:
   «Second Brain 0.1.0: плагин загружен (этап A1 — каркас)».

## Вариант Б. Без junction: сборка напрямую в хранилище (`SB_VAULT_PATH`)

Если junction не подходит (например, хранилище в облачной папке с ограничениями),
сборщик умеет писать `main.js` прямо в хранилище через переменную окружения.

```powershell
# 1. Задать путь к хранилищу (действует до закрытия окна PowerShell)
$env:SB_VAULT_PATH = "C:\Users\Имя\МоеХранилище"

# 2. Скопировать manifest.json и versions.json в хранилище (один раз;
#    скрипт сам создаст .obsidian\plugins\second-brain\)
cd D:\Проекты\SB_Qwen_PKB\plugin
npm run link:vault

# 3. Dev-сборка: main.js будет писаться сразу в хранилище
npm run dev
```

Минус варианта Б: `manifest.json`/`styles.css` при изменении нужно копировать
повторно (`npm run link:vault`), а переменную `$env:SB_VAULT_PATH` задавать
в каждом новом окне PowerShell.

## 4. Цикл разработки (как работать дальше)

```powershell
cd D:\Проекты\SB_Qwen_PKB\plugin
npm run dev
```

**`npm run dev`** (**термин**: watch-режим, «дежурная сборка») — esbuild следит
за файлами `src/` и при каждом сохранении пересобирает `main.js` за доли секунды.
Терминал не закрывайте — он «дежурит», пока вы разрабатываете.

После пересборки Obsidian нужно попросить перечитать плагин — три способа
по возрастанию удобства:

| Способ | Как | Когда удобен |
|---|---|---|
| Перезагрузить приложение | В Obsidian: `Ctrl+R` (или палитра `Ctrl+P` → «Reload app») | Всегда работает; самый простой |
| Выключить/включить плагин | `Настройки → Сторонние плагины → Second Brain` — тумблер туда-обратно | Когда меняли только код плагина |
| Плагин **Hot Reload** (сторонний, по желанию) | Community-плагин «Hot Reload» (pjkaufmann) сам перечитывает `main.js` после пересборки | Для быстрой итерации; **наша зависимость не создаёт** — ставится в хранилище пользователя добровольно |

Ошибки плагина смотрим в консоли разработчика: `Ctrl+Shift+I` → вкладка Console.
Наш лог: строки, начинающиеся с `[second-brain]`.

```powershell

```

И из корня репозитория (прогонщик примеров метамодели + проверка таблиц в документах —
оба обязаны остаться зелёными):


```powershell

```

(`check:docs` — защита от пустых строк внутри Markdown-таблиц, DL-262: разрыв ломает рендер
таблицы в Obsidian/GitHub; при находке скрипт печатает `file:line` — удалите пустую строку.)

## 6. Устранение неполадок

| Симптом | Причина | Лечение |
|---|---|---|
| Плагина нет в списке Obsidian | junction не создан / имя папки ≠ `second-brain` / безопасный режим включён | Проверьте §А1–А3: `Get-Item … | Select LinkType,Target`; имя папки ровно `second-brain`; выключите Restricted mode |
| `New-Item : … не имеет прав` | Попытка создать SymbolicLink вместо Junction | Используйте именно `-ItemType Junction` (права не нужны); `-ItemType SymbolicLink` требует прав администратора |
| Уведомление о загрузке не появилось, в консоли ошибка `main.js not found` | Не было сборки | `npm run build` (или запущенный `npm run dev`) |
| Изменения кода не видны после пересборки | Obsidian не перечитал бандл | `Ctrl+R` (см. §4); убедитесь, что `npm run dev` писал в тот же путь, куда смотрит хранилище (вариант Б: `$env:SB_VAULT_PATH` задана в ЭТОМ окне) |
| `npm install` падает с `Cannot read properties of null (reading 'edgesOut')` | Баг npm-arborist при резолве peer-зависимостей (встречен в песочнице на vitest@latest) | Ставьте пакеты по одному или используйте зафиксированные версии из `plugin/package-lock.json`: `npm ci` |
| Пути с пробелами/кириллицей ломают команды | Нет кавычек | Все пути — в двойных кавычках; внутри npm-скриптов пути уже экранированы кодом (урок DL-232) |
| Хранилище в OneDrive/облаке, junction «мигает» | Облачная синхронизация трогает `.obsidian` | Вариант Б (`SB_VAULT_PATH`) или локальная копия хранилища на время разработки |
| `npm ci` падает: `EPERM: operation not permitted, unlink …\@esbuild\win32-x64\esbuild.exe`; после этого `npm test` говорит «vitest не является внутренней или внешней командой» | Файл `esbuild.exe` заблокирован запущенным процессом (чаще всего — оставленный `npm run dev`/esbuild --watch в другом окне; реже — антивирус). `npm ci` успевает снести часть `node_modules` до ошибки, поэтому vitest исчезает | 1) Закройте окно с `npm run dev` (Ctrl+C) и Obsidian; если окно не найти: `Get-Process esbuild -ErrorAction SilentlyContinue \| Stop-Process -Force`. 2) `Remove-Item -Recurse -Force node_modules` (в `plugin\`; если не выходит — `cmd /c "rmdir /s /q node_modules"`, в крайнем случае перезагрузка). 3) `npm ci` заново → `npm test` |
| Notice/журнал показывает **старую версию** плагина (найдено 2026-10-25: журнал писал «версия 0.3.1» при коде 0.4.0 — функции новые, номер старый) | В папку плагина хранилища переносили только `main.js`, а `manifest.json` остался от прошлой версии; Obsidian берёт версию из манифеста, код — из `main.js` | Переносите **оба файла**: `main.js` + `manifest.json` (проще всего — `npm run link:vault` при заданной `SB_VAULT_PATH`, он копирует manifest/versions/styles/main.js автоматически); либо используйте вариант А (junction) — тогда файлы никогда не разойдутся. После замены — `Ctrl+R` |

## 7. Что уже есть и что появится дальше

- **Уже доступно (плагин 0.5.0 — этап A закрыт)**: команды в палитре `Ctrl+P` — «Создать
  тип объекта (create-object-type)», «Создать объект (create-object)», «Проверить объект
  (validate-object)», «Показать журнал плагина (show-log)» — окно журнала с фильтром по
  уровню, живым режимом и кнопкой «Скопировать», «Скопировать журнал в буфер обмена
  (copy-log)»; **вкладка настроек** «Second Brain»: выключатели журнала по уровням, лимит
  строк, режим подписей. Журнал — `.sb/logs/plugin-log.jsonl`, настройки —
  `.sb/settings.json` (ADR-002).
- **Бутстрап (0.4.0, DL-257)**: при первой загрузке плагин сам создаёт
  `Metamodel/ObjectTypes/` с 7 системными типами (OBJECT_TYPE-заметки с фиксированными
  ULID); повторная загрузка ничего не дублирует и не перезаписывает ваши правки.
  Notice загрузки показывает «типов в реестре: 7».
- **Front Matter Title (0.5.0, DL-258)**: при загрузке плагин проверяет наличие
  одноимённого плагина (уровень 2 читаемости, ADR-001). Не установлен/выключен — один раз
  предложит его поставить (повторно не пристаёт: флаг в `.sb/settings.json`); установлен —
  молча работает рядом. Без него всё работает: показываются имена файлов.
- **Генерация типов (D2, 0.5.0)**: после правки схем в `schema/**` выполните в `plugin/`
  `npm run generate:types` и закоммитьте обновлённый `src/generated/`; тест свежести
  в `npm test` поймает забытую перегенерацию.
- **Дальше — этап B (B1 «схема и свойства»)**: schema-engine, условные свойства,
  модалки на Svelte, команда «установить основные типы» (предметная библиотека: `book`,
  `person`, …).
