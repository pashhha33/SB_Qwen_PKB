# Границы MVP

> [!success] Статус: **принято пользователем 2026-10-22** (ответ «A», DL-162; серые зоны — DL-163)
> Документ собран из уже принятых решений (ADR-001…ADR-011, DL-001…DL-167). Его задача —
> собрать разрозненные «MVP / этап 2 / вне области» в **один список**, чтобы границу можно было
> увидеть целиком и оспорить одним решением, а не по частям.

## 1. Что значит MVP

**MVP** (**термин**, минимально жизнеспособный продукт) — версия плагина, которой уже можно
пользоваться каждый день: вести книги, главы, людей и изображения, — но в которой нет ничего,
без чего можно обойтись.

**Бытовая аналогия.** Первая версия велосипеда: рама, колёса, педали, тормоз. Без багажника,
крыльев и фары — они появятся позже, и для их установки не придётся переделывать раму.

**Проверка границы — три вопроса:**

| Вопрос | Если «нет» |
|---|---|
| Без этого основной сценарий пользователя ломается? | Переносим на этап 2 |
| Это требует недокументированных механизмов Obsidian? | Не делаем совсем (или делаем мягко отказывающим адаптером) |
| Это требует внешних сервисов или сети? | Вне области: проект локальный и офлайн |

## 2. Входит в MVP

### 2.1. Типы объектов — 15 (ядро)

| Группа | Типы |
|---|---|
| Системные (метамодель) | `object_type`, `property`, `relation_type`, `relation`, `taxonomy`, `facet`, `category` |
| Предметные | `book`, `chapter`, `person`, `project`, `knowledge`, `media` |
| Абстрактные родители | `work`, `activity` (экземпляров не имеют, только наследование) |

Из 15 типов **полные карточки** есть у 5 (`book`, `person`, `chapter`, `media`, `project`);
`knowledge`, `work`, `activity` и 7 системных описываются сокращённо (мера M1 ADR-006).

### 2.2. Типы отношений — 4

| Тип | `link_mode` | Особенность |
|---|---|---|
| `authorship` | `direct` | книга ↔ человек |
| `ownership` | `direct` | проект ↔ владелец |
| `contains` | `reified` | произведение ↔ глава; `part_of` — его вычисляемая обратная сторона |
| `related_to` | `symmetric` | «связано с», `uniqueness_rule: pair` |

### 2.3. Команды плагина — 18

| Команда | Что делает | Этап |
|---|---|---|
| `create-object-type` | Создаёт тип объекта | A |
| `create-object` | Создаёт экземпляр объекта | A |

| `create-relation-type` | Создаёт тип отношения | C |
| `create-relation` | Создаёт свободно стоящую связь | C |
| `show-object-relations` | Все связи объекта, включая свободно стоящие | C |
| `assign-category` | Назначает категорию фасета | B |
| `validate-object` | Проверяет один объект | A |
| `validate-vault` | Проверяет всё хранилище (уровни 2–4, 6) | B |
| `show-object-panel` | Панель объекта: свойства и связи | D |

> DL-177…DL-188). Итог вырос **15 → 18 команд**; входят в этапы B и D.

### 2.4. Механизмы

| Механизм | Что входит |
|---|---|
| Значения | 7 типов значений; частичные даты через `00`; локальное время без смещения |
| Отображение | `LabelResolver` (`view`/`source`); редактируемый шаблон вывода даты (17 токенов, 5 пресетов); `display.renderer` = `plain` / `stars` / `progress` |
| Условные свойства | `applies_when` с операциями `equals`, `in_category`, `includes_any`; правила М1–М7 |
| Классификация | `taxonomy → facet → category`; свободные `tags` вне метамодели |
| Связи | `.sb/relations/relations.jsonl`, типизированный граф, обратная сторона вычисляется, каскады |
| Медиа | Инвариант И8, постпроцессор встраивания, кнопки у изображений, индекс, мастер, теневые свойства |
| Валидация | **167 правил** в 14 группах (A–N), 6 уровней контроля, формат диагностики из 11 полей, 4 разрешённых автоисправления |
| Перечисления | 26 перечислений, 24 закрыто, 2 предварительных |
| Представления | Bases (таблица, карточки, список глав, **канбан проектов**), панель объекта, галерея медиа, список свободных файлов, навигация по главам |
| Интеграции | **Bases** (генерация `.base` — карточка [[../integrations/obsidian-bases\|obsidian-bases]]), **Front Matter Title** (необязательный адаптер с мягким отказом — карточка [[../integrations/front-matter-title\|front-matter-title]]). **Templater** — сосуществование без зависимости (DL-190): тело заметки плагин строит сам |
| Ссылки и псевдонимы | Создание объекта из пустой ссылки (перехват `vault.on('create')`, кнопка в контроле свойства, команда); `title` = текст ссылки; контекст свойства и типа отношения; сбор `aliases` из отображаемого текста ссылок; поиск дублей. Норма — [[../metamodel/12-links-and-aliases\|раздел 12]] |

## 3. Не входит в MVP — с причиной

### 3.1. Вне области проекта (не будем никогда, пока не изменятся рамки)

| Не входит | Причина |
|---|---|
| Мобильная версия | Рамки проекта: не требуется |
| Внешние API, LLM, скачивание медиа из сети | Рамки проекта: локально и офлайн |
| Патчи недокументированных внутренностей Obsidian (`EditorSuggest`, чужой рендеринг) | ADR-003 + исследование Front Matter Title: такие плагины ломаются на обновлениях |
| Dataview, DataviewJS как механизм представлений и как зависимость | **Отклонено** (DL-191): сторонний язык запросов; реифицированные связи в `.sb/` Dataview не видит — его картина неполна. Свои запросы пользователя не запрещены, но не поддерживаются |
| Templater как зависимость плагина | Тело заметки строит сам плагин (инвариант И8, блок `sb-chapter-nav`, команды ADR-004). Сосуществование совместимо (DL-190); публичного API у Templater нет |
| Собственный слой подмены названий (спецификация v1.1 §17) | ADR-001: вынесен за границы MVP; читаемость решается инвариантом `aliases[0] == title` и необязательным адаптером |
| RDF / OWL, экспорт в онтологии | `11-rdf-extension.md` — направление расширения, не требование |

### 3.2. Этап 2 (нужно, но позже)

| Не входит | Почему не в MVP | Что уже готово заранее |
|---|---|---|
| Автоматические миграции данных | Данных ещё нет; цена ошибки нулевая, а цена реализации высокая | Формат записи миграции и журнал (`10-migration-rules.md`); образец — сужение `book_format` и обязательность `person.role` |
| Типы `organization`, `event`, `character`, `award`, `music_track`, `guide`, `article`, `web_page` | Нет экземпляров, на которых можно проверить состав полей | Записи в реестре типов со статусом `phase2` и применёнными тестами |
| Отношения `employment`, `depicts`, `derived_from`, `pseudonym_of`, `family`, `member_of`, `sourced_from`, `co_authorship`, `conflicts_with` | Требуют реификации с периодом и ролью, а это проверяется только на данных | Реестр типов отношений; `contains` как отработанный образец `reified` |
| Автоперенумерация глав (`sb-renumber-chapters`) | Опасная операция над данными; в MVP достаточно warning о разрыве | Правило `relation.order.no_gap` |
| Смена типа объекта (`sb-change-type`) | В MVP данных нет — потребность нулевая; механизм опасный (переименование файла, аудит свойств, связей и категорий) | Механизм описан и принят: [[../metamodel/07-hierarchy\|07-hierarchy]] §8 (id сохраняется, `vault.rename`, аудит без удаления, журнал; DL-210) |
| Длительность аудио и видео в контроле, плеер | Сценарий «смотрю/слушаю» не приоритетный | `media_kind: audio` / `video` в схеме |
| `wrap-on-select`: автообёртка файла при выборе | Требует согласия пользователя на создание объекта в чужом действии | Кнопка «Создать обёртку» делает то же явно |
| Экспорт связей в Markdown (`export-relations`) | Страховка, нужна когда данных станет много | Формат `.jsonl` прост и стабилен |
| Типизированный граф (`show-typed-graph`) | Собственная визуализация графа дорога | Блок «Связан с этим объектом» |
| Составные условия `applies_when` (`и` / `или`), цепочки | Усложняют объяснение пользователю; правила М3, М5 запрещают | Одна операция на свойство покрывает и книгу, и человека, и медиа |
| Тип свойства `identifier` (IMDb, ORCID, ISBN как структура) | Требует проверки форматов и своего контрола | Поля `links`, `isbn` как текст |
| Отношения вместо текстовых полей человека (`employer`, `doctoral_students`, родственники) | То же, что отношения этапа 2 | Текстовые поля объявлены так, чтобы перевод на `object_reference` был миграцией, а не переделкой |
| Миниатюры в **стандартном** автодополнении ссылок Obsidian | Требует патча `EditorSuggest` | Миниатюры в **нашей** модалке |
| Fileclass, Metadata Menu как зависимости; QuickAdd до этапа 2 | Каждый тянет свой формат данных и свои конфликты | Карточки интеграций созданы (шаг 8d): [[../integrations/fileclass\|fileclass]] и [[../integrations/metadata-menu\|metadata-menu]] — референсы; [[../integrations/quickadd\|quickadd]] — отложен (этап 2, сценарий «быстрый захват») |
| Нормализация всех ссылок хранилища (`sb-normalize-links`) | Молча переписывать текст во всех заметках нельзя (принцип спецификации v1.0 §19); в MVP правится только ссылка в той заметке, где её создали | Точечная нормализация при создании (§7.3 раздела 12) |
| Освежение псевдонимов ссылок после смены `title` (`sb-refresh-link-aliases`) | Требует обхода всех ссылок и согласия на правку текста | Инвариант И4 и `aliases[0]` дают читаемость без этого |
| Слияние дублей (`sb-merge-duplicates`) | Опасная операция над данными; в MVP достаточно поиска дублей до создания | Поиск по `title` + `aliases` (`.sb/cache/alias-index.json`) |
| Кнопка «Создать объект» у пустой ссылки в тексте (Т4) | Тот же механизм, что у кнопок медиа; по объёму не успевает в этап B | Команда `sb-create-from-link` и перехват клика покрывают сценарий |
| Контекст по заголовку раздела и по папке (К6, К7) | Требуют новых полей в объявлении свойства и настроек соответствия «папка → тип» | Жёсткий контекст К1, К2, К5 и мягкие К3, К4 уже работают |
| Публикация в Community plugins | Проект личный | Установка через BRAT |
| Выделенные команды `create-facet`, `create-category` | Создание экземпляров фасетов и категорий покрывает универсальная команда `create-object`: это обычные объекты метамодельных типов (самоопределяемость, ADR-004); выделенная обёртка — UX-сахар с подсказками полей | Команды описаны в ADR-004 и `01-classification` §7; **DL-218 (ответ «А»)** — реестр **18 команд не меняется**; `create-taxonomy` и `assign-category` остаются в MVP |

### 3.3. Серые зоны — требуют решения (шаг 8)

Первые три закрыты пользователем 2026-10-22 (ответ «A», DL-163):

| Вопрос | Решение |
|---|---|
| Перечисление `object_status` | **Не вводится**: дублирует `lifecycle` у определений и свободные `tags` у данных |
| `media_target: both` в MVP | **Остаётся**: удаление сломало бы определения свойств |
| Канбан и карта как представления | Канбан — **штатно через Bases** (`type: kanban` + `groupBy` + `groupOrder`); собственная карта **не делается** |

Четвёртая серая зона — **канбан проектов** — закрыта решением пользователя от 2026-10-22
(ответ «C», DL-176): канбан **остаётся в MVP**, а чтобы он не висел в воздухе, создана карточка
типа `project` со свойством `status` (перечисление `project_status`). Противоречие между этим
документом и `08-views.md` (представление В6) устранено: В6 — в MVP.

Остальные три переносятся на этап 2 — они не влияют на границу MVP:

| Вопрос | Где решаем | Предложение ассистента |
|---|---|---|
| `book.print` как отдельный формат | Этап 2, по экземплярам | Оставить в перечислении, но не плодить свойства |
| Франшиза и Галерея: подтипы `collection` или категории | Этап 2 | Категории фасета |
| `music_track` против `media` вида `audio` | Этап 2 | Трек наследует `work` и ссылается на `media` |

## 4. Как проверяем, что граница не поехала

| Признак «MVP расползается» | Что делаем |
|---|---|
| В этап добавили фичу, которой нет в этом документе | Правка документа + запись в decision log, а не молчаливое расширение |
| Фича требует недокументированного API | Выносим из MVP, фиксируем в §3.1 |
| Фича нужна «чтобы было не хуже, чем у Dataview» | Проверяем тремя вопросами из §1; обычно это этап 2 |
| Этап не заканчивается видимым результатом | Делим этап, а не расширяем его |

Контроль — [[readiness-checklist|чек-лист готовности]]: переход к Фазе 5 разрешён только при
100 % блоков A и B.
