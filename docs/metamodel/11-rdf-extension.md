# 11. RDF-расширение (направление, не требование)

> [!info] Статус документа
> Это **информационный раздел**: он фиксирует направление расширения и границы, чтобы будущее
> «породить базу с внешним миром» не пришлось изобретать с нуля. **Никаких обязательств для MVP
> и этапа 2 он не создаёт.** Модуль `rdf-exporter` остаётся в списке «не реализуем»
> (`09-modules.md` §6); `mvp-scope.md` §3.1: «RDF / OWL, экспорт в онтологии — направление
> расширения, не требование». Вопрос об объёме этого документа — **8f-4**.

## 1. Пять минут про RDF (пользователь RDF не знает — объясняем с нуля)

- **Граф знаний** (термин уже в глоссарии) — база как сеть: вещи — точки, отношения — линии.
- **Трипл** (**термин**) — минимальная единица RDF: «субъект — предикат — объект», одно
  предложение-факт: «Пушкин — автор — „Евгения Онегина“». *Аналогия:* строка в журнале учёта:
  кто / что сделал / с чем. Вся база RDF — это миллионы таких строк.
- **IRI** — глобально уникальное имя вещи (похоже на URL). *Аналогия:* не «Иванов» (имён много),
  а номер паспорта. У нас роль такого имени уже играет **ULID** (ADR-001).
- **RDF / OWL** (термины в глоссарии) — мировые стандарты записи таких фактов и строгих правил
  над ними («классы», «свойства», ограничения). OWL добавляет логику: «каждая книга — произведение»,
  «авторство связывает человека и произведение».
- **SKOS** (**термин**) — стандарт для словарей и рубрикаторов: схемы концептов, концепты,
  отношения «шире / уже / связано». *Аналогия:* библиотечная классификация, понятная всем
  библиотекам мира. Это готовый двойник нашей классификации (таксономия/фасет/категория).
- **RDF-star** (**термин**) — расширение RDF: «предложение про предложение» — факт можно
  аннотировать, не теряя его как факт. *Аналогия:* пометка на полях договора: «подписан доверенным
  лицом, действует с марта». Это готовый двойник наших **реифицированных связей** с локальными
  свойствами (`order`, `starts_on`, `role`).
- **Turtle** (**термин**) — человекочитаемый текстовый формат записи триплов (`.ttl`).
- **SPARQL** (**термин**) — язык запросов к RDF-графам (как SQL к таблицам).
- **JSON-LD** (термин в глоссарии) — мостик: JSON, который однозначно переводится в RDF.

## 2. Зачем нам это может понадобиться (и почему не сейчас)

| Сценарий | Что даёт | Есть ли потребность сейчас |
|---|---|---|
| Слияние с внешними графами (Wikidata, библиографические базы) | Поля `person` уже сверялись с Wikidata при проектировании (`research/person-role-properties.md`) — сопоставление свойств заложено | Нет: проект локальный и офлайн (рамки DL-002) |
| Публикация своей базы как открытых данных | Стандартный формат понимают чужие программы | Нет |
| Логический вывод (reasoners) | «Если глава — часть книги, а книга — произведение, то глава относится к произведению» | Нет: наши правила валидации покрывают потребности |
| Обмен с другим ПО | Импорт/экспорт без промежуточных форматов | Нет: экспорта нет даже в Markdown (этап 2, ADR-010 M7) |

**Вывод:** направление зафиксировано, триггеров нет — не реализуем. Критерии запуска (§5).

## 3. Сопоставление понятий (главная ценность документа)

Если экспорт когда-нибудь понадобится, вот готовая карта «наше → RDF»:

| Second Brain | RDF / OWL / SKOS | Комментарий |
|---|---|---|
| `object_type` | `owl:Class` (или `rdfs:Class`) | дерево типов → `rdfs:subClassOf` (раздел 07) |
| абстрактный тип | `owl:Class` + пометка «не создаётся» | в OWL нет прямого аналога И3 — выражается соглашением |
| `property` с типом значения | `owl:DatatypeProperty` | `cardinality` → ограничения OWL (min/max) |
| `property` типа `object_reference` / `media_reference` | `owl:ObjectProperty` | `target_types` → `rdfs:domain`/`range` |
| `relation_type` | `owl:ObjectProperty` (симметричная → `owl:SymmetricProperty`) | `related_to` — готовый `owl:SymmetricProperty` |
| экземпляр `relation` (реифицированная связь) | трипл + **RDF-star** аннотация (`order`, `starts_on`, `ends_on`, `role`) | альтернатива — классическая реификация RDF, но она громоздкая |
| `origin_property` | qualifier «по какому свойству» в RDF-star | — |
| экземпляр объекта | `owl:NamedIndividual` | — |
| `id` (ULID) | IRI: `urn:sb:ulid:{ULID}` (предложение) | ULID стабилен и не переиспользуется (И1) — IRI наследует это свойство |
| `type` | `rdf:type` | — |
| `title` | `rdfs:label` | — |
| `aliases` | `skos:altLabel` | инвариант И4: `aliases[0] == title` → предпочтительная метка = `skos:prefLabel` |
| `taxonomy` | `skos:ConceptScheme` | — |
| `facet` | `skos:ConceptScheme` (или `skos:Collection`) | независимость фасета (ADR-007) передаётся отсутствием обязательной схемы |
| `category` | `skos:Concept` | — |
| `parent` у категории | `skos:broader` | предки вычисляются — как у нас |
| назначение категории объекту | `dcterms:subject` | — |
| `tags` | `skos:keyword` (свободные метки) | вне метамодели — как у нас |
| `lifecycle: deprecated` + `superseded_by` | `owl:deprecated` + `owl:replacedBy` (по духу) | ADR-011 |
| даты (`YYYY-MM-DD`, локальное время) | `xsd:date` / `xsd:dateTime` | **осторожно:** ограничение G-04-1 (локальное время без смещения) при экспорте придётся оговаривать |
| частичные даты (`1928-00-00`) | `xsd:gYear` / интервалы EDTF | наш формат «00» нестандартен — при экспорте преобразуется в диапазон (норма уже есть: `06-time-and-intervals`) |

## 4. Жёсткие границы (нормативная часть раздела)

1. **Экспорт — производные данные**, как кэш: полностью восстанавливается из Markdown-заметок
   и `.sb/` одной командой; источником истины **не является** и быть не может (ADR-002).
2. **Источник истины не меняется**: определения и объекты остаются Markdown-заметками; RDF —
   только файл выгрузки (`export.rdf.ttl` или JSON-LD), восстанавливаемый одной командой.
3. **ULID → IRI — стабильное одностороннее отображение**; обратного импорта в MVP и этапе 2
   **нет**: импорт чужих графов — отдельная большая задача (дубли, согласование схем),
   за её пределами этого документа.
4. **Офлайн-рамки не нарушаются**: экспорт — в локальный файл; никакие внешние сервисы
   не вызываются (DL-002).
5. Пока `rdf-exporter` не реализован, никакие решения модели **не принимаются «под RDF»**:
   модель развивается по своим требованиям; сопоставление §3 поддерживается актуальным
   при изменениях схемы (стоимость — правка таблицы, не кода).

## 5. Критерии запуска (когда возвращаемся к этому направлению)

Любой из трёх — повод пересмотреть решение `rdf-exporter: no`:
1. появилась задача слить базу с внешним графом (Wikidata, Zotero-RDF, библиографические базы);
2. появилась задача публиковать данные наружу;
3. понадобился логический вывод, который не выражается нашими 166 правилами.

Порядок работ тогда: IRI-политика → Turtle-экспорт ядра (типы, объекты, `direct`-связи) →
SKOS для классификации → RDF-star для реифицированных связей → JSON-LD-вариант. Модуль
переезжает из «не реализуем» в реестр с этапом и тестами.
