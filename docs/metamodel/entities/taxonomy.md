# Taxonomy (Таксономия) — системный тип

> **Группа:** ядро, системные (метамодель) · **Префикс:** `TAXONOMY` · **`abstract`:** нет —
> экземпляры создаются (экземпляр — конкретная система классификации,
> «Классификация художественных произведений»)
> Карточка **сокращённая** (мера M1 ADR-006): состав полей задан `01-classification` §2.1,
> карточка систематизирует и ссылается, не дублируя.

## 1. Назначение

**Необязательная** группировка фасетов в согласованную систему классификации (ADR-007).
Задаёт область применения (`allowed_object_types`) и значения по умолчанию для настроек
входящих фасетов. Фасет может существовать без таксономии — это самый частый случай
(одно измерение классификации); таксономия нужна, когда несколько фасетов разделяют
область применения или их удобно показывать как единое целое.

**Бытовая аналогия** (согласована с глоссарием): таксономия — **шкаф**, фасет — ящик в нём
(или отдельно стоящая полка — независимый фасет), категория — папка в ящике.

## 2. Состав полей (норма — `01-classification` §2.1)

| Поле | Смысл |
|---|---|
| `label` | отображаемое название на русском (`0..1`, текст) — слой подписей ADR-003. Объявлен схемой `taxonomy.schema.json` (**B1.3-6 = А**, DL-278; пример `01-classification` §2.1 его уже содержал) |
| `facets` | список ссылок на `facet`; **обязательно**, минимум один (правило `taxonomy.facets.min_one`) |
| `allowed_object_types` | список ссылок на `object_type`; пусто = ограничений нет; **служит значением по умолчанию для входящих фасетов**; семантика потомков и абстрактных типов — `07-hierarchy` §5, §7 (DL-208/209) |
| `hierarchy_mode` | значение по умолчанию для фасетов (`strict` / `polyhierarchical` — перечисление §3.5 `05-enumerations`) |
| `assignment_cardinality` | значение по умолчанию для фасетов (`0..1`, `1`, `0..N`, `1..N`) |
| `root_requirement_min` / `root_requirement_max` | значения по умолчанию для фасетов; `null` в максимуме = без ограничения |

**Правило П8 (ADR-007):** категория не ссылается на таксономию напрямую — только через фасет
(правило `category.taxonomy_direct.forbidden`). Второго пути классификации нет.

## 3. Где живёт и как создаётся

Markdown-заметка в `Metamodel/**` (ADR-002). Создание и правка — **только командами**
(ADR-004, П1–П6): `create-taxonomy` (MVP, этап B) группирует **существующие** фасеты
и задаёт общие значения по умолчанию; автоматически создавать фасеты она перестала (DL-077).

## 4. Связи с другими типами метамодели

- `facet` — принадлежность таксономии хранится на фасете (`facet.taxonomy`, `0..1`);
  таксономия перечисляет входящие фасеты в `facets`;
- `object_type` — область применения через `allowed_object_types`;
- `category` — прямой связи **нет** (П8), только через фасет.

## 5. Валидация

Группа **E** реестра: `taxonomy.facets.min_one` (error), `assignment.type_allowed`
(error; при назначении категории проверяется область применения таксономии **или** фасета —
правило наследования `01-classification` §2.2). Новых правил карточка не добавляет.

## 6. Открытые вопросы

Нет. Расхождение состава команд классификации (`create-facet` / `create-category` описаны
в ADR-004 и `01-classification` §7, но отсутствуют в реестре 18 команд MVP) — **решено:
DL-218 принято (ответ «А», 2026-10-23)**: экземпляры фасетов и категорий создаёт
универсальная команда `create-object`, выделенные обёртки — этап 2 (`mvp-scope` §3.2);
реестр 18 команд не меняется.

## 7. Этап реализации и модуль

Этап **B**; модуль `classification-service` (`09-modules`).
