# Category (Категория) — системный тип

> **Группа:** ядро, системные (метамодель) · **Префикс:** `CATEGORY` (в коде сравнивать строки
> целиком: `CHARACTER` — другая строка с той же первой буквой, `02-entities` §6) ·
> **`abstract`:** нет — экземпляры создаются (экземпляр — конкретное значение справочника,
> «Научная фантастика», «Космическая опера»)
> Карточка **сокращённая** (мера M1 ADR-006): состав полей задан `01-classification` §2.3,
> карточка систематизирует и ссылается, не дублируя.

## 1. Назначение

Конкретное значение внутри **ровно одного** фасета. Объекты базы получают классификацию
через назначенные категории (системное поле `categories`), а не через прямые ссылки на
фасеты или таксономии. Категория — **открытый справочник**: пользователь пополняет его
без изменения метамодели (в отличие от закрытых перечислений `05-enumerations`, DL-104).

## 2. Состав полей (норма — `01-classification` §2.3)

| Поле | Смысл |
|---|---|
| `facet` | ссылка на `facet`; **обязательно, ровно один** (`category.facet.required`, `category.facet.single`) |
| `parent` | список ссылок на категории-**непосредственных** родителей того же фасета; корень — `parent: []`; вышестоящие предки вычисляются; искусственный объект «Корень» не создаётся |

В полиерархическом фасете (`hierarchy_mode: polyhierarchical`) родителей может быть несколько;
в строгом (`strict`) — не более одного (`category.parent.strict_mode`). Перенос категории
в другой фасет — **контролируемая операция**, потому что меняет смысл всех назначений.

## 3. Назначение объекту (норма — `01-classification` §2.4, `04-attributes` §2)

Системное поле `categories` — `object_reference` → `category`, `0..N`; заполняется
пользователем через команду `assign-category`. Фасет назначения вычисляется через категорию
и в объекте не хранится. Кардинальность и область применения проверяются по фасету
(`assignment.cardinality`, `assignment.type_allowed`).

**Граница с `tags`** (`01-classification` §3): метки свободны и не валидируются; прижившаяся
метка **повышается** до категории фасета; обратное движение выводит значение из справочника.

## 4. Где живёт и как создаётся

Markdown-заметка в `Metamodel/**` (ADR-002). Создание — **только командами** (ADR-004, П1–П6).
**DL-218 принято (ответ «А», 2026-10-23):** экземпляр категории создаёт универсальная команда
`create-object` (категория — обычный объект метамодельного типа); выделенная обёртка
`create-category` (ADR-004, `01-classification` §7) — UX-сахар этапа 2 (`mvp-scope` §3.2).
Реестр 18 команд не меняется. Назначение объекту — `assign-category` (MVP, этап B).

## 5. Связи с другими типами метамодели

- `facet` — принадлежность ровно одному фасету;
- `category` — иерархия «родитель → потомок» внутри фасета;
- `taxonomy` — прямой связи **нет** (правило П8 ADR-007, `category.taxonomy_direct.forbidden`);
- экземпляры объектов — через поле `categories`.

## 6. Валидация

Группа **E** реестра: `category.facet.required`, `category.facet.single`,
`category.parent.exists`, `category.parent.same_facet`, `category.parent.no_cycle`,
`category.parent.strict_mode`, `category.taxonomy_direct.forbidden` (все — error),
плюс правила назначения `assignment.*`. Новых правил карточка не добавляет.

## 7. Открытые вопросы

Нет — состав команд классификации решён (DL-218, ответ «А»); см. §4.

## 8. Этап реализации и модуль

Этап **B**; модуль `classification-service`; команда MVP — `assign-category`.
