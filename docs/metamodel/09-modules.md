# 09. Модули плагина

> [!warning] Статус: **предложено**, ждёт подтверждения пользователя
> Реестр закрывает пункт C2 чек-листа готовности: каждый модуль помечен как
> **реализуем в MVP**, **отложен** или **не реализуем**, с обоснованием и привязкой к этапу A–E
> из [[../roadmap/phases|`phases.md`]].

## 1. Что такое модуль и зачем их считать

**Модуль** (**термин**) — самостоятельная часть плагина с одной понятной задачей: «хранит связи»,
«рисует кнопки у изображений», «проверяет значения». У модуля есть имя, вход, выход и список того,
от чего он зависит.

**Бытовая аналогия.** Кухонный комбайн: мотор, чаша, ножи, тёрка — это модули. Каждый можно снять
и помыть отдельно, и поломка тёрки не означает, что сгорел мотор. Если собрать всё одним куском,
любая мелкая правка превращается в разборку всего устройства.

**Зачем считать модули до написания кода:**

| Причина | Что даёт |
|---|---|
| Видно, где тонко | 45 модулей MVP — это оценка объёма; если их станет 65, MVP не доедет до релиза. Уже сейчас этап B весит 16 модулей — его стоит разбить на B1 (схема и свойства) и B2 (ссылки и псевдонимы) |
| Можно распределить по этапам | Каждый модуль привязан к этапу A–E, порядок работы становится очевидным |
| Зависимости видны заранее | Модуль не может зависеть от того, что делается позже |
| Отказ фиксируется письменно | «Не реализуем» с причиной защищает от возврата к уже отвергнутым идеям |

## 2. Три статуса

| Статус | Что значит | Проверка |
|---|---|---|
| **`mvp`** | Реализуем в первой версии | Без него ломается основной сценарий пользователя |
| **`phase2`** | Отложен: нужен, но позже | Основной сценарий без него работает, а данных для проверки ещё нет |
| **`no`** | Не реализуем | Требует недокументированных механизмов, внешних сервисов или противоречит принятым ADR |

**Правило добавления модуля:** новый модуль появляется только вместе с записью в decision log
и строкой в этом реестре. Молча добавить «ещё один маленький модуль» нельзя — так MVP расползается
(контроль в [[../roadmap/mvp-scope|`mvp-scope.md`]] §4).

## 3. Слои: кто от кого зависит

```
┌────────────────────────────────────────────────────────────┐
│ 5. UI: панели, модалки, декорации, код-блоки                │  plugin-ui, object-panel,
│                                                             │  editor-decorations, media-wizard
├────────────────────────────────────────────────────────────┤
│ 4. Команды и представления                                  │  commands, bases-adapter,
│                                                             │  base-generator, views
├────────────────────────────────────────────────────────────┤
│ 3. Сервисы предметной области                               │  object-service, relation-service,
│                                                             │  media-service, classification-service
├────────────────────────────────────────────────────────────┤
│ 2. Схема и валидация (SchemaEngine)                         │  schema-engine, applies-when,
│                                                             │  validation, diagnostics, display
├────────────────────────────────────────────────────────────┤
│ 1. Ядро: определения, парсер, хранение                      │  bootstrap, parser, registry,
│                                                             │  identity, labels, relation-store
├────────────────────────────────────────────────────────────┤
│ 0. Obsidian API (vault, workspace, metadataCache, adapter)  │  obsidian-adapter
└────────────────────────────────────────────────────────────┘
```

**Правило слоёв:** модуль может зависеть только от своего слоя и нижележащих.
`SchemaEngine` **не знает** ни о Bases, ни о декорациях редактора (требование черновика v1.1 §18.5,
закреплено в `08-views.md` §9). Обратные зависимости запрещены — их ловит тест на импорт.

> `link-context-resolver`, `unresolved-link-service`, `alias-service`, `alias-index`,
> `alias-review-ui` — норма [[12-links-and-aliases]] (статус **`accepted`** после ответов

> `sb-review-aliases`, `sb-rebuild-alias-index`). Этап B стал самым тяжёлым (16 модулей):

Три модуля добавлены по ответу пользователя «C — что-то добавить» (DL-174). Это **не новые идеи**,
а закрытие пробелов: `backup-service` требовался мерой защиты ADR-010 (резервные копии `.sb/`),
`settings-ui` и `demo-vault` — содержанием этапа E в `phases.md` (вкладка настроек,
демо-хранилище и тесты на фикстуре), но ни один модуль за них не отвечал.

### 4.1. Стек UI: Svelte (решение пользователя, DL-175)

| Параметр | Норма |
|---|---|
| Что пишем на Svelte | Только слой 5: `plugin-ui`, `property-editor`, `object-panel`, `media-wizard`, `gallery-ui`, `list-fallback`, `settings-ui` |
| Что остаётся чистым TypeScript | Слои 0–4: ядро, схема, валидация, сервисы, команды. Правило **М2** сохраняется: `SchemaEngine` не знает об UI |
| Сборка | esbuild + `svelte` как плагин сборки; результат — один `main.js`, как требует Obsidian |
| Зависимости | `svelte` — единственная новая зависимость в MVP. Компоненты Obsidian (`Modal`, `Setting`, `Notice`) используем как оболочку, внутрь которой монтируется Svelte-компонент |
| Мера против риска «новичок + новый фреймворк» | Каркас модалки делается на vanilla (одна рабочая модалка), и только потом переносится на Svelte; глоссарий пополняется терминами Svelte по мере появления |
| Мера против разрастания | Svelte-компонент не имеет права читать vault напрямую: только через сервисы слоёв 1–3 |
| Критерий отката | Если на этапе B сборка или отладка Svelte займёт заметно больше времени, чем vanilla-прототип, возвращаемся к vanilla — это решение уровня ADR, откат фиксируем в decision log |

> [!note] Что это меняет в этапах
> Этап B получает дополнительную работу: настройка сборки Svelte внутри esbuild. Она заложена
> в критерий готовности этапа B («модалка свойств показывает условные поля»).

## 8. Правила для модулей

| Правило | Формулировка |
|---|---|
| **М1** | Модуль зависит только от своего слоя и нижележащих |
| **М2** | `SchemaEngine` и `validation-runner` не импортируют ничего из UI и интеграций |
| **М3** | Любой модуль интеграции (`bases-adapter`, `front-matter-title-adapter`) изолирован: его отключение не ломает ядро |
| **М4** | У каждого модуля есть тесты; модуль без тестов не принимается в этап |
| **М5** | Кэш (`.sb/cache/`) — не источник истины: любой индекс перестраивается командой |
| **М6** | Модуль не пишет в данные молча: любое изменение сопровождается диагностикой |
| **М7** | Имена модулей — английский `kebab-case`, в документации — с обратными кавычками |
