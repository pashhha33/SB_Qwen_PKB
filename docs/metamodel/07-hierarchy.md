# 07. Иерархия типов

> [!success] Статус: **принято пользователем 2026-10-23** (ответы **А / А / А** на вопросы
> 8f-1…8f-3, DL-208…DL-210; утверждение раздела — DL-212). Пункт **A8** чек-листа готовности
> и проблема **G-09** закрыты. Семантика потомков и абстрактных типов в `allowed_*` действует
> для связей (ADR-009) и фасетов (ADR-007) — перекрёстные ссылки внесены в `03-relations`
> и `01-classification`.

## 1. О чём раздел и почему он понадобился

У типов объектов Second Brain есть **родители**: `chapter` — подтип `work`, `character` — подтип
`person`, `project` — подтип `activity`. Механика наследования уже принята (`01-classification` §5),
но **дерево «кто от кого» нигде не было собрано** — это и есть проблема G-09. Раздел:
1. собирает полное дерево типов (закрытие G-09);
2. уточняет, как наследование взаимодействует со связями, классификацией и префиксами;
3. фиксирует правило смены типа объекта (механизм — этап 2, потребность — сейчас).

**Термины** (в глоссарии есть): **наследование** — подтип получает свойства родителя;
**абстрактный тип** — тип-«папка», экземпляр создать нельзя (И3); **подтип** — конкретный
наследник. Бытовая аналогия: «заявление» — абстрактный тип (есть шапка, дата, подпись),
«заявление на паспорт» — подтип (плюс свои поля). Заполнить можно только конкретный бланк.

## 2. Действующая нормативная база (не изобретается заново)

| Норма | Где | Суть |
|---|---|---|
| Правила наследника | `01-classification` §5 (из спецификации v1.0 §14) | **Может:** уточнять обязательность, сужать кардинальность, добавлять ограничения, добавлять новые свойства. **Не может:** менять смысл унаследованного свойства, менять фундаментальный тип значения, ослаблять обязательность родительского свойства |
| Хранение родителя | там же | Хранится **только непосредственный родитель** (`parent_type`); вышестоящие предки вычисляются; поле `family` не хранится |
| Абстрактность | ADR-005, ADR-006 | Признак `abstract: true`; экземпляры запрещены — инвариант **И3**; карточки абстрактных типов сокращённые (меры M1/M2 ADR-006) |
| Критерий «подтип или категория» | ADR-005 | Два теста: (1) нужны собственные свойства → подтип; (2) открытое множество значений → категория |
| Правила валидации | `rules.md` (уже в реестре, группа B) | `object_type.parent.exists` (error), `object_type.parent.no_cycle` (error), `object_type.abstract.no_instance` (error), плюс `object.type.not_abstract` (группа A, error) |
| Родители в реестре | `02-entities` (колонка «Родитель») | book → work (предложение, принято); project → activity; chapter → work (DL-124); character → person; poem → work; lyrics → music_work; movie/series/episode → audiovisual_work; music_track/music_album → music_work; video_game → work; article/web_page/video_source/audio_source → source; series (SERIES_COLLECTION) → collection |

**Новых правил валидации раздел не добавляет**: иерархия уже покрыта реестром (166 правил не меняются).

## 3. Три уровня иерархии (спецификация 01 §14)

Спецификация называла уровни «универсальные / семейства / специализированные», но не перечисляла
их (часть G-09). Определяем:

| Уровень | Что это | Наши типы |
|---|---|---|
| 1. Универсальные | Абстрактные корни предметных ветвей; задают минимальный общий набор свойств | `work`, `activity` (оба — ядро, `abstract: true`) |
| 2. Семейства | Группирующие типы — абстрактные или конкретные, объединяющие подтипы по предметной области | `audiovisual_work`, `music_work`, `source`, `collection` (все — `phase2`, `abstract: true`); `person` (конкретный, но родитель `character`) |
| 3. Специализированные | Листовые типы с собственными свойствами; только у них создаются экземпляры | `book`, `chapter`, `poem`, `movie`, `series`, `episode`, `music_track`, `music_album`, `lyrics`, `video_game`, `article`, `web_page`, `video_source`, `audio_source`, `character`, `series` (SERIES_COLLECTION), `project` |

Уровни — **описательная разметка дерева, а не поле схемы** (вопрос 8f-4): в определении
`object_type` нового поля не появляется, состав системных атрибутов не меняется.

Глубина наследования не ограничена жёстко; фактическая глубина в текущем реестре — **не более 3**
(`work → audiovisual_work → movie`).

## 4. Дерево типов (закрытие G-09)

**Системная ветвь — без наследования.** Системные типы метамодели плоские: `object_type`,
`property`, `property_type`, `relation_type`, `relation`, `taxonomy`, `facet`, `category` —
родителей не имеют (их состав задан кодом и ADR).

**Предметная ветвь** (✳ — ядро, [а] — абстрактный, (2) — phase2):

```
person ✳
└── character (2)
knowledge ✳          (без родителя)
media ✳              (без родителя)
guide (2)            (без родителя)

work ✳ [а]
├── book ✳
├── chapter ✳        (префикс CHP, DL-124)
├── poem (2)
├── video_game (2)
├── audiovisual_work (2) [а]
│   ├── movie (2)
│   ├── series (2)             (префикс SERIES — аудиовизуальный сериал)
│   └── episode (2)
└── music_work (2) [а]
    ├── music_track (2)
    ├── music_album (2)
    └── lyrics (2)

activity ✳ [а]
└── project ✳        (позже: task, goal, problem)

source (2) [а]
├── article (2)
├── web_page (2)
├── video_source (2)
└── audio_source (2)

collection (2) [а]
└── series (2)       (префикс SERIES_COLLECTION — книжная/киносерия как коллекция)
```

> [!note] Два `series` — не дубль
> Аудиовизуальный сериал (`SERIES`, родитель `audiovisual_work`) и объединённая книжная/киносерия
> (`SERIES_COLLECTION`, родитель `collection`, DL о слиянии `book_series`+`film_series`) — разные
> типы с разными префиксами. Размещение `audiovisual_work` и `music_work` под `work` следует из
> колонки «Позже» строки `work` в реестре и впервые фиксируется явно этим деревом.

## 5. Абстрактные типы — свод правил

1. Экземпляры запрещены: инвариант **И3** + правила `object.type.not_abstract`,
   `object_type.abstract.no_instance` (error).
2. Карточка абстрактного типа — сокращённая (меры M1/M2 ADR-006): `work`, `activity` в ядре;
   `property_type` — в реестре без карточки (ADR-004).
3. Абстрактный тип **может быть родителем** и участвовать в `allowed_subject_types` /
   `allowed_object_types` связей и фасетов — со смыслом «любой неабстрактный потомок»
   (**принято**, ответ «А», DL-209).
4. Свойства абстрактного типа наследуются всеми потомками (например, общие свойства `work`
   достаются `book`, `chapter`, `poem`…).
5. Абстрактный тип нельзя назначить значением `type` объекта, но можно выбрать в окне создания
   как «ветвь» — плагин предложит список неабстрактных потомков (поведение UI, этап реализации).

## 6. Наследование свойств

1. Подтип наследует **все** свойства родителя; в своей карточке описывает только собственные —
   унаследованные не дублируются (один источник: карточка родителя).
2. Права наследника — по `01-classification` §5 (таблица в §2 этого документа): сужать можно,
   ослаблять нельзя.
3. `applies_when` работает на любом уровне: условное свойство может быть объявлено у родителя
   (применяется и к подтипам) или только у подтипа.
4. Обязательность: требование родителя обязательно и для подтипа; подтип может сделать
   необязательное свойство родителя обязательным (сужение) — с миграцией по разделу 10,
   если экземпляры уже есть.
5. Удаление свойства у родителя затрагивает всех потомков — шаг 4 последовательности v1.1 §15.4
   (проверка совместимости) обязан считать потомков.

## 7. Иерархия и остальные механизмы

| Механизм | Правило |
|---|---|
| Связи (`allowed_*`) | **Принято (DL-208, DL-209):** указание типа в `allowed_subject_types` / `allowed_object_types` включает **всех его потомков**; абстрактные типы разрешены и означают «любой неабстрактный потомок». `suggested_*` — та же семантика, влияет только на порядок |
| Классификация (`allowed_object_types` таксономии/фасета) | Та же семантика (DL-208): тип в списке покрывает всех потомков |
| `TYPE_PREFIX` и имя файла | У подтипа **всегда собственный префикс** (`CHP`, `POEM`, `CHARACTER`…); имя файла — по префиксу собственного типа, никогда родительского |
| Представления (`.base`) | Фильтр «все произведения» генерируется как `type in [work + все неабстрактные потомки]` — список разворачивает `base-generator`; в схеме `.base` потомки видны явно |
| Валидация | Правила, объявленные для типа родителя, применяются к экземплярам подтипов (проверка идёт по цепочке предков) |
| Отношение `contains` | `book` содержит `chapter` — связь «часть — целое» не тождественна наследованию: глава — подтип `work`, но не «вид книги» |

## 8. Смена типа объекта (принято: механизм — сейчас, реализация — этап 2; DL-210)

Пункт 2 §13 черновика v1.1 закрыт: **механизм фиксируется**, реализация (`sb-change-type`) —
этап 2 (в MVP данных нет, потребность нулевая; в реестр отложенных модулей не добавляется —
остаётся записью потребности):

1. `id` **сохраняется** (ULID не переиспользуется и не меняется — И1).
2. Файл переименовывается под префикс нового типа через `vault.rename()` — Obsidian сам обновит
   ссылки (тот же приём, что в разделе 12 и ADR-001 M5).
3. Аудит данных: свойства, не принадлежащие новому типу, **не удаляются** — помечаются
   «вне схемы» (warning); пользователь решает вручную.
4. Перепроверка: категории против `allowed_object_types` новых фасетов; связи против
   `allowed_*` новых типов; обязательные свойства нового типа.
5. Всё действие — одна запись в журнале `.sb/logs/` с возможностью отката (по образцу раздела 10).
6. Команда `sb-change-type` — этап 2; ограничений на переходы нет (любой → любой при успешном
   аудите), но в окне команды первыми предлагаются типы той же ветви.

## 9. Что раздел закрывает и что не меняет

- **G-09 закрыта**: дерево перечислено (§4), уровни определены (§3).
- **A8 чек-листа закрыт**: наследование описано, абстрактные типы — тоже (DL-212).
- Реестр правил раздел **не пополнил** — иерархия уже покрыта группой B; состав команд (18),
  модулей (45), системных атрибутов (8) — **не меняются**.
- Попутная сверка (DL-207): в `02-entities.md` строка `chapter` приведена к DL-124
  (`CHP`, `core`; было `CHAPTER`, `phase2`), сводка пересчитана (13 `core` + 2 `core_abstract`
  = **15 типов ядра**, 26 `phase2`).
