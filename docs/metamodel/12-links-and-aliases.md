# Раздел 12. Пустые ссылки и псевдонимы

> [!info] Назначение документа
> Нормативный раздел метамодели: **как система ведёт себя с неразрешёнными («пустыми») ссылками**
> и **как пополняется список псевдонимов `aliases`**. Закрывает требование пользователя
> от 2026-10-22 и переносит в норму разделы черновика v1.1 §11 и §1.4.
>
> Статус `proposed`: разделы 1–6 и 9–11 опираются на уже принятые решения и требование пользователя;
> разделы 7–8 содержат **четыре открытых вопроса** (помечены «❓ вопрос 12.N»).

---

## 1. Требование пользователя (источник, дословно)

> 1. При создании заметки из пустой ссылки в теле заметки предоставляются варианты выбора типа
>    будущей заметки, а само значение ссылки заносится в `title`. Если пустая ссылка находится
>    в каком-либо свойстве, то, если у свойства есть контекст, создаётся тип из этого контекста;
>    если контекстов несколько — предоставляется выбор из них.
> 2. Добавление `aliases`: если в ссылку вручную пишется новый псевдоним, он заносится в `aliases`
>    сущности, но не на место, уже занятое дублем `title`.

Оба пункта **принимаются как требование**. Ниже — как они раскладываются на правила, что уже было
решено раньше и где нужны уточнения.

## 2. Термины раздела

| Термин | Простое объяснение | Аналогия |
|---|---|---|
| **Пустая (неразрешённая) ссылка** | Внутренняя ссылка `[[…]]`, для которой в хранилище нет файла. Obsidian рисует её приглушённым цветом, а клик создаёт новую заметку | Запись в записной книжке «позвонить Иванову» без номера: имя есть, человека за ним пока нет |
| **Текст ссылки** | То, что стоит между `[[` и `]]` (или до `\|`), — «адрес» ссылки | Адрес на конверте |
| **Отображаемый текст (псевдоним ссылки)** | То, что стоит после `\|`: `[[АДРЕС\|вот это видно]]`. Видит читатель, а не механизм разрешения ссылок | Подпись на конверте «маме» — адрес тот же, написано по-человечески |
| **Контекст ссылки** | Сведения о месте, где стоит ссылка: свойство и его объявление, тип отношения, тип содержащего объекта, заголовок раздела, папка | Если надпись «молоко» стоит в списке покупок — понятно, что это продукт; если в журнале тренировок — непонятно |
| **Сбор псевдонимов** | Автоматическое пополнение `aliases` объекта из отображаемых текстов ссылок, ведущих на него | Секретарь записывает в карточку клиента каждое обращение: «Миша», «М. И. Иванов», «тот, кто по договору» |
| **Управляемая заметка** | Заметка, у которой во frontmatter есть `id`, `type`, `title` — объект метамодели. Противоположность — обычная заметка пользователя | Паспорт есть / паспорта нет |

> [!note] Почему «пустая ссылка» ≠ «несуществующий объект»
> Ссылка может быть пустой по двум причинам: объекта действительно нет, либо он есть, но ссылка
> написана не по имени файла (например, по названию или по псевдониму, а файл называется
> `PERSON-01J8….md`). Оба случая обрабатываются одинаково на входе и **разводятся** проверкой
> дублей (§6.4): сначала ищем существующий объект, потом предлагаем создать новый.

## 3. Где встречается пустая ссылка: четыре места

| № | Место | Пример | Контекст | Сложность |
|---|---|---|---|---|
| **М1** | Значение свойства во frontmatter | `author: "[[Иван Петров]]"` | **Полный**: объявление свойства (`value_type`, `target_types`, `link_mode`) | низкая |
| **М2** | Тело управляемой заметки | `…как писал [[Иван Петров]]…` | **Частичный**: тип содержащего объекта, заголовок раздела, папка | средняя |
| **М3** | Тело обычной заметки (не объект метамодели) | черновик, дневник, входящие | **Нет** | средняя |
| **М4** | Значение свойства типа `media_reference` | `cover: "[[cover.jpg]]"` | Полный, но цель — **обёртка медиа**, а не произвольный объект | низкая (мастер уже описан) |

Правила §5–§6 применяются ко всем четырём местам; различается только набор доступного контекста.

## 4. Общие принципы (норма)

| № | Принцип | Обоснование |
|---|---|---|
| **П1** | Плагин **никогда не создаёт объект молча**. Создание — всегда явное действие пользователя: клик по кнопке, выбор в окне, команда | Спецификация v1.0 §19: молчаливое изменение данных запрещено |
| **П2** | Плагин **не угадывает тип по тексту ссылки**. «Иван Петров» не превращается в `person` только потому, что похоже на имя | Черновик v1.1 §11.1 п. 3 |
| **П3** | Плагин **не меняет тип существующего объекта** ради соответствия контексту свойства | Черновик v1.1 §11.4; смена типа — отдельная контролируемая операция (открытый вопрос из §13 v1.1) |
| **П4** | Отказ пользователя (Esc, «Отмена», закрытие окна) означает **«не создавать ничего»**. Уже созданный Obsidian файл остаётся обычной заметкой; плагин его не удаляет и не переписывает | Безопасность: чужой текст не теряется |
| **П5** | Перед созданием проверяются **дубли** по названию и псевдонимам; при совпадении пользователю предлагается выбрать существующий объект | Черновик v1.1 §11.4 |
| **П6** | Все автоматические правки текста (нормализация ссылки, добавление псевдонима) **обратимы**: действие пишется в журнал `.sb/logs/` и отменяется командой | Правило М5 модулей: кэш и журнал не источник истины, но след обязан быть |
| **П7** | Поведение раздела не зависит от сторонних плагинов. Если Front Matter Title выключен или сломан — создание из пустой ссылки и сбор псевдонимов работают так же | ADR-001, мера M3 |

## 5. Требование 1. Создание объекта из пустой ссылки

### 5.1. Четыре точки запуска

Obsidian не даёт плагину «перехватить клик по пустой ссылке до создания файла»: такого публичного API нет.
Поэтому используется штатное поведение Obsidian (клик создаёт заметку с именем = текст ссылки) и
перехват **после** факта, по публичному событию `vault.on('create')`.

> **Термин:** *перехват после факта (post-create interception)* — плагин подписывается на событие
> создания файла, узнаёт «это файл, который Obsidian создал из пустой ссылки», и предлагает
> превратить его в объект метамодели.
> **Аналогия:** вы бросили письмо в ящик, а дежурный на почте догнал его и спросил «оформить как
> заказное?». Письмо уже в системе, но решение всё ещё за вами.
> **Зачем в проекте:** единственный способ получить сценарий «кликнул по ссылке — получил объект»,
> не патчуя недокументированные внутренности Obsidian (урок исследования Front Matter Title).

| Точка | Что делает пользователь | Что делает плагин | Обязательность в MVP |
|---|---|---|---|
| **Т1. Клик по пустой ссылке** | Кликает `[[Иван Петров]]` в тексте | Ловит `vault.on('create')`; если имя нового файла совпадает с текстом неразрешённой ссылки и файл пуст (или создан из шаблона Obsidian) — открывает окно выбора типа (§5.5) | **да**, этап B |
| **Т2. Кнопка в контроле свойства** | В модалке свойств у пустой ссылки видит кнопку «Создать» | Создаёт объект с типом из контекста свойства (§5.3); окно выбора типа показывается, только если контекстов несколько | **да**, этап B |
| **Т3. Команда `sb-create-from-link`** | Вызывает команду (палитра или хоткей) | Показывает список всех неразрешённых ссылок хранилища (или текущей заметки) и создаёт объекты по выбору | **да**, этап B |
| **Т4. Кнопка у ссылки в тексте** | Наводит на пустую ссылку — появляется кнопка «Создать объект» | То же, что Т1, но без создания промежуточного файла | нет, **этап 2** (механизм тот же, что у `editor-decorations` для медиа; в MVP не успеваем по объёму) |

Обработка Т1 по шагам:

1. Событие `vault.on('create', file)`.
2. Проверки: имя файла (без `.md`) есть среди неразрешённых ссылок хранилища
   (`metadataCache.unresolvedLinks`); файл пуст или содержит только шаблон новых заметок Obsidian;
   файл не находится в `Metamodel/` и `.sb/`.
3. Если проверки не прошли — **ничего не делаем** (пользователь создал обычную заметку руками).
4. Окно выбора типа: предвыбранный тип (если контекст однозначен), поле «Название» = текст ссылки,
   строка «Выбрать существующий объект» (§6.4), кнопки «Создать» / «Отмена».
5. «Создать»: генерируем ULID → `vault.rename(file, '{TYPE_PREFIX}-{ULID}.md')` → пишем frontmatter
   (`id`, `type`, `title`, `aliases`, `created_at`, `updated_at`) → нормализуем ссылку в исходной
   заметке (§7.3). Obsidian сам обновит ссылку при переименовании — это публичное поведение.
6. «Отмена»: файл остаётся как есть, ссылка остаётся пустой, в журнал пишется `link.creation.cancelled`.

### 5.2. Значение ссылки → `title` (норма, принято)

- Текст ссылки становится значением `title` нового объекта.
- Обработка: обрезаются пробелы по краям, переносы строк заменяются пробелом, схлопываются
  повторяющиеся пробелы.
- Символы, запрещённые в именах файлов (ADR-001), в `title` **разрешены**: имя файла от названия
  не зависит. Исключение — пустая строка после обрезки: тогда поле «Название» в окне остаётся
  пустым и создание блокируется подсказкой.
- Часть ссылки до `#` и `^` (заголовок и блок) в `title` не попадает: `[[Иван Петров#Биография]]`
  даёт `title = «Иван Петров»`, а указание на раздел сохраняется в ссылке.
- Пользователь **может поправить** название в окне создания. Тогда:
  - `title` = исправленное значение;
  - исходный текст ссылки сохраняется как псевдоним (§6.2, правило «текст ссылки не теряется»).

### 5.3. Контекст ссылки: источники и их сила

| Источник | Сила | Что даёт | Состояние в MVP |
|---|---|---|---|
| **К1.** `target_types` свойства (`04-attributes` §4) | **жёсткий** | 1 тип → предвыбор; N типов → список; пусто → список всех типов | ✅ принят |
| **К2.** `allowed_object_types` / `allowed_subject_types` типа отношения (`03-relations` §5) | **жёсткий** | То же, для `link_mode: reified` и для свободно стоящих связей | ✅ принят |
| **К3.** `suggested_*` типа отношения | **мягкий** | Порядок вариантов и предвыбор; никогда не запрет | ✅ принят (ADR-009) |
| **К4.** Тип содержащего объекта | **мягкий** | Внутри `chapter` ссылка «Персонажи» скорее про `person`; используется только для порядка вариантов | ✅ принят |
| **К5.** `media_target` / `media_kinds` свойства `media_reference` | **жёсткий** | Создаётся не произвольный объект, а обёртка `media` → передаём управление мастеру `sb-create-media` | ✅ принят (ADR-008) |
| **К6.** Заголовок раздела, в котором стоит ссылка | **мягкий** | Требовал бы нового поля в объявлении свойства (например `heading_hints`) | ❌ **этап 2** |
| **К7.** Папка файла | **мягкий** | Требовал бы настройки соответствия «папка → тип» | ❌ **этап 2** |
| **К8.** Анализ текста ссылки (похоже на имя, на дату, на ISBN) | — | **Запрещён** принципом П2 | ❌ не реализуем |

Правила применения:

- **Пр1.** Жёсткий контекст **сужает** список: типы вне `target_types` / `allowed_*` не предлагаются
  вообще. Если жёстких источников несколько — берётся **пересечение**; пустое пересечение =
  ошибка определения свойства (`link.context.conflict`, `error`), создание не предлагается.
- **Пр2.** Мягкий контекст только **упорядочивает** и подсвечивает, никогда не фильтрует.
- **Пр3.** Если после всех фильтров остался ровно один тип — он предвыбран, но пользователь видит
  его название и может изменить (черновик v1.1 §11.1 п. 1: «предлагает создать», а не «создаёт»).
- **Пр4.** Свойство с `target_facet` (словарь-фасет) **не создаёт** произвольный объект: его цель —
  `category`. Клик по пустой ссылке в таком свойстве предлагает создать **категорию** нужного фасета,
  а не объект другого типа (правило П8 из ADR-007 сохраняется).
- **Пр5.** Свойство может запретить создание из ссылки вовсе — настройка `create_from_link`
  (§9.1). По умолчанию `ask`.

### 5.4. Настройка `create_from_link` у свойства

| Значение | Поведение |
|---|---|
| `ask` (по умолчанию) | Пустая ссылка в свойстве предлагает создание: с предвыбором типа, если контекст однозначен |
| `forbid` | Создание из этого свойства запрещено; пустая ссылка даёт диагностику `link.creation.forbidden` (`warning`) и кнопку «Выбрать существующий объект» |
| `auto` | Объект создаётся без вопроса, если жёсткий контекст даёт **ровно один** тип; иначе как `ask`. Значение доступно только для свойств, у которых `target_types` содержит ровно один тип |

Значение `auto` вводится, но **в MVP не рекомендуется**: оно противоречит духу принципа П1
(создание без явного действия). Оставляем его в перечислении, чтобы не ломать схему позже.

### 5.5. Окно выбора типа (состав)

1. Поле **«Название»** — предзаполнено текстом ссылки, редактируемо.
2. Список **типов**: сначала жёсткий контекст, затем мягкие подсказки, затем недавно использованные
   типы, затем все остальные. Поиск по русской подписи (`label`) и по `key`.
3. Строка **«Выбрать существующий объект»** — поиск по `title` и `aliases` (§6.4).
4. Показ **причины выбора**: «тип задан свойством `author`», «тип выбран вами» — чтобы пользователь
   понимал, откуда взялся предвыбор (обучающая подсказка, требование наставничества).
5. Кнопки «Создать» / «Отмена». Esc = «Отмена» (принцип П4).

### 5.6. Что пишется в новый объект

Стандартный набор системных атрибутов (ADR-006) плюс:

| Поле | Значение |
|---|---|
| `id` | новый ULID |
| `type` | выбранный тип |
| `title` | текст ссылки (или исправленный пользователем) |
| `aliases[0]` | копия `title` — инвариант **И4** |
| `aliases[1..]` | исходный текст ссылки, если пользователь его поправил (§5.2); затем — собранные псевдонимы (§6) |
| `created_at`, `updated_at` | момент создания |
| Обязательные свойства типа | **не выдумываются**: объект создаётся «неполным», а недостающее показывается как диагностика уровня 2 | 

Последний пункт важен: создание из ссылки не должно превращаться в длинный опрос. Пользователь
получил объект и ссылку — остальное доделает в модалке свойств, а валидация напомнит.

## 6. Требование 2. Сбор псевдонимов в `aliases`

### 6.1. Что уже решено раньше (инвариант И4)

| Правило | Содержание | Источник |
|---|---|---|
| **И4** | `aliases[0] == title`; остальные элементы — дополнительные псевдонимы, их порядок сохраняется | ADR-006, `04-attributes` §3 |
| Синхронизация | При изменении `title` плагин обновляет `aliases[0]`, остальные элементы не трогает | черновик v1.1 §1.4 |
| Дословно из черновика | «Если пользователь задаёт для управляемой ссылки отображаемый текст, отличающийся от канонического названия, плагин рассматривает этот текст как возможный новый псевдоним и добавляет его в `aliases` после проверки **согласно режиму работы плагина**» | черновик v1.1 §1.4 |

То есть требование пользователя **не противоречит** принятой модели, а уточняет её: «не на место,
занятое дублем title» = «после `aliases[0]`». Формулировка «согласно режиму работы плагина»
оставляла режим неопределённым — теперь определяем (§6.5, ❓ вопрос 12.2).

### 6.2. Правила сбора (норма)

| № | Правило |
|---|---|
| **С1** | Источник — **отображаемый текст** управляемой ссылки, ведущей на существующий объект: `[[PERSON-01J8….md\|М. Булгаков]]` |
| **С2** | Псевдоним **добавляется в конец** списка. `aliases[0]` остаётся за `title` и не занимается никогда |
| **С3** | **Не добавляется**, если после нормализации совпадает с: `title`; любым существующим `aliases[i]`; именем файла цели (с расширением и без); текстом ссылки до `\|` |
| **С4** | Нормализация при сравнении: регистр не учитывается, пробелы схлопываются, невидимые пробельные символы (U+00A0, U+2007, U+202F) заменяются обычным пробелом, кавычки «ёлочки» и дюймы считаются разными (**не** уравниваются) |
| **С5** | Исходное написание **сохраняется**: пишем так, как написал пользователь (`«М.Булгаков»` останется с точкой без пробела, если так было в ссылке) |
| **С6** | Существующие псевдонимы **не удаляются и не переставляются**. Сбор только добавляет |
| **С7** | Мусор не собирается — фильтр (§6.3) |
| **С8** | Если цель ссылки определена неоднозначно (два файла с одним именем в разных папках) — псевдоним **не добавляется**, выдаётся диагностика `link.target.ambiguous` (`warning`) |
| **С9** | Каждое добавление пишется в журнал `.sb/logs/alias-collections.jsonl`: метка времени, объект, значение, откуда (файл и ссылка), действие пользователя. Журнал — не источник истины, но по нему работает отмена |
| **С10** | Сбор **не меняет** `title`, `id`, имя файла и тело заметки, кроме случая, выбранного в ❓ вопросе 12.1 |
| **С11** | Сбор работает и для ссылок в свойствах, и для ссылок в теле, и для ссылок из обычных (не управляемых) заметок |
| **С12** | Сбор **не работает** для неразрешённых ссылок: добавлять некуда. После создания объекта (§5) текст ссылки обрабатывается по правилам С1–С11 |

### 6.3. Фильтр мусора

Отображаемый текст часто пишут не как имя, а как пометку: `[[PERSON-…\|см. выше]]`, `[[BOOK-…\|та самая книга]]`.
Такие значения в `aliases` вредны: они попадают в автодополнение Obsidian и начинают предлагаться
как имена объектов.

| Что не собирается | Пример |
|---|---|
| Короче 3 символов после нормализации | `[[…\|он]]` |
| Совпадает с текстом ссылки до `\|` или с именем файла | `[[PERSON-….md\|PERSON-….md]]` |
| Состоит только из знаков препинания, цифр и пробелов | `[[…\|→]]`, `[[…\|123]]` |
| Начинается со слова из стоп-списка | `см.`, `смотри`, `тут`, `здесь`, `выше`, `ниже`, `там`, `→`, `ibid` |
| Совпадает с `title` или `aliases` другого объекта (признак ошибки) | не добавляется, выдаётся `alias.cross_object_duplicate` (`info`) |

Стоп-лист хранится в настройках плагина и **редактируется пользователем** (§9.2).
Всё отфильтрованное видно в окне разбора (§6.6) — ничего не пропадает молча.

### 6.4. Дубли: сначала ищем, потом создаём

При создании объекта из пустой ссылки (§5) и при сборе псевдонимов (§6) используется один и тот же
поиск по `title` + `aliases`:

| Ситуация | Поведение |
|---|---|
| Пустая ссылка совпадает с `title` существующего объекта | Окно показывает объект первым пунктом: «Открыть / связать с существующим». Создание — только если пользователь явно выберет «создать новый» |
| Пустая ссылка совпадает с `aliases[i]` существующего объекта | То же, с пометкой «найден по псевдониму» |
| Совпадений несколько | Список вариантов, ничего не создаётся автоматически (черновик v1.1 §11.4) |
| Совпадений нет | Обычный сценарий создания |

**Риск, который это закрывает:** автодополнение Obsidian предлагает и имена файлов, и псевдонимы.
Набрав псевдоним и нажав Enter, пользователь может создать **новую заметку с именем = псевдоним** —
получится дубль. Перехват Т1 (§5.1) распознаёт такой файл и предлагает «объединить с существующим».

### 6.5. Режим сбора — ❓ вопрос 12.2

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **А. Молча + уведомление + отмена** *(рекомендация)* | Псевдоним добавляется сразу; всплывает уведомление «Добавлен псевдоним „М. Булгаков“ к „Михаил Булгаков“» с кнопкой «Отменить»; всё видно в окне разбора | Не прерывает работу; ничего не теряется; отмена в один клик | Правки чужого файла без спроса — смягчается уведомлением и журналом |
| **Б. Спросить каждый раз** | Модалка «Добавить псевдоним?» на каждое новое значение | Полный контроль | Прерывает письмо; при активной работе — десятки окон в день; люди начинают отвечать «нет» не глядя |
| **В. Только через команду** | Псевдонимы копятся в кэше, добавляются пачкой из окна разбора `sb-review-aliases` | Никаких скрытых правок; удобно разбирать скопом | Между написанием ссылки и появлением псевдонима проходит время; автодополнение не улучшается сразу |

**Рекомендация: А**, с настройкой «режим сбора» (§9.2), чтобы любой из трёх режимов можно было
включить без изменения кода. Обоснование: сбор псевдонимов — операция низкого риска (добавляется
одно значение в список, который пользователь видит во frontmatter), а выигрыш от неё
(автодополнение ссылок, поиск) приходит только тогда, когда она не требует усилий.

### 6.6. Судьба отображаемого текста после сохранения — ❓ вопрос 12.1

Черновик v1.1 §1.4 требует: «после сохранения нового псевдонима управляемая ссылка нормализуется
к каноническому виду `[[{TYPE_PREFIX}-{ID}.md|{название}]]`». Это значит, что написанный вами
текст ссылки **заменяется** на актуальное название.

| Вариант | Что происходит со ссылкой `[[PERSON-….md\|М.Булгаков]]`, если `title = «Михаил Булгаков»` | Плюсы | Минусы |
|---|---|---|---|
| **А. Переписать на канонический** (как в черновике) | становится `[[PERSON-….md\|Михаил Булгаков]]`; «М.Булгаков» уезжает в `aliases` | Все ссылки выглядят одинаково; при смене `title` ссылки обновляются одним проходом; текст всегда читаем | Плагин **переписывает ваш текст** — авторская формулировка теряется; нельзя написать «…как отмечал [[М.Булгаков\|автор „Мастера“]]» |
| **Б. Оставить как написал пользователь** *(рекомендация)* | остаётся `[[PERSON-….md\|М.Булгаков]]`; значение добавлено в `aliases` | Текст принадлежит пользователю (принцип спецификации v1.0 §19); контекстные подписи в прозе работают; `aliases[0] == title` всё равно даёт читаемость в автодополнении и в проводнике | Ссылки выглядят по-разному; при смене `title` старые отображаемые тексты устаревают — лечится командой `sb-refresh-link-aliases` (этап 2) |
| **В. Спросить при первом случае** | настройка на хранилище, значение по умолчанию — Б | Гибко | Ещё одна настройка, которую новичку трудно выбрать осознанно |

**Рекомендация: Б.** Обоснование: вариант А молча переписывает содержимое заметки, а это ровно то,
что запрещено общим принципом проекта («никаких молчаливых правок данных») и что уже отвергнуто
для медиа (DL-149: замена `![[photo.jpg]]` на обёртку — только по явному согласию).
Псевдоним при этом всё равно собирается, так что польза варианта А (пополнение `aliases`) сохраняется.

### 6.7. Окно разбора псевдонимов (`sb-review-aliases`)

Панель со списком: объект → собранные псевдонимы → откуда → когда. Действия: удалить, перенести
в другой объект, отфильтровать. Нужно по двум причинам: (1) отмена молчаливого режима;
(2) разбор мусора, который фильтр пропустил.

### 6.8. Взаимодействие с `person`

У типа `person` есть содержательные поля псевдонимов: `birth_name`, `pen_name`, `also_known_as`,
`original_name` (DL-151). Правило согласования:

- **Собранный из ссылки псевдоним попадает в `aliases`, а не в эти поля.** Плагин не знает,
  настоящее ли это имя, творческий псевдоним или прозвище.
- Все значения `birth_name`, `pen_name`, `also_known_as`, `original_name` **обязаны** присутствовать
  в `aliases` (правило уже зафиксировано в карточке `person`) — то есть движение одностороннее:
  из полей в `aliases`, а не наоборот.
- Окно разбора (§6.7) подсвечивает собранные псевдонимы человека с предложением «перенести в
  `also_known_as`» — как **подсказка**, не как автоисправление.

## 7. Каноническая ссылка после создания

### 7.1. Формат (напоминание ADR-001)

```markdown
[[{TYPE_PREFIX}-{ULID}.md|{title}]]
```

### 7.2. Обязательность псевдонима в ссылке — ❓ вопрос 12.3

| Вариант | Ссылка в тексте после создания объекта «Иван Петров» | Плюсы | Минусы |
|---|---|---|---|
| **А. Всегда с псевдонимом** *(рекомендация)* | `[[PERSON-01J8….md\|Иван Петров]]` | Текст читаем **без сторонних плагинов** — закрывает уровень 1 стратегии ADR-001 там, где Front Matter Title бессилен (тело заметки) | Ссылка длиннее; при смене `title` псевдоним в ссылке устаревает (лечится командой, этап 2) |
| **Б. Без псевдонима** | `[[PERSON-01J8….md]]` | Ссылка короче и всегда «свежая»: Obsidian сам подставит новое имя файла при переименовании | В тексте видно `PERSON-01J8Z6M4K2Q7V9X3N5B0C1D2EF.md` — без Front Matter Title это нечитаемо; ADR-001 признаёт отображение best effort |
| **В. Спрашивать в окне создания** | галочка «показывать название в тексте» | Гибко | Лишнее решение в окне, которое должно быть быстрым |

**Рекомендация: А.** Обоснование: ADR-001 прямо называет слабое место — «имена файлов в проводнике
и на диске нечитаемы», а уровень 1 стратегии (`aliases[0] == title`) работает в автодополнении
и быстром переключателе, но **не в теле заметки**. Псевдоним в ссылке — единственный способ
сделать текст читаемым без чужого плагина и без собственного слоя подмены (который вне MVP).
Это же канонический формат из ADR-001, так что нового правила не появляется.

### 7.3. Нормализация ссылки

| Шаг | Что делается |
|---|---|
| 1 | В исходной заметке пустая ссылка заменяется на каноническую (§7.1). Замена точечная: правится только эта ссылка, остальной текст не трогается |
| 2 | Если ссылок на тот же текст несколько — правятся **все** в той же заметке; в других заметках — по команде `sb-normalize-links` (этап 2), не молча |
| 3 | Действие пишется в журнал с возможностью отмены (принцип П6) |
| 4 | Если пользователь выбрал существующий объект — новый не создаётся, ссылка нормализуется на него (черновик v1.1 §11.3) |

## 12. Риски и деградация

| Риск | Последствие | Мера |
|---|---|---|
| Obsidian изменит поведение создания заметки из пустой ссылки | Т1 перестанет срабатывать | Т2 и Т3 не зависят от этого; настройка `interceptObsidianCreate`; тесты на фиксуре (`demo-vault`) |
| Перехват `vault.on('create')` сработает на файл, созданный не из ссылки (синхронизация, сторонний плагин, Templater) | Лишнее окно | Проверки §5.1 п. 2: совпадение с текстом неразрешённой ссылки + пустота файла + не `Metamodel/`/`.sb/` |
| Дубль из-за автодополнения Obsidian по псевдониму | Два объекта вместо одного | §6.4: поиск дублей до создания; команда слияния — этап 2 |
| Мусор в `aliases` | Автодополнение предлагает «см. выше» | Фильтр §6.3 + окно разбора §6.7 + правило `alias.min_length` |
| Сбор псевдонимов правит чужой файл (frontmatter объекта) | Недоверие пользователя | Режим `ask`/`manual` (§6.5), уведомление с отменой, журнал |
| Плагины Templater / QuickAdd создают заметки со своими именами | Заметка вне метамодели | Это допустимо: объект появляется только через наши команды (ADR-004); такие заметки остаются «обычными», валидация их не трогает |
| Front Matter Title сломан | Названия не подменяются в проводнике | Не влияет на этот раздел (принцип П7); читаемость в теле даёт псевдоним в ссылке (§7.2) |

**Деградация:** если все механизмы раздела выключены настройками, система возвращается к
поведению «до раздела 12»: объекты создаются командой `create-object`, ссылки пишутся руками,
`aliases` правит пользователь. Данные при этом не теряются и не портятся.
