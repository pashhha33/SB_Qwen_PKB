# 10. Правила миграций

> [!success] Статус: **принято пользователем 2026-10-23** (ответы **А / А / А / А** на вопросы
> 8e-1…8e-4, DL-201…DL-204; утверждение раздела — DL-205). Пункт **B4** чек-листа готовности
> закрыт → блок **B — 4/4 (100%)**; проблема **G-08** закрыта.

## 1. Что такое миграция и зачем этот раздел

**Миграция** (**термин**, см. глоссарий) — управляемое преобразование **уже существующих данных**
после изменения схемы: старые заметки приводятся к новым правилам.

**Бытовая аналогия.** Дом перешёл на новые квитанции: старая форма оплаты больше не принимается.
Миграция — это не «выбросить старые квитанции», а организованная кампания: всем разослали новые
бланки, заполнили их по старым данным, каждый получил уведомление «что изменилось», а оригиналы
лежат в архиве, пока не убедимся, что ничего не потеряли.

**Зачем раздел, если миграций в MVP нет** (DL-006, модуль `migration-engine` отложен)? Требование
чек-листа (B4) и `mvp-scope` §3.2: **потребность фиксируется в документах заранее**, чтобы:
1. решения, принятые сегодня (обязательный `person.role`, пять значений `book_format`, состав
   `aliases`), уже знали, как будут применяться к данным завтра;
2. формат записи миграции не изобретался в спешке, когда данные уже есть и цена ошибки ненулевая;
3. черновик v1.1 §15.6 («резервирование и журналирование… не утверждены») получил норму.

Основание из черновика v1.1 §15.4: «если изменение схемы требует преобразования данных, плагин
должен оформить его как **явную миграцию** или пакетную операцию».

## 2. Принципы (МГ1–МГ8)

| № | Принцип | Основание |
|---|---|---|
| МГ1 | **Никаких молчаливых переписываний.** Любое преобразование данных — видимое, сообщённое, записанное в журнал | спецификация v1.0 §19, `severity-policy.md` §2 |
| МГ2 | **Резервная копия до, а не после.** Перед применением миграции создаётся снимок всех затрагиваемых файлов и `.sb/relations/relations.jsonl` | ADR-010 мера M1 |
| МГ3 | **Сначала предпросмотр, потом подтверждение.** Сухой прогон (dry run) показывает: сколько файлов, какие поля, какие значения; применение — только по явному подтверждению | v1.1 §15.4 шаги 5–6; по образцу DL-170 (перегенерация всегда спрашивает) |
| МГ4 | **Обратимость.** У каждой миграции есть путь отката: снимок + обратные операции (§8) | ADR-010 меры M1, M8 |
| МГ5 | **Атомарность.** Ошибка на файле — миграция останавливается, уже изменённые файлы остаются согласованными (каждый файл преобразуется атомарно: временный файл → переименование), состояние фиксируется в журнале | ADR-010 мера M3 |
| МГ6 | **Миграция — явное действие.** Запускается командой пользователем. Единственное исключение — четвёртый случай автоисправления `severity-policy` (подстановка значения-заглушки при записи объекта): оно точечное, всегда сообщается и пишется в журнал миграций как «ленивая» операция | DL-159, v1.1 §15.4 |
| МГ7 | **Идемпотентность.** Повторный запуск той же миграции не дублирует изменения: уже преобразованные файлы пропускаются (операции проверяют текущее значение перед записью) | — |
| МГ8 | **Честный отчёт.** Итог показывает: преобразовано / пропущено / ошибки; файлы, которые не удалось преобразовать, перечислены с причиной и остаются нетронутыми | — |

## 3. Какие изменения требуют миграции

Классификация согласована с semver-политикой `CHANGELOG.md` (MAJOR = «старая заметка перестаёт
быть правильной»).

| Изменение схемы | Пример из проекта | Миграция данных | Версия метамодели (после 1.0.0) |
|---|---|---|---|
| Новое **необязательное** свойство, новый тип, новое значение перечисления, новое правило-`warning` | фасет `genre`, тип `chapter` | Не нужна: старые заметки остаются корректными | MINOR |
| Свойство стало **обязательным** | `person.role` (DL-156) | Да: подстановка значения-заглушки с предупреждением (случай 4 `severity-policy`, DL-159) | MAJOR |
| **Сужение перечисления** (значение удалено) | гипотетическое удаление значения `book_format` | Да: обязательное отображение «старое значение → новое»; значения без отображения останавливают миграцию | MAJOR |
| **Переименование** ключа свойства, типа, `TYPE_PREFIX` | таблица 40 имён ADR-003 | Да: перепись frontmatter + переименование файлов (по `id`, ADR-001 M5) + обновление ссылок | MAJOR |
| **Удаление** свойства или типа | — | По умолчанию данные **не трогаем**: значения остаются во frontmatter как «вне схемы» (warning); явная очистка — отдельная операция с подтверждением | MAJOR |
| Ужесточение кардинальности / `allowed_*` у связей | — | Да: excess-значения — в отчёт, автоматическое удаление запрещено | MAJOR |
| Смена `link_mode` у свойства (`direct` → `reified`) | — | Да: `backfill_relation` — создание объектов `relation` из значений поля с заполнением `origin_property` | MAJOR |
| Текстовое поле → `object_reference` | `employer` → `organization` (этап 2, §9.4) | Да: `convert_text_to_reference` с созданием объектов и поиском дублей | MAJOR |
| Формат служебных данных (`.sb/`) | версия формата `relations.jsonl` | Миграция уровня плагина: прозрачно для заметок, обязательный снимок `.sb/` | версия плагина |

**Правило двух фаз.** Применение изменения схемы (правка определения) и преобразование данных —
**два отдельных действия**: схема применяется по 8-шаговой последовательности v1.1 §15.4, миграция
данных предлагается следом и запускается явно. Плагин никогда не преобразует данные «в момент»
правки определения.

## 4. Версии схемы и состояние хранилища

- **Версия метамодели** (semver) — уже ведётся в `CHANGELOG.md`; она и есть версия схемы.
  Отдельной нумерации «версий схемы» не вводится — второй счётчик создал бы рассинхрон.
- Технический маркер хранилища (**принято**, ответ «А», DL-201): файл `.sb/state.json`:

```json
{
  "schema_version": "0.17.0",
  "plugin_version": "0.1.0",
  "migrations_applied": ["MIG-01JQ…"],
  "updated_at": "2026-11-01T12:00"
}
```

- `schema_version` — версия метамодели, до которой данные хранилища приведены. При открытии
  хранилища плагин сравнивает её с версией определений: отставание = «доступны миграции»
  (уведомление, без автозапуска — МГ6).
- В frontmatter объектов версия **не пишется**: системные атрибуты — закрытый набор из 8 полей
  (ADR-006), и техническое поле там нарушило бы И6 и засоряло бы данные.
- Отсутствующий `.sb/state.json` (старое хранилище) трактуется как «версия неизвестна»:
  плагин предлагает полную проверку `validate-vault` вместо угадывания.

## 5. Запись миграции: формат и каталог операций

**Где живёт** (**принято**, ответ «А», DL-202): `.sb/migrations/` — один JSON-файл на миграцию
(`MIG-{ULID}.json`), по ADR-002 («черновики миграций — `.sb/`, JSON») и критерию «с чем работает
только плагин».

**Состав записи:**

```json
{
  "id": "MIG-{ULID}",
  "title": "Обязательный role: подстановка заглушки",
  "description": "person.role стал обязательным (DL-156); пустые значения заполняются other_occupation",
  "created_at": "2026-11-01T12:00",
  "from_version": "0.16.0",
  "to_version": "0.17.0",
  "trigger": "property.person.role.required",
  "status": "draft",
  "operations": [
    {
      "op": "set_value_if_empty",
      "object_types": ["person"],
      "property": "role",
      "value": ["other_occupation"],
      "notify": "warning"
    }
  ],
  "undo": [
    {
      "op": "remove_value",
      "object_types": ["person"],
      "property": "role",
      "value": ["other_occupation"],
      "only_if_added_by": "MIG-{ULID}"
    }
  ],
  "report": null
}
```

`status`: `draft` → `approved` (подтверждена пользователем в предпросмотре) → `applied` | `failed`
| `rolled_back`. `report` заполняется после применения (числа, список файлов, ошибки).

**Каталог операций** (закрытый в первой версии формата; новая операция = новая версия формата):

| Операция | Что делает | Пример |
|---|---|---|
| `set_value_if_empty` | Подставляет значение, если поле пустое | заглушка `other_occupation` |
| `add_property` | Добавляет поле со значением по умолчанию (или без) | новое свойство со `standard`-статусом |
| `rename_key` | Переименовывает ключ во frontmatter затронутых типов | `years_active` → `active_years` |
| `map_enum_value` | Заменяет значения по карте «старое → новое»; значение без карты — ошибка, стоп | сужение `book_format` |
| `remove_key` | Удаляет ключ (только с явным подтверждением; по умолчанию схема §3 — значения остаются) | явная очистка удалённого свойства |
| `rename_type_prefix` | Переименовывает файлы `{OLD}-{ULID}.md` → `{NEW}-{ULID}.md` + переписывает ссылки (Obsidian обновляет их сам при `vault.rename`) | исправление `CHARACTЕR` → `CHARACTER` |
| `backfill_relation` | Создаёт объекты `relation` из значений `direct`-поля, заполняет `origin_property` | смена `link_mode` на `reified` |
| `convert_text_to_reference` | Создаёт объекты из текстовых значений и заменяет поле ссылкой (с поиском дублей по `title`+`aliases`) | `employer` → `organization` (этап 2) |

## 6. Как миграция встроена в 8-шаговую последовательность (v1.1 §15.4)

```
Изменение определения (команда или найдено в файле)
 1 принять команду / обнаружить изменение
 2 разобрать и проверить структуру
 3 проверить обязательные поля, уникальность id, целостность ссылок
 4 проверить совместимость со схемой и затронутыми объектами   ← здесь рождается черновик миграции
 5 показать предварительный просмотр последствий               ← сухой прогон (§7)
 6 создать резервную копию и запросить подтверждение            ← МГ2, МГ3
 7 сохранить изменение (схемы)
 8 перепроверить сохранённое и обновить кэш
 ───────────────────────────────────────────────
 Миграция данных — отдельное явное действие после шага 8 (МГ6, «правило двух фаз»):
 9 команда sb-migrate-apply → снимок → применение по файлам → журнал → отчёт → schema_version+
```

## 7. Безопасность: снимки, журнал, сухой прогон

**Два вида резервных копий — не смешивать:**

| | `backup-service` (MVP, этап C) | Снимок миграции (этап 2) |
|---|---|---|
| Что копирует | `.sb/` (связи, кэш, журналы) перед каждой записью | Затронутые `.md`-файлы + `.sb/relations/relations.jsonl` + изменяемые определения |
| Где | `.sb/backups/` (ротация, последние N) | `.sb/backups/migrations/{MIG-id}/` |
| Когда удаляется | Ротация автоматически (последние 10) | **Не удаляется автоматически** — только явной командой после успешной проверки (**принято**, DL-204) |

**Журнал миграций** — `.sb/logs/migrations.jsonl`, одна строка на событие (формат общий
с `alias-collections.jsonl` раздела 12):

```json
{"ts":"2026-11-01T12:03","migration_id":"MIG-01JQ…","event":"file_done","file":"PERSON-01J….md","ops":["set_value_if_empty:role"],"backup":".sb/backups/migrations/MIG-01JQ…/PERSON-01J….md"}
```

События: `start`, `file_done`, `file_skipped`, `file_error`, `done`, `rollback_start`,
`rollback_done`, `lazy_fix` (четвёртый случай автоисправления — точечно при записи объекта).
Журнал **append-only**; исправление журнала = новое событие.

**Сухой прогон (dry run)** (**термин**) — прогон без записи: считается список затронутых файлов
и изменений, показывается разница (по образцу перегенерации `.base`, DL-170) и сводка
«N файлов, M операций, K ошибок-блокеров». Команда этапа 2: `sb-migrate-preview`.

## 8. Откат

Три уровня; принята глубина **1 + 2** (ответ «А», DL-203):

1. **Снимок** — восстановление файлов из `.sb/backups/migrations/{MIG-id}/` (всегда есть, МГ2).
2. **Обратные операции** — секция `undo` в записи: точечная отмена добавленного (с защитой
   «только если значение добавлено этой миграцией» — `only_if_added_by`, чтобы не удалить
   данные, которые пользователь успел поменять руками).
3. **Пошаговый replay журнала** — не реализуем: избыточно при наличии 1 и 2.

Откат — явная команда (`sb-migrate-undo`), сам пишется в журнал, после отката
`schema_version` не меняется (схема остаётся новой; данные помечаются как требующие повторной
миграции — уведомление).

## 9. Четыре образцовых сценария

### 9.1. `person.role` стал обязательным (образец из DL-159)

Первое в проекте изменение «было необязательным — стало обязательным». Два механизма, оба нужны:
- **ленивый** (случай 4 `severity-policy`): при записи объекта с пустым `role` подставляется
  `["other_occupation"]`, показывается `warning` «замените значение», пишется событие `lazy_fix`;
- **пакетный** (миграция `set_value_if_empty` из §5): прогоняется один раз после применения
  новой схемы, чтобы не ждать первого открытия каждой записи.
Конфликта нет: операция идемпотентна (МГ7) — ленивое исправление делает пакетный прогон пустым.

### 9.2. Сужение перечисления (`book_format`)

Образец на будущее (`book_format` сейчас закрыт из пяти значений, DL-121). Норма: значение
**нельзя удалить**, не объявив отображение `map_enum_value` («старое → новое») или не перенеся
его в `lifecycle: deprecated` → `archived` (ADR-011: значения сохраняются, скрываются из форм).
Значение без отображения — блокер: миграция останавливается до решения пользователя.

### 9.3. Включение/выключение сбора псевдонимов (состав `aliases`)

Миграции данных **нет** — это политика, и она фиксируется здесь:
- при **выключении** сбора уже собранные псевдонимы **остаются** (удаление было бы молчаливой
  правкой данных, МГ1); журнал `alias-collections.jsonl` хранит происхождение каждого;
- очистка — только руками через окно разбора `sb-review-aliases` (раздел 12, §6);
- при **включении** сбора задним числом ничего не пересчитывается: источник — будущие ссылки,
  не архив (пересчёт всех ссылок хранилища — отдельная команда этапа 2 `sb-normalize-links`).

### 9.4. Текстовые поля `person` → `organization` (этап 2)

Самый сложный образец: `convert_text_to_reference` для `employer`, `affiliation` и подобных
(вопрос 9.4 карточки `person`). Порядок: сухой прогон → для каждого текстового значения поиск
существующего объекта по `title`+`aliases` (`.sb/cache/alias-index.json`) → нет — создание
`organization` (командой, по схеме) → замена значения ссылкой → отношение `employment`
(реестр типов отношений этапа 2) создаётся, только если пользователь выбрал реификацию в предпросмотре.
Отчёт обязателен: какие объекты созданы, какие значения объединены в один объект.

| Что | Когда |

уже есть в `rules.md` («правила, которых пока нет»). Состав будущей группы (черновик,

`migration.journal.append_only`, `migration.enum_map.total`, `migration.undo.protected`,
`migration.state.version_consistent`.
