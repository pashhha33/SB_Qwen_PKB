# 08. Представления

> [!warning] Статус: **предложено**, ждёт подтверждения пользователя
> Документ закрывает вопросы G-07 (какие представления нужны) и C-10 (какими механизмами).
> Ограничения Bases в разделе 6 проверены по официальной документации Obsidian, а не по догадкам.

## 1. Что такое представление

**Представление** (**термин**) — способ показать набор объектов или один объект человеку: таблица,
карточки, список, панель, блок навигации.

**Бытовая аналогия.** Данные — это картотека в ящике. Представление — способ её предъявить:
разложить карточки таблицей на столе, повесить на стену как галерею или показать одну карточку
крупно. Содержимое ящика при этом не меняется.

**Принцип, из которого исходим:** представление **никогда не хранит данные**. Оно их читает.
Если представление и данные расходятся, правда — в данных (ADR-002).

## 2. Главное решение: в MVP представление — не объект метамодели

Тип объекта `view` остаётся в реестре со статусом `phase2` (как и было решено на шаге 4).
В MVP представления существуют как **реальные артефакты**, которые можно открыть и посмотреть:

| Артефакт | Что это | Кто владеет |
|---|---|---|
| Файл `.base` | Декларация таблицы/карточек/канбана/списка в формате Bases | Генерирует плагин, читает Obsidian |
| Код-блок в заметке | Например ` ```sb-chapter-nav``` ` — навигация по главам | Пользователь вставляет, плагин рисует |
| Панель плагина | Свой интерфейс: карточка объекта, галерея медиа, список свободных файлов | Плагин |

**Почему так, а не объектами метамодели:**

| Довод | Объяснение |
|---|---|
| Файл `.base` **уже** декларация | Держать рядом ещё и объект `view` с тем же содержанием — это денормализация: две копии правды, которые разъедутся |
| Меньше сущностей до кода | В MVP не нужно реализовывать тип `view`, его валидацию, редактор и хранение |
| Представление видно глазами | Файл `.base` открывается в Obsidian штатно; объект метамодели открывался бы только нашей панелью |
| Путь к объектам открыт | На этапе 2 тип `view` вводится для пользовательских сохранённых представлений; `.base`-файлы останутся механизмом, а объект — описанием |

**Следствие для валидации:** уровень контроля 5 («проверка представлений») проверяет не объекты
`view`, а **артефакты**: существует ли `.base`-файл, ссылаются ли его колонки на объявленные
свойства, доступен ли механизм (установлен ли Bases).

## 3. Механизм представления: закрытый список

Перечисление `mechanism` (было предварительным из четырёх значений, `05-enumerations` §3.13)
**закрывается** в составе трёх значений:

| Значение | Подпись | Что это | В MVP |
|---|---|---|---|
| `base` | Obsidian Bases | Файл `.base` или встроенный код-блок `base`; таблица, карточки, список, канбан, карта | **да** |
| `plugin_view` | Панель плагина | Собственный интерфейс: карточка объекта, галерея медиа, список свободных файлов | **да** |
| `code_block` | Код-блок плагина | Свой `code_block_processor`: `sb-chapter-nav` | **да** |

**Убраны из предварительного списка:**

| Было | Куда делось | Почему |
|---|---|---|
| `dataview` | Этап 2 | Требует установки стороннего плагина и своего языка запросов; метамодель не должна зависеть от него (C-10, черновик v1.1 §18.5: «Fileclass и Bases — не обязательные зависимости», тем более Dataview) |
| `dataviewjs` | Этап 2 | То же + исполнение произвольного JS в запросе: это дыра в предсказуемости |

## 4. Реестр представлений MVP

| # | Представление | Механизм | Что показывает | Деградация, если Bases недоступен |
|---|---|---|---|---|
| В1 | Таблица книг | `base` (table) | Название, автор, год, `read_status`, `rating`, `format` | Команда `show-object-list` — простой список плагина |
| В2 | Карточки книг с обложками | `base` (cards) | Обложка через `cover_file`, название, автор | Тот же список, без обложек |
| В3 | Полка прочитанного | `base` (table) | Фильтр `read_status == "read"`, сортировка по `finished_on` | Список с фильтром |
| В4 | Список глав книги | `base` (table) | `order`, `chapter_number`, `title`; фильтр по книге | Навигационный блок в главе (В10) остаётся |
| В5 | Таблица людей | `base` (table) | Имя, `role`, `sort_name`, число книг | Список |
| В6 | Канбан проектов | `base` (kanban) | Группировка по `status`, порядок групп через `groupOrder` | Список, сгруппированный плагином |
| В7 | Карточка объекта | `plugin_view` | Свойства с русскими подписями, условные поля, связи, диагностики | Не зависит от Bases |
| В8 | Галерея медиа | `plugin_view` | Миниатюры через `getResourcePath()`, роли, способ создания, где используется | Не зависит от Bases |
| В9 | Свободные файлы | `plugin_view` | Вложения без обёрток + кнопка «создать обёртку» | Не зависит от Bases |
| В10 | Навигация по главам | `code_block` | Кнопки «предыдущая / следующая / к книге» | Не зависит от Bases |
| В11 | Проблемные объекты | `base` (table) | Фильтр по служебным меткам `sb/error`, `sb/warning` (§7) | Панель диагностик (В7) |
| В12 | Узел графа | — (штатный граф Obsidian) | Связи `direct` видны в графе; `reified` — нет | Не наше: компенсируется блоком «Связан с этим объектом» |

**Что намеренно не делаем в MVP:** собственную визуализацию графа (дорого, а штатный граф есть),
карту (map) — нет объектов с координатами, собственные таблицы — Bases их делает лучше.

## 5. Генерация `.base`-файлов

| Параметр | Норма |
|---|---|
| Где живут | `Metamodel/views/` (рядом с определениями метамодели) |
| Имя файла | `VIEW-{type_key}-{purpose}.base`, например `VIEW-book-shelf.base` |
| Кто создаёт | Команда `create-view` (появится на этапе 2 вместе с типом `view`) и генератор при первом запуске: плагин предлагает готовые представления для типов ядра |
| Кто правит | Пользователь может править руками; плагин **не перезаписывает** изменённый файл молча |
| Защита от перезаписи | В начале файла — комментарий-маркер `# sb-generated: v1`; при регенерации плагин сравнивает маркер и спрашивает |
| Встраивание в заметку | Тот же YAML можно вставить код-блоком ` ```base ``` ` — Bases это поддерживает |

**Образец файла** (полка прочитанного с обложками):

```yaml
# sb-generated: v1
filters:
  and:
    - note.type == "book"
    - note.read_status == "read"
properties:
  note.title:
    displayName: Название
  note.author:
    displayName: Автор
  note.rating:
    displayName: Оценка
views:
  - type: cards
    name: Обложки
    order:
      - note.title
      - note.author
      - note.rating
  - type: table
    name: Таблица
    order:
      - note.title
      - note.author
      - note.finished_on
      - note.rating
    summaries:
      note.rating: Average
```

Свойство-изображение для карточек настраивается в самой карточке Bases («Image property» =
`cover_file`): по документации это параметр вида, а не файла, поэтому генератор записывает его,
если версия Obsidian это позволяет, и иначе предлагает сделать один клик руками.

## 6. Что мы используем в Bases и что не используем

Проверено по официальной документации Bases (синтаксис, функции, карточный вид).

### 6.1. Используем (устойчиво)

| Возможность | Как используем |
|---|---|
| Встроенные виды `table`, `cards`, `list`, `kanban`, `map` | В1–В6, В11 |
| `filters` с `and` / `or` / `not` и сравнениями | Отборы по `type`, `read_status`, меткам |
| `file.hasTag()`, `file.inFolder()`, `file.links`, `file.ext`, `file.name` | Фильтр проблемных объектов, поиск вложений |
| `formulas` со встроенными функциями (`if`, `date`, `image`, `link`, `list`, `number`) | Вычисляемые колонки в таблице |
| `properties.*.displayName` | **Русские подписи колонок** — прямой ответ на требование ADR-003: ключи английские, подписи русские |
| `summaries` (Average, Sum, Filled, Unique…) | Средний рейтинг на полке, число заполненных полей |
| `groupBy` + `groupOrder` | Канбан проектов по статусу |

### 6.2. Не используем (не положимся в MVP)

| Возможность | Почему |
|---|---|
| **Свои функции в фильтрах и формулах от плагинов** | В документации прямо сказано: «в будущем плагины смогут добавлять функции». Значит сейчас это не опора — свой `sb.hasErrors()` не делаем |
| **Свои типы видов от плагинов** | `type` выбирается из встроенных и добавленных плагинами видов, но контракт на чтение/запись настроек вида объявлен как будущий API. Свой вид «галерея Second Brain» внутрь Bases не встраиваем |
| **Формула `image()` как свойство-изображение в карточном виде** | Свойство-изображение принимает вложение, URL или hex-цвет; формула в таблице работает, в карточках — известная проблема сообщества. Поэтому — теневое свойство `cover_file` (DL-144, DL-153) |
| Ссылка на заметку как свойство-изображение | Не поддерживается: обёртка `media` — заметка, а не вложение |
| Dataview / DataviewJS как механизм | Убраны из `mechanism` (§3) |

> [!important] Следствие для теневых свойств
> Поскольку формулы и свои функции не опора, теневое свойство `{key}_file` — **единственный**
> способ показать обложку в карточном виде. Оно остаётся обязательной частью механизма медиа,
> а не удобством. Правило `media.referrers.shadow_synced` — уровня `warning`, команда
> `sb-resync-media-shadows` чинит расхождения.

## 7. Диагностики в представлениях

Проблема: как показать «в этой записи есть ошибка» в таблице Bases, если свои функции запрещены.

**Решение: служебные метки (термин).** Плагин после проверки (уровни 2–4, 6) пишет в `tags`
объекта служебные метки:

| Метка | Когда ставится |
|---|---|
| `sb/error` | Есть хотя бы одна диагностика уровня `error` |
| `sb/warning` | Есть `warning`, но нет `error` |
| `sb/info` | Есть только `info` |

Метки убираются, когда проблема исправлена. Тогда в Bases работает обычный встроенный фильтр:

```yaml
filters:
  and:
    - note.type == "book"
    - file.hasTag("sb/error")
```

**Где ещё видны диагностики:**

| Место | Как |
|---|---|
| Панель объекта (В7) | Список диагностик с сообщениями и кнопками исправления — основное место |
| Карточка объекта | Значок и счётчик рядом с заголовком |
| Таблица/карточки Bases | Через служебные метки (фильтр) и через колонку `sb_issues` — по желанию |
| Статусная строка | Число ошибок в хранилище после `validate-vault` |
| Журнал проверок | Файл `.sb/logs/validation-{date}.json` (формат — шаг 8e) |

**Почему метки, а не свойство:** метки — свободный механизм, они не объявляются в метамодели
(спецификация v1.0 §12), их видно в поиске Obsidian, и их можно снять руками. Свойство `sb_issues`
требовало бы объявления и попало бы в формы пользователя. Вариант со свойством оставлен как
запасной — вопрос в конце документа.

## 8. Уровень контроля 5 — проверка представлений

Запускается **лениво**, при открытии представления (ADR-011 часть 6).

| Что проверяется | Правило |
|---|---|
| Файл `.base` существует и парсится как YAML | `view.base.parsable` |
| Целевой тип существует и не абстрактный | `view.target_type.exists` |
| Каждое свойство в `order` / `filters` объявлено в метамодели | `view.property.declared` |
| Механизм доступен (Bases включён в этой версии Obsidian) | `view.mechanism.available` |
| Свойство-изображение карточек указывает на теневое свойство, а не на обёртку | `view.cards.image_property` |
| Представление не ссылается на `deprecated`-свойства | `view.lifecycle.not_deprecated` |

Если проверка не прошла, представление **не ломается**: плагин показывает диагностику
в панели и предлагает действие («обновить представление», «открыть свойство»).

## 9. Контракт `BasesAdapter`

Черновик v1.1 §18.6 требовал изолировать Bases от ядра. Фиксируем как норму:

| Требование | Норма |
|---|---|
| Ядро не знает о Bases | `SchemaEngine`, парсер и валидация не импортируют ничего из адаптера |
| Адаптер один | Модуль `bases-adapter` (реестр модулей — шаг 8c) |
| Проверка доступности | При старте: существует ли внутренний плагин `bases`; если нет — механизм `base` помечается недоступным |
| Деградация | Для каждого представления из §4 указан запасной путь; команда `show-object-list` покрывает В1–В6 |
| Отключение Bases не ломает данные | `.base`-файлы остаются в хранилище как обычный текст; метамодель и объекты не меняются |
| Версионная зависимость | Адаптер проверяет версию Obsidian и не использует возможности новее минимальной поддерживаемой |

## 10. Правила валидации представлений

Группа **K** в [[../validation/rules|едином реестре]] — 7 правил (§8). До появления представлений
этих правил в реестре не было; они добавлены заранее, чтобы движок валидации не переделывать.

## 11. Открытые вопросы

- [ ] **11.1. Служебные метки или свойство `sb_issues`.** Предложение ассистента: метки (§7).
      Альтернатива — свойство: его можно показать колонкой, но оно попадёт в формы пользователя
      и потребует объявления в метамодели.
- [ ] **11.2. Папка `.base`-файлов**: `Metamodel/views/` или `Views/` в корне хранилища.
      Предложение: `Metamodel/views/` — рядом с определениями, чтобы не плодить корневые папки.
- [ ] **11.3. Регенерация представлений**: спрашивать каждый раз или только при изменении
      маркера версии. Предложение: спрашивать, если файл правили руками.
- [ ] **11.4. Канбан проектов** (В6) зависит от свойства `status` типа `project`, карточка которого
      ещё не описана. Если статусов не будет — представление снимается.
- [ ] **11.5. Средний рейтинг в `summaries`** работает по числу; у нас `rating` — число 1–10,
      поэтому итог корректен. Нужна ли медиана вместо среднего — вопрос вкуса, оставлено на потом.
