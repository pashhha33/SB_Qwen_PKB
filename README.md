# Second Brain

Репозиторий: <https://github.com/pashhha33/SB_Qwen_PKB>

Метамодель личной базы знаний и плагин для [Obsidian](https://obsidian.md), который её поддерживает.

**Что это.** Не «список типов заметок», а самоопределяющаяся объектная модель: тип объекта, свойство,
тип свойства, тип отношения, отношение, таксономия, фасет, категория, представление и автоматизация —
тоже объекты со своими `id` и `type`. Модель расширяется без изменения кода плагина.

**Стадия проекта.** Метамодель версии `0.23.0` — зафиксированы фундамент (идентификация, хранение,
имена полей, объём первого прохода), классификация, атрибуты, связи, перечисления и даты;
добавлены тип `chapter`, отношение `contains`, фасет `genre` и механизм условных свойств
`applies_when` (включая мультивыбор через `includes_any`); описаны карточками **все 15 типов ядра** —
`book`, `person`, `chapter`, `media`, `project`, `knowledge`, `work`, `activity`, `object_type`,
`property`, `relation_type`, `relation`, `taxonomy`, `facet`, `category`; у человека род занятий стал триггером свойств по профессиям,
у обёртки медиа описано поведение в базе (встраивание, карточки Bases, кнопки, мастер создания).
Ядро — **15 типов** и **5 типов отношений**, реестр — 53 записи (пересчёт аудита A9),
**одиннадцать принятых ADR**, **167 правил валидации** в едином реестре (14 групп A–N), **25 перечислений** (23 закрыто), **45 модулей** плагина в реестре MVP, **18 команд**.
Утверждены этапы реализации A–E и границы MVP; описаны представления (12 штук) и чем они рисуются.
Принят раздел **12 «Пустые ссылки и псевдонимы»**: создание объекта кликом по неразрешённой ссылке,
`title` из текста ссылки, выбор типа по контексту свойства и отношения, сбор псевдонимов в `aliases`
(ответы пользователя Б / А / А / А, DL-184…DL-188).
Шаг **8 «План реализации» завершён целиком**: этапы A–E, границы MVP, 12 представлений,
45 модулей, 7 карточек интеграций, правила миграций, дерево типов и иерархия, RDF-направление
(DL-160…DL-212). Карточки типов ядра — **15 из 15, все созданы** (DL-213…DL-217);
пункты чек-листа готовности A2/A3 закрыты — в блоке A остался только итоговый аудит A9.
Код плагина ещё не начинался.

## Главные правила проекта

| Правило | Где зафиксировано |
|---|---|
| Документация на русском, идентификаторы и код на английском | [[docs/adr/ADR-003-bilingual-keys-and-label-layer\|ADR-003]] |
| Локально и офлайн, без внешних API и LLM в MVP | промпт проекта, DL-002 |
| `id` объекта — голый ULID, имя файла `{TYPE_PREFIX}-{ULID}.md` | [[docs/adr/ADR-001-identity-and-file-naming\|ADR-001]] |
| Определения метамодели — Markdown-заметки в хранилище; `.sb/` — только служебные данные | [[docs/adr/ADR-002-source-of-truth\|ADR-002]] |
| Элементы метамодели создаются командами плагина, а не ручным редактированием | [[docs/adr/ADR-004-first-pass-scope-and-command-driven-authoring\|ADR-004]] |
| Классификация: `taxonomy → facet → category`, обязательность задаёт фасет | [[docs/adr/ADR-005-classification-model\|ADR-005]] |
| Фасет — самостоятельный объект, таксономия необязательна, второй путь классификации запрещён | [[docs/adr/ADR-007-facet-independence\|ADR-007]] |
| Тип свойства `media_reference`: цель ссылки, семь настроек, миниатюры через публичный API | [[docs/adr/ADR-008-media-property-type\|ADR-008]] |
| Семь типов значений; множественность задаёт только `cardinality`; 8 системных атрибутов и 6 инвариантов | [[docs/adr/ADR-006-system-attributes-value-types-media\|ADR-006]] |
| Значения перечислений — английский `snake_case` + русская подпись; частичные даты через `00`; редактируемый шаблон вывода даты | [[docs/adr/ADR-011-enumerations-dates-lifecycle\|ADR-011]] |
| 167 правил валидации в едином реестре; система не переписывает неправильные данные молча | [[docs/validation/rules\|rules]] и [[docs/validation/severity-policy\|severity-policy]] |
| Связи: `link_mode` в свойстве, `origin_property`, двусторонняя кардинальность, симметрия, роли | [[docs/adr/ADR-009-relations-model\|ADR-009]] |
| Экземпляры связей — в `.sb/relations/` (JSON Lines), чтобы не засорять граф Obsidian | [[docs/adr/ADR-010-relation-storage\|ADR-010]] |
| Даты в локальном времени без смещения; представление — настройка плагина | ADR-006 |
| Система не должна молча переписывать неправильные данные | спецификация v1.0 §19, сохранено |
| Старые документы не удаляются, а помечаются `deprecated` / `superseded` | [[docs/README]] |
| Условные свойства: `applies_when` влияет на показ, но никогда — на хранение; операции `equals`, `in_category`, `includes_any` | [[docs/metamodel/04-attributes\|04-attributes §11]] |
| Представление в MVP — артефакт (`.base`-файл, код-блок, панель), а не объект метамодели; механизмов три | [[docs/metamodel/08-views\|08-views]] |
| Этапы реализации A–E и границы MVP зафиксированы и приняты | [[docs/roadmap/phases\|phases]], [[docs/roadmap/mvp-scope\|mvp-scope]] |
| Обёртка медиа показывает изображение при встраивании (инвариант И8) и рисует обложку в Bases через теневое свойство `{key}_src` | [[docs/metamodel/entities/media\|карточка `media` §7]] |

## Как вести документацию

Коротко (полностью — в [[docs/README]]):

1. Новое решение → артефакт **сразу**, в тот же ход.
2. Новые файлы создаём, старые не удаляем; устаревшему ставим `status` и `superseded_by`.
3. У каждого артефакта есть frontmatter: `doc_type`, `status`, `version`, `created`, `updated`.
4. Термины — в глоссарий сразу, в тексте даём ссылку, а не повторное объяснение.
5. Каждое изменение метамодели — запись в changelog с версией, причиной и ссылкой на ADR.
6. Контрольная точка обновляется после каждого сообщения с решениями.
